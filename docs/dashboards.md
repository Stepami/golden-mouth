## Конкурсные показатели

| Показатель | Как считать | Источник |
|---|---|---|
| DAU | `count(distinct player_id)` по календарному дню, `activity_kind = real` | `product` |
| Обращения / DAU | число GenAI operations за день / DAU | `gen_ai.client.operation.duration` и `product` |
| Токены | сумма input/output token usage по модели и операции | `gen_ai.client.token.usage` |
| LLM-cost / DAU | сумма измеренной стоимости шлюза в рублях за день / DAU; при отсутствии стоимости — отдельная оценка по токенам и версионированному прайсу | `gen_ai_usage_cost` в GenAI traces + `product` |
| Ошибки | 5xx и Error/Critical по часу, route и exception type | HTTP metrics + `backend` |
| Нагрузка | RPS, p50/p95/p99 latency, active requests, GC, allocations, exceptions, thread-pool queue | ASP.NET Core + runtime metrics |

Тестовые и отладочные обращения не должны попадать в конкурсный расчёт. Production-события имеют `activity_kind = real`; тесты проекта не экспортируют OTLP.

Техническая таблица «Вызовы языковой модели» считает завершённые chat-спаны за выбранный период, включая ошибки. Фильтр использует `gen_ai_operation_name = 'chat'` и совместимые имена `chat` / `chat <модель>`. Группировка: модель запроса, иначе модель ответа, иначе суффикс имени спана, иначе `unknown`. Спаны без модели не теряются. Число отражает доставленные трейсы; незавершённые или потерянные спаны в него не входят. Это техническая диагностика, без фильтра реальной активности для конкурсного расчёта.

## Стоимость шлюза

Для streaming бэкенд передаёт `stream_options.include_usage = true` и читает числовое `usage.cost` из чанка ответа. Поле появляется только при серверной настройке `litellm_settings.include_cost_in_streaming_usage = true`; включить её обычным параметром запроса нельзя. `gen_ai.usage.cost.method = stream_usage` обозначает источник. Обычный успешный ответ использует числовые `X-Litellm-Response-Cost`, `X-Litellm-Response-Cost-Input` и `X-Litellm-Response-Cost-Output`; при отсутствии общей стоимости поле не добавляется. Заголовки streaming не используются: на момент отправки они ещё не содержат фактических расходов. В OpenObserve это те же поля `gen_ai_usage_cost`, `gen_ai_usage_cost_input` и `gen_ai_usage_cost_output`, которые использует встроенная LLM observability. Дополнительного counter нет; учёт input/output токенов остаётся стандартным. Переданная стоимость имеет приоритет над встроенным прайсом OpenObserve v1.0.4.

`gen_ai.usage.cost.currency = RUB` и `gen_ai.usage.cost.source = gateway` обозначают валюту и происхождение суммы. Встроенный интерфейс может показывать долларовую подпись; числовое значение не конвертируется. Для рублёвых запросов нужно фильтровать `gen_ai_usage_cost_currency = 'RUB'` и `gen_ai_usage_cost_source = 'gateway'`, чтобы не смешивать измеренные расходы с оценками по прайсу. Отсутствующая, отрицательная, бесконечная или нечисловая общая стоимость не добавляется приложением; явный ноль допустим. Сам OpenObserve может записать ноль по своему прайсу — наличие измерения определяется также полем source.

Policy выполняется после retries для обычных ответов. Streaming стоимость записывается в существующий GenAI-спан при получении usage-чанка; `LlmSpendWriter` обслуживает обе обёртки. Отдельных запросов `/spend/logs`, Polly lookup и пауз после стрима нет. Если шлюз не прислал стоимость, поле не добавляется; отсутствие измерения не подменяется нулём. Незавершённые или потерянные spans и отсутствие стоимости в ответах могут уменьшать сумму: это не точная бухгалтерия ключа, сверка с `/key/info` остаётся необходимой.

Старый расход ключа без детализации регистрируется отдельно через MCP ingestion в log stream `llm_cost_ledger`: `event_name = historical_spend_snapshot`, стабильный `event_id`, `cost_rub`, `currency = RUB`, `source = gateway_key_spend`, `scope = project_key`, `detail_available = false`, `snapshot_at` и `_timestamp` момента снимка. Реальные суммы и идентификаторы записей не хранятся в Git и не добавляются в настройки бэкенда. Перед повторной записью проверяется `event_id`; при агрегации дубликаты одного события сворачиваются через `max(cost_rub)`.

Общий расход: один начальный снимок + измеренные вызовы строго после снимка. Повторные cumulative снимки ключа нельзя складывать друг с другом. Старый расход показывается отдельной строкой «До начала детализации»; он не распределяется по моделям, дням или DAU. Между снимком и включением нового сбора может остаться пробел: он требует нового снимка ключа и переноса точки отсчёта, а не выдуманной детализации. Запись не восполняет последующие потери телеметрии и не заменяет сверку с `/key/info`.

Встроенная карточка «Общая стоимость» на экране ИИ → Аналитика считает `sum(gen_ai_usage_cost)` по выбранному trace stream и диапазону времени. Запись из `llm_cost_ledger` в неё автоматически не входит. Чтобы включить подтверждённый начальный снимок именно в эту карточку, можно однократно импортировать в `backend` отдельный OTLP span `historical_spend_snapshot` со стоимостью, валютой, стабильным event ID и признаком отсутствия детализации. У него нет `gen_ai.operation.name`, модели, токенов или сообщений: это снимок общей суммы, а не LLM-вызов. Перед импортом проверяется отсутствие event ID; повторный импорт недопустим. Для просмотра суммы диапазон должен включать момент снимка. После такого импорта снимок из log ledger повторно не прибавляется. Импорт в production требует явного подтверждения конкретной записи; он не выполняется бэкендом при старте.

## Поля продуктового stream

`ProductTelemetry` пишет плоские log attributes: `event_name`, `player_id`, `event_time_unix_ms`, `received_time_unix_ms`, `session_id`, `platform`, `screen`, `previous_screen`, `world`, `age_group`, `registration_source`, `launch_surface`, `experiment_plus_offer` и разрешённые `prop_*`. Тексты постов, сообщений, комментариев, имена, Telegram ID и `initData` не экспортируются.

Для DAU и когорт используется `player_id`, для сессий — `session_id`. Эти поля допустимы в log stream, но не должны становиться labels OTel-метрик.

Серверное `world_created` фиксирует создание мира: `world_id` — ID экземпляра, `template_id` — UUID шаблона или null, `difficulty` — easy/normal/hard, `age_group` — из профиля. Источник записывается в `player_created` при регистрации; отдельного поля в профиле и миграции нет. Источник и возраст берутся из событий; мир и подписчики — из последнего по `_timestamp` события `world_audience_updated` каждого мира. Серверное `player_deleted` после удаления профиля исключает этот ID из всех SQL-панелей, включая исторические когорты и активность. Старые удаления без события неизвестны; снимки профилей больше не используются. `audience_known_accounts` показывает покрытие доставленных состояний; старые миры без состояния не считаются нулём.

## Продуктовый дашборд v2 (#127)

Три вкладки: **Обзор** (текущие аккаунты, DAU/WAU/MAU, календарная активность, stickiness, публикации и подписчики), **Воронка и удержание** (прохождение в горизонтальных полосах с числами; отдельно D1/D3/D7 с eligible), **Активность** (процентная интенсивность по возрастам, посты/время, способ запуска и устройство, ошибки генерации).

Общие single-select фильтры: период анализа 7/30/90 дней, мир, возраст, источник регистрации, способ запуска. Выбор `all` означает все сегменты; `unknown` позволяет видеть неизмеренные старые данные. Запросы воспроизводятся генератором `observability/dashboards/build.py` и общим модулем `product_v2.py`. Источник для каждого запроса — 90 дней, отображаемый диапазон задаёт явный фильтр периода; нативный date picker не должен незаметно обрезать источник для этапов воронки и событий удаления.

Дни — по Москве; для подписей графиков открывать с `timezone=Europe%2FMoscow`. Автообновление — `refresh=1m`, поскольку OpenObserve хранит интервал в URL. Карточка «Всего аккаунтов в Mongo» использует `max(reki_players_registered)`: сервер раз в 30 минут вызывает `CountDocumentsAsync`, без перебора профилей. Это общий счётчик без фильтров сегментов; отсутствие метрики не означает ноль. SQL-панели показывают наблюдаемую аудиторию за доступную историю событий и исключают все ID с доставленным `player_deleted`. Покрытие событий может быть неполным и не равно общей базе Mongo. Проценты retention имеют собственные зрелые базы и не являются этапами последовательной воронки.

Новый прирост подписчиков измеряется только с момента доставки серверного delta, а способ запуска — с момента доставки launchSurface. Неполное покрытие показано в таблицах; NULL не означает ноль. Графики не подменяют отсутствие измерений демо-значениями. Правила полностью описаны в [analytics.md](analytics.md#продуктовый-дашборд-v2--127).

Дополнительный общий переключатель «База воронки и удержания» позволяет исследовать старые профили по первому наблюдению без подмены этого события регистрацией. По умолчанию — подтверждённая регистрация; legacy-режим явно обозначен.

## Фоновые задачи (#146)

Задачи `RestoreEnergyJob` (раз в две минуты) и `RefreshRegisteredPlayersJob` (раз в 30 минут) запускаются по расписанию. Настройки описаны в [deployment.md](deployment.md#фоновые-задачи-146).

В OpenObserve выполнения видны в traces с instrumentation scope `TickerQ`. Логи выполнения попадают в `backend`; gauge `reki.players.registered` сохраняет прежнее имя и семантику. Новых продуктовых событий и снимков профилей нет.


С 2.5.0 (#215) world_id — UUID экземпляра в формате D; template_id обозначает происхождение, difficulty — механическую сложность. Старые обозначения миров больше не отправляются как world/BalanceKey. Исторические внешние события не переписываются. При сравнении периодов нормализовать строковые GUID world_id (с дефисами и без) и учитывать, что ранние составные ID заменены детерминированными UUID по алгоритму миграции; исходные старые события сохраняются.

### Разрез репостов и цитат (#205)

По `post_scored` различать `prop_publication_kind=post|repost|quote`; отсутствие поля исторически означает `post`. Конверсия 1→2→3 обычных постов исключает репосты и цитаты, они считаются отдельными разрезами. Отдельных событий награды репоста нет. Сохранённые серверные панели в этом PR не публикуются.

## Тест браузерных лендингов — #205

Основной отчёт — в продуктовом OpenObserve после выпуска анонимного сбора через `/events`.
Яндекс.Метрика получает прежние цели параллельно для дополнительной сверки;
посещение её интерфейса для продуктового анализа не требуется.

### Полная A/B-воронка OpenObserve

После расширения `/events` источником служит product:
landing_view → landing_continue → landing_auth_complete →
landing_character_selected → landing_profile_link → первый обычный
post_scored → landing_reaction_viewed. Мир уже может быть выбран на лендинге,
поэтому посещение каталога после авторизации не является обязательным шагом.

Когорту задаёт первое landing_view попытки в выбранных датах; последующие шаги
могут произойти после конца этого периода. Связь строится по visitor_id + entry_id,
профиль — только из серверного landing_profile_link. Публикация должна быть
обычной (publication_kind отсутствует или post), принадлежать связанному
профилю и произойти после начала попытки. Реакция привязана к entry_post_id.
Одинаковое окно конверсии для A/B — 24 часа; незавершённые сутки отдельно.

Чистое рекламное сравнение: experiment=entry_v1, source=link, switched=false,
initial_variant=variant, одинаковая кампания. Direct и неизвестная атрибуция —
отдельные группы. До появления новых полей после deployment старая сверка
авторизованных событий не считается полной воронкой.

SQL-шаблон полного сравнения: `observability/dashboards/panel-sql/product-landing-ab.sql`.
Параметры периода задают первое посещение, история последующих шагов читается
до конца 24-часового окна. Посетитель, переключавший вариант, исключается по
всей доступной истории. Полный acquisition-отчёт показывается для всех возрастов:
возраст неизвестен у ушедших до регистрации. Возрастные срезы применимы к
авторизованной части и явно меняют базу сравнения.
Шаблон нельзя публиковать до выпуска сборщика, появления полей в stream и
проверки SQL на фактической схеме. До этого текущая панель наблюдаемых событий
остаётся частичной и не определяет победителя A/B.

Отдельные страницы миров: `/?landing=hogwarts`, `/?landing=infobiz`, `/?landing=evening`, `/?landing=houses`; разводящая — `/?landing=worlds`. Доли трафика для расширенного теста задаются маркетологами, не приложением. Сегментировать по реальному `landing_variant`, сохранять фильтр `landing_switched=false`.

После выпуска сверять посещения по одинаковым рекламным кампаниям и периоду в OpenObserve и Яндекс.Метрике. Метки кампании не подтверждают подлинность посещения. До фактической сверки расхождения и полнота сбора остаются непроверенными.

Уведомления: число принятых сервисами отправок (`notification_sent`) отделяется
от подтверждённых открытий Web Push (`notification_opened`, `prop_kind=webpush`).
Отправки не входят в активность игроков. Для Telegram открытие не выводится
как ноль, поскольку канал пока не имеет отдельного измеряемого перехода.

В удержании выбранной когорты две линии с одной постоянной базой:
игровая активность и создание контента в конкретный день после регистрации.
Вторая линия считает уникальных игроков с `post_scored` (обычный пост, репост,
цитата) либо серверным `comment_created` (комментарий/ответ игрока), а не клики.
Будущие или незавершённые дни не показаны. До выпуска события комментария
исторические комментарии не восстанавливаются, и линия имеет неполное покрытие.

Для диагностики входа используйте цели Яндекс Метрики по `entry_id`: «Начать играть» / «Войти» → показ входа → действие провайдера → ответ SDK → обмен с API → регистрация при необходимости. Сравнивайте входы через две кнопки отдельно. В OpenObserve текущая когорта посадочной по-прежнему строится по «Начать играть». После входа ищите этапы в `screen_view`, `tap` и `onboarding_step`; успешную публикацию и ответ считайте по серверным `post_scored` и `comment_created`.

## Результат публикации (#356)

В `product` сравнивать `post_scored` (сохранение поста), `tap / result_card_viewed` (показ карточки), `tap / post_open_conversation` и `tap / result_open_next_post` (переходы). Целевое продолжение подтверждается следующим `post_scored` с видом `post` или `comment_created`, с разделением по типу действия. D1 считать по активным зарегистрированным игрокам из полностью наблюдаемых когорт. Гостевые цели Метрики показывают демо-воронку отдельно.

## Задания дня: доступные измерения (#321)

Для первого этапа интерфейса можно считать открытия полного списка по `event_name=tap`, `prop_id=daily_tasks_viewed` с источником `prop_kind=channel|profile` и переходы по `prop_id=daily_task_action` с типом в `prop_kind` и экраном назначения в `prop_to`. Встроенная карточка канала видна сразу. Учитываются переходы из её строк, просмотры встроенного списка и листание карточек в редакторе не считаются открытиями. Полная воронка «первый обычный пост → обучение → задания → сохранённое действие → второй обычный пост», доли и время перехода требуют телеметрии обучения, подтверждённого серверного прогресса и порядка публикаций. Текущие события измеряют открытия списка и переходы к действию.
