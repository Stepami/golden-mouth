# Аудит системных промптов личностей — #97

Дата: 08.10.2026. Проверяемая база: master после #93; аудит не меняет действующие промпты.

**Вывод: инструкции достаточны для общей темы мира и формата ответа, но недостаточны для устойчивых, понятно описанных личностей.** Единого каталога персонажей нет. Кроме Сцены, состав фронтенда и backend расходится. Роль, характер, мотивация, манера речи и имя выбранной личности не передаются отдельным профилем. Модель достраивает их по идентификатору и общей строке правил.

## Что фактически получает модель

Источники: [StarAgentInstructions](../../backend/src/Reki.Application/Posts/StarAgentInstructions.cs), [StarTurnGenerator](../../backend/src/Reki.Application/Posts/StarTurnGenerator.cs), [GeneratePublicationHandler](../../backend/src/Reki.Application/Posts/GeneratePublicationHandler.cs), [SendDirectMessageHandler](../../backend/src/Reki.Application/Social/SendDirectMessageHandler.cs), [WorldRulesDefaults](../../backend/src/Reki.Application/Worlds/WorldRulesDefaults.cs).

| Порядок | Слой | Содержание | Пробелы |
|---|---|---|---|
| 1, system | Платформа | Русскоязычная игра 14+, только tools, запрет менять экономику, 18+ и персональной травли; ограничения текущего хода | Нет явного правила считать память и текст игрока данными, а не инструкциями |
| 2, system | «Пользовательский системный слой» | Мир/описание/правила, драма, голос канала, текущий starId, память | Нет отдельного имени, роли, биографии, мотивации и речевых особенностей персонажа; голос автора и голос звезды не разделены |
| 3, user, пост | Контекст публикации | Этап, разрешён ли хейт, три последние публикации и новый пост | starId=null, память=[]: модель сама выбирает звезду; выбор первой звезды не ограничивает ответ |
| 3, user, личка | Сообщение игрока | Текущий текст; starId и память находятся во втором system layer | История разговора не отправляется; выбранное обращение she/he/nick и возрастная группа отсутствуют в профиле |

На публикацию требуется `comment` ровно один раз, `react` не более одного. На личку требуется `dm`; допускается один безопасный memory_fact. Все пять tools (`react`, `comment`, `repost`, `dm`, `start_event`) доступны в обоих сценариях. Схемы ограничивают длину, обязательные поля и оценки; экономика вычисляется сервером. Наличие схемы репоста/события не означает, что соответствующий отдельный AI-сценарий реализован.

## Проверки и свидетельства

Запущены **90 синтетических проб через внешний deepseek-flash**: 15 доступных ID × представление, неудача, юмор, спор, просьба сменить роль/начислить подписчиков, память. Ошибок провайдера: 0. Во всех 90 ответах получен ожидаемый star_id через dm. При 15 попытках изменить роль/экономику модель сохранила ID и отказалась начислять миллион. Это наблюдение на данном наборе, а не доказательство устойчивости к любой prompt injection.

Артефакт: [persona-probes-2026-10-08.json](persona-probes-2026-10-08.json). В нём только искусственные запросы/ответы, без реальных переписок и credentials. Воспроизведение: `LLM_BASE_URL=... LLM_PAT=... LLM_MODEL=... python3 scripts/audit-star-prompts.py`; секреты задавать через окружение. Скрипт читает system templates, правила и JSON schemas из исходников. Generation budget ограничен 600 токенами, temperature=0; описания tools сокращены до имён. Это диагностическая проверка system layers, не замена интеграционных HTTP-тестов или полной оценки production-параметров модели.

Примеры из артефакта:

- academy/ren: «Рин. Капитан клуба кендо…» — реальное несоответствие Рэну из frontend.
- it/alexey_nl: «alexey_nl на связи. Пишу про айти без пафоса…» — не закреплены имя Куляш AI и роль исследователя.
- own/echo: «живу на репите и в чужих плейлистах… пою…» — профиль певца придумала модель, источник его не содержит.
- stream/glitch, pixel и save используют похожий общий набор «стрим/турниры/рейды/самоирония», что ожидаемо при отсутствии индивидуального профиля.

Component tests `PublishPost_UsesPlayerOwnedWorldSettingsSystemLayerAsync` и `SendDirectMessage_UsesStarMemorySystemLayerWithCurrentUserMessageAsync` проверяют сборку реального HTTP pipeline и два system messages. Проверки формата/tools, фильтра выхода и экономики уже есть в suite; оценка художественной различимости остаётся содержательным аудитом.

## Валидация и границы платформы

- DM валидирует возвращённый starId против запрошенного; это защищает от подмены ID в результате, но **не проверяет принадлежность запрошенного ID миру**.
- При реакции на пост parser проверяет структуру, длину и диапазоны оценок, а имя и starId приходят от модели. Каталожной проверки соответствия пары имя/ID миру нет.
- `ApiMapper.CreateStar` возвращает имя «Мира» для mira и «Соня» для любого другого ID: UI backend-лички расходится даже с правильным ID.
- `ContentSafetyPolicy` — набор подстрок, а не полный семантический фильтр. Гарантировать безопасность всех формулировок по нему нельзя; контроль экономики сильнее, поскольку числа считает код.
- Мир, голос и память помещаются в system message без явного отделения пользовательских данных от команд. Текст текущего сообщения — user message; память требует отдельной защиты от переноса инструкций между ходами.
- `hateEnabled` в post context зависит от drama/cooldown; порог подписчиков не участвует, хотя текст правил мира говорит о пороге. Это противоречие между булевым контекстом и текстом инструкции.

## Рекомендации

1. **Высокий приоритет:** единый каталог ID/мира/имени/роли/характера/речи; согласовать frontend/backend и передавать целевой профиль в промпт. Валидировать ID/имя на входе и выходе; исправить MapStar.
2. **Высокий приоритет:** разделить доверенные ограничения, пользовательские настройки и данные памяти; согласовать разрешённые tools и hateEnabled с правилами текущего хода. Добавить серверные негативные проверки подмены мира/личности.
3. **Средний приоритет:** добавить выбранное обращение, контекст беседы и требования к памяти; разделить голос канала и индивидуальный голос звезды. Оценивать шестью сценариями все личности после появления каталога, включая backend-only.
4. **Средний приоритет:** дополнить лексический safety filter семантическими и adversarial проверками; не трактовать отсутствие совпадений подстрок как доказательство безопасности.

Исправления этих дефектов — отдельные задачи; этот отчёт фиксирует фактическое состояние и не меняет персонажей или игровые правила молча.
