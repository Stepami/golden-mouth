## 1. Главный принцип: модель пишет текст, код считает игру

| Делает LLM | Делает код |
|---|---|
| Оценивает пост по трём шкалам мира (0–1) и объясняет «за что» | Подписчики, залёт, провал, опыт, уровни, отношения, лимиты |
| Пишет комментарии фанатов и звёзд, ответы в личке, тексты событий | Кто и когда комментирует, сколько ответов, когда событие |
| Дописывает черновик игрока в голосе канала («Подскажи») | Фильтр 14+, кризис, жалобы, антифрод |
| Собирает правила своего мира из описания | Какие правила можно править (правило 14+ нельзя) |

Звезда действует только инструментами: `react`, `comment`, `thread_reply`, `repost`, `dm`, `start_event(type)`. Модель не может изменить экономику: любые числа в её ответе игнорируются.

### LLM-клиент

- В Application используется абстракция `Microsoft.Extensions.AI.IChatClient`; конкретный провайдер подключается только в Infrastructure через `Microsoft.Extensions.AI.OpenAI`.
- Провайдер предоставляет OpenAI-compatible API. Для MVP используем Chat Completions; переход на Responses API требует отдельного решения и подтверждённой поддержки провайдером.
- Решено 05.10.2026: так как весь игровой контент русскоязычный, основная модель MVP — `gigachat3.5-432b-a28b` без reasoning. Бюджетный fallback — `deepseek-v4-flash` в non-thinking режиме; в MVP переключаем его вручную через конфигурацию, без каскадного повторного вызова. Reasoning-вариант GigaChat оставляем только кандидатом для редких сложных задач. Исследование и тарифный снимок: [llm-model-research.md](llm-model-research.md).
- Base URL, Bearer token и имя модели приходят только из typed options: `Llm__BaseUrl`, `Llm__ApiKey`, `Llm__Model`. Production-значений в репозитории, Compose-файлах, issue и логах нет. Compose передаёт настройки провайдера в backend из переменных окружения `LLM_BASE_URL`, `LLM_PAT`, `LLM_MODEL`; выбор модели для локального запуска также остаётся вне репозитория.
- API вызывается только бэкендом. Фронт не получает URL провайдера, токен или прямой доступ к модели.
- Обычный игровой ход выполняется без reasoning с явными `Temperature` и `MaxOutputTokens`. Для ограниченной генерации и вызова tools достаточно `IChatClient`; многошаговый agent loop в MVP не нужен.
- Prompt каждого хода состоит из двух `System`-сообщений: неизменяемой policy платформы и JSON-данных настроек игрока, правил своего мира и безопасной памяти. Эти данные не могут менять policy, каталог, доступные tools или экономику. Готовые миры используют текущие серверные правила. Голос канала принадлежит игроку, голос звезды — каталогу. Текущий пост или сообщение остаётся `User`-вводом. Изменение доступной игроку настройки применяется уже к следующему вызову модели.
- Ответ модели считается недоверенным вводом: аргументы tools и структурированный JSON проверяются по JSON Schema, все поля строгого контракта обязательны, `additionalProperties: false`; неизвестные поля и любые числа экономики игнорируются.
- Timeout и отмена запроса выполняются вокруг `IChatClient`; поток ответа перечисляется через Mediator `IStreamRequest`, каждый update сохраняется в `Publication` отдельно. После начала потока автоматического повтора нет. Ошибка провайдера или небезопасный ответ не тратит пост и не раскрывает текст исключения игроку.
- В telemetry и логи не попадают Bearer token, полный URL провайдера, HTTP body, тексты игрока и ответы модели. Разрешены имя модели, latency, usage, finish reason и безопасный код ошибки.

## 2. Ход: потоковая публикация

1. Клиент создаёт UUID публикации и отправляет `POST /posts/publications`. Бэкенд проверяет лимит (`posts.free_per_day` / `plus_per_day` + бонусы) и сохраняет `pending`; повтор с тем же UUID и тем же содержимым возвращает сохранённый статус, с другим — 409.
2. Обработчики публикаций, ответов в треде и лички проверяют вход через `PlayerSafetyGuard.EnsureInputAllowedAsync` перед генерацией; асинхронность нужна только для сохранения кризисной паузы в БД. Сгенерированные тексты проверяются синхронно через `PlayerSafetyGuard.EnsureOutputAllowed` / `IsOutputAllowed`, включая личку, память и фоновые посты звёзд. Guard централизует прежние списки фраз и поиск подстрок без учёта регистра; `ContentModerator`, `IContentModerator` и отдельный вызов LLM для модерации удалены. Проверка не является семантической классификацией: контекст, отрицания и цитаты не учитываются. Создание и изменение мира не вызывают проверку содержания. При генерации публикации отказ сохраняется как `failed` с категорией и версией статической политики `2026-10-14.1`; при подтверждении публикации сохраняются повторные проверки входа и результата, а при ответе в треде — входа до генерации и перед коммитом. Небезопасная реплика в треде завершается кодом `unsafe_generated_content`, структурно неверный ответ модели — `ai_unavailable`. `IChatClient` используется только для генерации; его цепочка сохраняет настройки провайдера, DeepSeek и телеметрию. Поток перечисляется обработчиком `IStreamRequest`, каждый update сохраняется в MongoDB отдельно.
3. Полный ответ собирается из сохранённых частей. Невалидный или небезопасный ответ переводит публикацию в `failed` без повторной генерации; пост не тратится. У подтверждённой ошибки части ответа очищаются сразу, короткая запись удаляется TTL-индексом через сутки. Незавершённый `pending` тоже имеет TTL на случай остановки процесса; при успешной генерации TTL снимается.
4. Успешная генерация переводит публикацию в `ready_for_moderation`. Клиент отправляет `POST /posts/publications/:id/moderation`; код считает итог по `balance.json`, а сохранение поста, списание доступного поста, запись нити и итогового статуса выполняются одной короткой MongoDB-транзакцией. LLM внутри транзакции не вызывается.
5. Модерация отдаёт JSON-массив `LiveEvent[]` в строчном wire-контракте `views` → `react` → `comment` → `typing` → `result`. Фронтенд последовательно показывает элементы массива с минимальными паузами для анимации; бэкенд отдаёт весь массив сразу. После обрыва клиент делает `GET /posts/publications/:id`: `completed` содержит результат, `failed` возвращает в редактор, `pending` или `ready_for_moderation` предлагает вручную проверить статус; автоматического повторного постинга нет.
6. Ответ в треде — один `POST /posts/:id/replies?worldId=…` с `{ requestId, commentId, text }` и SSE через Mediator `IStreamRequest`. Проверяются владелец мира, принадлежность поста миру, видимый целевой комментарий звезды и текст. Сохранённый `RequestId` возвращает актуальный пост без LLM и списания; другая цель/текст — 409. После проверки энергии модель вызывается вне транзакции. Проверенный промежуточный текст передаётся как `generating`, но ещё не опубликован. После проверки полного ответа сервер перечитывает пост, игрока и мир и заново проверяет энергию и бонус. Одна MongoDB-транзакция проверяет отсутствие ключа и ожидаемые версии трёх документов, сохраняет комментарии/реакции, списывает `energy.comment_cost` и начисляет бонус за первые `thread.bonus_replies` сохранённых ответов игрока. `completed` возвращает актуальный пост, остаток энергии и подписчиков. Ошибка после начала SSE — `failed` с безопасным кодом; до начала SSE используются ProblemDetails (400/404/409/422). До коммита обрыв отменяет сохранение, после него результат доступен через GET поста. Повтор использует тот же `requestId`. `ReplyLiveEvent.Status` типизирован enum `ReplyStatus` (Generating / Completed / Failed), все поля события заданы в primary constructor. JSON-значения статусов остаются `generating` / `completed` / `failed`.

### Тред: авторы, AI-контекст и энергия

- `AuthorKind`: Player / Star. `AuthorId` — Vogen над строкой `Player_ID` / `Star_ID`; Mongo хранит ту же строку через сгенерированный BSON serializer, как для остальных ID. Автор разрешается по полному `AuthorId` из владельца мира или его звёзд; исходный ID и тип берутся из найденного автора, отдельных свойств `Kind` / `Id` у `AuthorId` нет. Разделитель при валидации — первый `_`, остальные `_` принадлежат ID. Валидация принимает только точные префиксы `Player_` / `Star_` и непустой ID. Сгенерированные Vogen `Parse` / `TryParse` реализуют `IParsable<AuthorId>` и используют ту же валидацию. `PlayerId.ToAuthorId()` и `StarId.ToAuthorId()` создают тип явно через `AuthorId.Create`.
- `GamePost`: обязательный `WorldId`, `AuthorId`, `Version` и единственный массив `Comments`. Доступ определяется владельцем мира, авторство проверяется отдельно. `ThreadReplies`, `ThreadReply` и `CommentOperation` отсутствуют.
- `GameComment`: `Id`, nullable `ParentCommentId`, nullable `RequestId`, `AuthorId`, `Text`, `Hidden`, `Reactions`. `CommentReaction`: `AuthorId`, `Emoji`. Имена, аватары, роли, `Star`, `Me`, глубина, расход энергии и сумма бонуса в комментариях не хранятся. API разрешает автора из `World.Player` / `World.Stars`, сравнивая сохранённый `AuthorId` с результатом `PlayerId.ToAuthorId()` / `StarId.ToAuthorId()`, вычисляет `Me` относительно текущего игрока и глубину по цепочке родителей. Для отсутствующего автора возвращает данные `WorldStar.DeletedAccount`: имя «Удалённый аккаунт», пустые аватар, ник и роль; `Star = false` не позволяет предлагать ответ отсутствующей звезде. В `authorId` такого ответа остаётся полное сохранённое значение `AuthorId` без разбора строки, чтобы различать авторов реакций. Это применяется к ленте, комментариям, реакциям и повторной выдаче результата публикации. Ответ разрешён только автору из текущего `World.Stars`.
- Корень — глубина 0. Игрок отвечает выбранному комментарию звезды, выбранная звезда отвечает игроку; каждый ответ увеличивает глубину на 1. Разговор можно продолжать без ограничения глубины. Реакция ставится на комментарий игрока. Дополнительная реплика другой звезды — новый корень. Сервер проверяет принадлежность обеих звёзд миру и 14+.
- Контекст LLM: пост, цепочка выбранного треда, ответ игрока, личности звёзд и правила мира. Единственный tool `thread_reply`: `star_id`, `text`, `tone`, `emoji`, `additional_star_id`, `additional_text`, `additional_tone`; необязательные значения — пустые строки. Без оценок поста, hook и памяти лички. Модель не управляет энергией или бонусом.
- `PlayerProfile.EnergyUsed` заменяет `PostsUsed`. Пост стоит `energy.post_cost = 1`, ответ — `energy.comment_cost = 1`; AI входит в эту стоимость. Общий запас всех миров сохраняет прежние лимиты и бонусы из `posts.*`. Счётчик сбрасывается в 09:00 МСК. Рост и опыт поста учитывают `EnergyUsed`, поэтому комментарии сдвигают дневной бюджет прогрессии. `PlayerProfile.Energy` хранит готовый остаток; `EnergyUsed` — расход только для прогрессии. API `/me` и onboarding возвращают `energy` вместо `postsLeft` / `postsCap`; SSE ответа сохраняет поле `energyLeft`. Расчёт доступности действия использует только `Energy`.
- Миграция 2.2.0 переносит авторов, связи родителей, ключи и старые реакции из `ThreadReplies`, удаляет заменённые поля, переименовывает счётчик без оплаты старых комментариев, заполняет массивы/версии, обновляет индекс `WorldId, CreatedAtUtc`. Встроенные `Publication.Result.Post` мигрируются тоже. Неопределимые/неоднозначные авторы, циклы, потерянные родители и дубли ключей останавливают миграцию для явного разбора исходных данных; runtime-исправлений нет. Она сохраняет `AuthorId` строкой, принимает исторические поля, прежний вложенный `{ Kind, Id }` и готовые строки, проверяет принадлежность миру и допускает повторный запуск. Для строкового рефакторинга изменена сама 2.2.0, новая версия не вводится.

## 3. Оценка поста LLM

Вход: видимый игроку системный слой (описание и правила мира, градус драмы, голос канала), этап, последние 3 поста игрока и текст поста. В личке тот же слой дополнен выбранной звездой и её памятью. Выход строго JSON:

```json
{ "brave": 0.6, "humor": 0.8, "topic": 0.4,
  "why": [{ "icon": "😂", "label": "смешно" }, { "icon": "🔥", "label": "смело" }],
  "on_topic": true }
```

- `why` до 3 причин, только подписи, числа подставляет код (`+12`, `−6`).
- `on_topic: false` (пост не про мир) даёт причину «не про <мир>» и повышает шанс провала.
- Главный навык поста = шкала с максимальной оценкой, ему весь опыт, остальным по 15%.

## 4. Нить в конце хода

Каждый итог заканчивается одной нитью. На постах 1–9 дня она закрывается через 1–3 хода: ответ звезды придёт через пару постов, тема для следующего поста, близкая цель («до 1k осталось 40»). Только у последнего поста дня нить «на завтра», её закрывает сообщение бота в 9:00. Открыта одна нить, максимум две. Храним в `players.threads_open`.

## 7. Безопасность

- **Возраст:** год рождения и точный возраст не храним. `BirthGroup` остаётся `14-17` / `18+` для безопасности; optional `AgeBand` в onboarding и профиле — `14-17`, `18-24`, `25-34`, `35-44`, `45+` для аналитики, с проверкой соответствия BirthGroup. Младше 14: ничего не сохраняем.
- **Фильтр 14+** на входе (пост, ответ, описание своего мира) и на выходе (текст модели): сексуальный контент, насилие, наркотики, самоповреждение как тема для шуток, травля по внешности. Сработал на входе: мягкий отказ «так не получится, попробуй по-другому», пост не тратится. На выходе: подтверждённая ошибка без перегенерации и списания поста.
- **Кризис:** признаки суицидальных мыслей в любом тексте игрока → игра на паузе, экран 06-2 (14–17, телефон доверия 8-800-2000-122) или 06-3 (18+), хейт выключен на 7 дней. Детектор: классификатор + список фраз; лучше ложное срабатывание, чем пропуск.
- **Конфликт при проверке лички:** если состояние игрока изменилось во время сохранения кризисной паузы, `POST /dm/:starId` возвращает 409; генерация ответа и сохранение переписки не выполняются.
- **Жалоба:** реплика скрыта сразу у пожаловавшегося, разбор за 24 часа, журнал жалоб.
- **Удаление аккаунта:** стирает всё по игроку, включая память звёзд и аналитику с привязкой к ID.

Бэкенд хранит логи 30 дней и удаляет их вместе с аккаунтом.

События фронта (`POST /events`): `session_start`, `screen_view`, `screen_leave`, `tap`, `app_hidden`, `app_visible`, `onboarding_step` (age / world / channel / world_settings / done), `post_publish` (len, own_words), `post_result` (delta, viral, flop), `limit_reached`, `plus_interest`, `plus_bonus_only`, `invite_sent`, `share` (chat / story), `event_answered`, `challenge_post`, `report`, `crisis_shown`. Серверные события, полный список с полями и метрики теста: [analytics.md](analytics.md) («Что пишет бэкенд сам»), формат записи для дашбордов: [dashboards.md](dashboards.md).
Метрики теста: D1 ≥ 40%, D7 ≥ 15%, K (честный: приглашённый дожил до D1), доля упёршихся в лимит и что они выбрали, на каком посте впервые пишут своими словами, клик «Хочу Реки+».

## 11. API для фронта

Авторизация: `Authorization: TMiniApp <initData raw>`. ### Генерация карточек для сторис

Публичная ссылка строится из случайных внутренних ID игрока и поста. Она доступна любому, кто её знает, пока существуют игрок и пост. Маршрут проверяет принадлежность поста игроку и возвращает 404 для неверной пары и удалённых данных. Telegram загружает PNG без заголовка Authorization.

При реализации динамических PNG рендерер принимает целевой `Stream` и `CancellationToken`, а endpoint пишет результат через `HttpResponse.Body` / `BodyWriter`: готовая картинка не возвращается из Application как `byte[]`, не копируется через `MemoryStream.ToArray()` и не хранится в MongoDB. Если выбранный PNG-кодировщик требует seekable stream или выполняет только синхронную запись, используем ограниченный pooled/recyclable stream и затем `CopyToAsync` в response; синхронный I/O Kestrel глобально не включаем.

- `ArrayPool<byte>` / `MemoryPool<byte>` используем только для временных managed-буферов, которые реально нужны кодировщику. Буфер возвращается в `finally` только после завершения всех async-операций и не сохраняется в кеше после возврата в pool.
- Native-ресурсы рендера освобождаются детерминированно. Шрифты и SVG-иконки входят в backend image; на системные шрифты и emoji Linux не полагаемся.
- Число одновременных рендеров ограничено; ожидание уважает request cancellation. Публичный PNG отдаётся с `Cache-Control: no-store`, чтобы удалённые данные не сохранялись в HTTP-кеше.
- Перед выпуском проверяем под параллельной нагрузкой время p95, managed allocations, process RSS/native memory и освобождение ресурсов после отменённых запросов. Нагрузка не должна приводить к неограниченному росту очереди или памяти.

## 10. Окружение

Production-настройки LLM (`Llm__BaseUrl`, `Llm__ApiKey`, `Llm__Model`), токен бота и строка Mongo приходят только из переменных окружения сервера или защищённого secret store (#26). Отсутствующая обязательная настройка останавливает startup без вывода её значения. Локальный Compose использует те же переменные окружения, не меняя контракт конфигурации приложения. Фронт получает только same-origin runtime config для `/api/v1` и не знает адресов внутренних сервисов.

`docs/config/balance.json` включается в backend Docker image как `/app/config/balance.json` с правами только на чтение (`COPY --chmod=0444`). Бэкенд читает и валидирует его при startup; отсутствующий или невалидный файл останавливает запуск. В production конфиг не перезаписывается и не подменяется writable volume. Изменение баланса не требует правки кода, но требует пересборки и деплоя backend image.

### Уточнение #98 / #99 (08.10.2026)

Личка передаёт выбранное обращение и последние 12 сообщений с исходными user/assistant ролями. В prompt попадают до 20 коротких фактов памяти; инструкция вместо факта отбрасывается при сохранении и чтении. Неизвестный или чужой мирy ID возвращает 404 до вызова модели.

В публикации доступны только `comment` и `react`, в личке только `dm`. Комментарий содержит обязательный `tone`: `support`, `critique`, `hate`. Сервер проверяет пару star_id/name по звёздам выбранного мира и разрешает hate только при достижении `hate_from` выбранной сложности, drama не off и истёкшем safety cooldown. Проверка повторяется при подтверждении публикации. Невалидные действия не расходуют лимит. Проверка tone не доказывает смысл текста: LLM может неверно классифицировать реплику; лексические safety/memory фильтры также не являются полной семантической защитой.

Проверки и границы: [повторный аудит](audits/persona-prompts-after-98-99.md).

### Настройки и Реки+ (#104)

PATCH /settings принимает optional address (she/he/nick); POST /plus-interest принимает optional {interest: bool}, без тела interest=true для совместимости. Переход `plus: false → true` сразу добавляет разницу запасов Plus и Free в `Energy`; повторное `plus: true` не начисляет снова. Отключение Plus сохраняет текущую энергию до ежедневного сброса. Изменения баланса применяются к запасу при следующем сбросе. Одноразовый бонус `/plus-interest` увеличивает `Energy`, без изменения расхода. PlusNotifyRequested отделён от однократного бонуса PlusInterestClaimed; запрос bonus-only не включает уведомление. Обе записи используют CAS по версии профиля с ограниченным повтором. Оплата и бот-рассылка этим API не реализуются. Сохранённые notifications/quiet являются предпочтениями будущей доставки. Проверки: [settings audit](audits/settings-2026-10-08.md).


### Консолидация миров (1.2.0 / 2.0.0)

`players` хранит Telegram-идентичность, возрастную группу, обращение, навыки, общие дневные лимиты, Plus, рефералы и предпочтения уведомлений. `worlds` хранит экземпляры миров игрока. `world_templates` хранит готовые шаблоны; обе коллекции используют доменный класс `World`, у шаблонов `PlayerId` равен нулевому ID. Связь с шаблоном и активный мир в документе игрока не сохраняются.

Документ мира содержит канал (имя, ник, роль, аватар), стиль аватарки, голос, драму, подписчиков, прогресс публикаций, желания и достижения. Массивы звёзд (включая `StarTrait`, отношение и его дневной прогресс), ролей, правил и контента встроены в каждый мир и шаблон. Звёзды берутся из выбранного экземпляра мира; отдельного `StarCatalog` нет.

Удаление звезды при полном PUT мира убирает её из `Stars`, сохраняя посты, комментарии, реакции, переписку и память. `ArchivedStars` не используется: миграция `2.4.3` удаляет это поле целиком из `worlds` и `world_templates`, а также удаляет `AppearanceProfile` и `AgeBand` у действующих звёзд. Повторное добавление того же ID в тот же мир восстанавливает авторство по сохранённым `AuthorId` и доступ к переписке; отношение начинается с нуля. Пока звезда отсутствует, новые обращения к ней отклоняются. На фронте пустой сид показывает стандартный кружок с `?`, а возможность ответа определяется наличием автора в текущем составе мира.

Фронт получает шаблоны без авторизации через `GET /worlds/templates` и заполняет описание мира. POST /onboarding создаёт только игрока: возрастную группу, обращение и реферальную атрибуцию. Мир и звезда в его запрос не входят. После успешного создания игрока фронт отдельным запросом POST /worlds создаёт первый мир; при ошибке этого запроса повторяется только создание мира. `GET /me` возвращает только игрока. `GET /worlds` возвращает полные документы принадлежащих игроку миров, включая звёзд, роли и правила; фронт выбирает нужный экземпляр из этого ответа. Отдельных запросов мира и его правил нет. `POST /worlds` создаёт дополнительный экземпляр из полного описания. В запросе создания мира фронт передаёт описание мира со звёздами, ролями, правилами и контентом; выбор шаблона только заполняет этот объект на фронте. TemplateId содержит UUID исходного доступного шаблона или null для создания с нуля; каталог возвращает только активные шаблоны, POST сохраняет переданный TemplateId без повторной загрузки шаблона; доступ к созданию с нуля проверяется отдельно. PUT сохраняет исходный TemplateId. Сервер всегда назначает новый ID и владельца, выставляет начальных подписчиков и обнуляет прогресс. Онбординг доступен только новому игроку. Для существующего игрока запрос отклоняется с 409 без изменений игрока и миров; дополнительные миры создаются только через POST /worlds. Для операций, которым нужен мир, `worldId` обязателен и передаётся явно в маршруте либо query-параметре; заголовки и автоматический выбор мира не используются.

Миграция `1.2.0` создаёт коллекцию шаблонов с вложенными объектами непосредственно в C#; JSON-файлы при её выполнении не читаются. Миграция `2.0.0` создаёт полный мир каждого существующего игрока из шаблона, выбранного по старому полю `Player.World`, переносит поля и прогресс игрока и привязывает публикации, посты, треды, события и память звёзд к экземпляру мира. Повторное выполнение не перезаписывает изменённые шаблоны и игровые данные.

Миграция `2.0.1` заполняет отсутствующие и BSON-null обязательные массивы пустыми массивами в постах, памяти звёзд, событиях, публикациях, мирах и шаблонах. Существующие массивы и остальные поля сохраняются; повторное выполнение безопасно. Также она восстанавливает отсутствующий/null Experience навыков и старый нулевой Experience выше первого уровня из сохранённых Level/Progress по зафиксированным порогам опыта. Доменные модели читают эти свойства напрямую, без обходов старой схемы.

Решено 12.10.2026: доменный `World` хранит описание и интерфейсные метаданные в `Interface: WorldInterface`, владельца, настройки канала и прогресс — в `Player: WorldPlayer`. Сложность типизирована `WorldDifficulty` в домене и передаётся числом 1–3 в HTTP; драма типизирована `WorldDrama`, в HTTP используется строковый enum. `Presets`, `Handle`, `TotalPostsPublished`, `PostsSinceViral`, `ConsecutiveFlops` удалены. Для аватара остаётся единственный `Avatar`. Миграция 2.0.2 переносит поля обоих видов документов, преобразует драму и заменяет индекс владельца на `Player.PlayerId`, сохраняя звёзд и прогресс. HTTP-описание мира остаётся плоским; запрос создания принимает `avatar`. Залёты и провалы определяются вероятностью, детерминированный выбор привязан к ID публикации; первая публикация определяется отсутствием `Player.LastPostAtUtc`.

### Расширение аналитики #127

`POST /events` принимает optional `launchSurface` (`telegram-mini-app`, `browser`, `standalone`), старые клиенты остаются совместимы. Серверные события результата не принимаются из клиентского batch. `post_scored` экспортирует непрозрачный ID сохранённого поста и подписанный `SubscriberDelta`; после неуспешной генерации сервер пишет `post_failed` с ID попытки. Размеры наград и игровой баланс не меняются.

Число аккаунтов для аналитики задача TickerQ `RefreshRegisteredPlayersJob` получает раз в минуту через Mongo CountDocumentsAsync и отправляет gauge, без перебора профилей и чтений миров/приглашений. После очистки связанных данных и удаления профиля пишет player_deleted с activity_kind=lifecycle; SQL-панели исключают этот ID из всех расчётов по событиям. Мир и виртуальные подписчики фиксируются после записи мира/поста/ответа через world_audience_updated с activity_kind=inventory и не считаются активностью. Снимки профилей не отправляются; старые удаления без события неизвестны. Подробная семантика и поля — [analytics.md](analytics.md#продуктовый-дашборд-v2--127).

### Пагинация постов мира (#209, #211)

`GET /feed` и `GET /posts/mine` принимают через `[FromQuery]` общую модель `WorldPostsRequest` из `Reki.Api/Requests/Posts`: обязательный `worldId`, необязательный `cursor` (UUIDv7 поста), `pageSize` (по умолчанию 10). Лента включает посты игрока и AI-звёзд выбранного мира; канал — только собственные посты игрока. Доступ к миру проверяется до чтения. Имена параметров заданы штатными `[FromQuery(Name = ...)]`, присутствие `worldId` — `[BindRequired]`, размер по умолчанию для OpenAPI — `[DefaultValue]` с той же константой, что используется в инициализаторе свойства.

Обе ручки возвращают общий `PageResponse<T>`: `{ items, nextCursor }`. Элементы имеют прежние типы `FeedItemResponse` и `ChannelPostResponse`. Репозиторий сортирует по `Id DESC`; при заданном курсоре выбирает `Id < cursor`, без `Skip`. UUID хранятся в BSON Standard, поэтому порядок соответствует байтам UUIDv7. Миграция 2.4.8 заменяет индекс по времени индексами `(WorldId, _id DESC)` и `(WorldId, AuthorId, _id DESC)`. Также миграция 2.4.8 удаляет устаревший `ix_invites_player` по полю `PlayerId`; актуальные индексы по `InviterId` и `InviteeId` сохраняются. Повторная миграция ID не требуется: UUIDv7 уже введены миграцией 2.4.6.

Весь цикл страницы выполняет репозиторий: читает `pageSize + 1`, при наличии дополнительной записи удаляет её через `List.RemoveAt` и возвращает ID последнего оставшегося поста как `nextCursor`. Если продолжения нет, `nextCursor` равен `null`; пустая выборка возвращает HTTP 200 с пустым `items` и `nextCursor: null`. Подсчёта общего количества и дополнительной коллекции для отсечения нет. Некорректный курсор, UUID другой версии, неположительный `pageSize`, нечисловые значения и переполнение размера выборки возвращают HTTP 400 `ValidationProblemDetails`. Отдельный продуктовый максимум размера страницы не установлен; техническое ограничение — диапазон Int32 для `pageSize + 1`.

Первый запрос и обновление выполняются без курсора. Клиент передаёт полученный `nextCursor` в следующий запрос, пока он не станет `null`. Следующая страница загружается автоматически при приближении к концу списка. Обновление жестом вниз от начала списка заменяет накопленные страницы первой. Кнопок пагинации нет. При ошибке загруженные посты остаются видны; повтор выполняется обновлением жестом. Повторные запросы блокируются на время загрузки, дубли удаляются по `postId`, запросы предыдущего мира отменяются. Ключи кеша страниц обновлены для нового контракта; совместимость старых ссылок на заменённые ID не поддерживается, постоянной таблицы соответствий нет.

`WorldPostsQuery` требует явные `Cursor` и `PageSize`; внутренние сценарии генерации и публикации читают первую страницу без курсора размером 3 и 20 соответственно. POST-ручки не получают новых query-параметров. Чтение ленты сохраняет прежнюю постановку фоновой генерации. Генерация ID и идемпотентность джобы, `GetPostAsync` и `InsertPostAsync` остаются прежними. Payload фоновой генерации содержит стабильный `PostId` и обязательный `CreatedAtUnixMilliseconds` типа `long`. ID и Unix-время в миллисекундах создаются из одного значения часов при постановке задания. `CreatedAtUtc` поста восстанавливается через `DateTimeOffset.FromUnixTimeMilliseconds`; задержки и повторы не меняют ID и время. Старые задания без числовой метки не поддерживаются и завершаются ошибкой десериализации.

### Фоновая лента звёзд (#148)

После успешной публикации и сохранённого ответа в треде, а также с вероятностью `feed.open_probability` при чтении ленты, backend ставит одноразовый TimeTicker через type-safe `AddAsync<GenerateStarFeedPostJob, StarFeedRequest>`. Параметры содержат типизированные Vogen ID игрока, мира и будущего поста, а также Unix-время создания в миллисекундах (`long`). ID поста создаётся через UUIDv7 при постановке и сохраняется в payload. Джоба напрямую загружает проверенный мир и недавние посты, выбирает автора из его звёзд. В промпте выбран автор; история передаётся JSON-данными с именем автора, StarId (null для игрока) и isOwn для собственных постов выбранной звезды. Джоба вызывает `IChatClient.GetResponseAsync` и проверяет полный ответ по политике 14+. Mediator и HTTP-контекст ей не нужны. Результат сохраняется отдельным постом без изменений экономики и прогрессии; доступен в существующей ленте и деталях поста.

`RekiTimeTicker` задаёт три retry с интервалами 30/120/600 секунд до сохранения задания. Технические ошибки передаются TickerQ; небезопасный/пустой ответ и удалённый мир завершаются через `TerminateExecutionException` без повторов. ID результирующего поста сохраняется в payload и остаётся одинаковым на всех попытках джобы; проверка существования перед AI и уникальный Mongo `_id` исключают повторную публикацию. Повтор успешного HTTP-действия не ставит новое задание. Задания хранятся в существующей MongoDB. Между бизнес-коммитом и постановкой нет общей транзакции: отказ постановки, возвращённый TickerQ как неуспешный result, логируется, не отменяет действие игрока, но может потерять эту возможность фоновой генерации. `ScheduleAsync` ставит задание без вероятностного гейта; `ScheduleFromFeedAsync` ставит его при random < feed.open_probability. CancellationToken.None через эти методы не передаётся; неожиданные исключения шедулер не перехватывает. MongoPostRepository выполняет обычный InsertPostAsync; ошибки вставки передаются TickerQ. Лента загружается одним GET /feed; GET /posts/mine нужен только экрану канала. Детали поста содержат authorId, флагов разрешений нет. Без backend frontend возвращает пустую ленту. Новых продуктовых событий нет.

### Фоновые задачи TickerQ (#146)

Расписания и история исполнений хранятся в той же MongoDB через `alexjamesbrown.TickerQ.MongoDB`. Задача `ResetGameDayJob` запускается ежедневно в 09:00 МСК (`Europe/Moscow`), массово обновляет только игроков и миры со старым дневным периодом и увеличивает версии документов. Она обнуляет расход `EnergyUsed`, выставляет `Energy` по Free/Plus балансу с активной наградой за зарубу, сбрасывает выполненные желания и дневной прирост отношений звёзд; бонус отдыха следует текущему балансу. При старте задачи обслуживания не запускаются; следующий запуск по расписанию обрабатывает устаревшие периоды. Индексы дневных периодов создаёт миграция 2.3.0 без изменения документов. Чтения игрока и миров больше не нормализуют день и не записывают документы. Повторный запуск для того же периода безопасен. Миграция 2.4.0 читает `IOptions<GameBalance>` через DI и переводит прежний лимит минус расход в неотрицательный остаток `Energy`, сохраняя расход и дневной период. Прежние `DailyBonus` и `ChallengeDailyBonus` удаляются; существующая `Energy` при повторе не пересчитывается. `ChallengeBonusUntilUtc` остаётся сроком повторных начислений, их размер берётся из баланса. Уже использованные инвайты не переигрываются.

Трейсы TickerQ, структурированные технические логи и gauge `reki.players.registered` отправляются через существующий OpenTelemetry/OTLP. Подробнее о настройках — [backend/README.md](../backend/README.md#scheduled-maintenance-tickerq).

## Пользовательский контекст и lifetime обработчиков

Mediator и handlers зарегистрированы singleton. `GameDayPeriod` и `ChallengeLifecycle` также singleton; scoped HTTP-сервисы не внедряются в их конструкторы. Внутри операции handler получает локальный `IRekiContext` через singleton `IRekiContextAccessor.Context`. Сам контекст живёт в scoped DI одного HTTP-запроса и хранит только текущий профиль игрока и словарь его миров.

Конструктор контекста не обращается к БД. `Player` и `Worlds` ленивые; повторные обращения переиспользуют загрузку. Чтение только профиля не загружает миры. Существующий `Reload()` сбрасывает lazy-задачи; потребитель заново получает `Player` и `Worlds`, когда нужен свежий пользовательский снимок. После LLM в треде профиль и миры обновляются через контекст, пост читается отдельно, затем повторяются проверки энергии, безопасности, цели ответа и принадлежности миру. Optimistic concurrency и MongoDB-транзакция остаются границей коммита. При replay сначала читается сохранённый ключ ответа, затем обновляется зависимое пользовательское состояние.

Промежуточные запросы текущего игрока и его миров удалены. `/me` и `/invitation` сохраняют самостоятельные handlers и готовые DTO. Контекст не хранит посты, переписку, события, соперников или приглашения. Ежедневный сброс энергии и подготовка миров выполняются существующими jobs.

Обычные чтения ленты, канала и деталей поста проверяют выбранный мир в `Context.Worlds`. Store читает посты по проверенному `WorldId`, отдельный пост фильтруется одновременно по ID поста и мира. Повторная загрузка мира в Mongo при этих чтениях не нужна. Публичная карточка сохраняет отдельную проверку владельца по явному `PlayerId`; онбординг получает проверенный `TelegramUserId` из controller и работает без существующего профиля. Соперники и фоновые jobs продолжают читать store по явным ID без обязательного HTTP-контекста.

### Корневые комментарии к постам звёзд (#150, 14.10.2026)

Пустая строка недопустима. Для корневого комментария целевая звезда определяется по AuthorId поста и должна принадлежать текущему составу проверенного мира; под постом игрока сервер возвращает 409. StarReplyContext содержит текст поста, пустую ветку и текст игрока; общий StarTurnGenerator возвращает thread_reply именно автора. Для ответа используется существующая цепочка ветки. Модерация, SSE, повтор requestId, проверки версий и TryCommitReplyAsync общие. Перед коммитом цель перечитывается; удаление автора во время генерации не публикует результат. Корневой GameComment игрока и ответ звезды сохраняются вместе с энергией и бонусом. Первые thread.bonus_replies комментариев игрока под постом (включая корневые) дают thread.subscriber_bonus. GET поста и completed возвращают authorId вместо canReply. UI открывает любой сохранённый пост, под постом звезды сразу предлагает корневой комментарий, под своим — выбор реплики звезды. Выбор цели сохраняется в черновике; «К посту» возвращает к корневому комментарию без потери текста. Новых событий аналитики и миграций нет.


## Единая сложность и UUID миров — 2.5.0 (#215)

World.Id — WorldId<Guid>, TemplateId — WorldId?, BSON UUID Standard subtype 4; в JSON UUID в формате D. Difficulty находится на уровне World; API и balance.difficulties используют easy/normal/hard. В BSON стандартный EnumSerializer хранит имена Easy/Normal/Hard. BalanceKey и Interface.Difficulty удалены. Создание/редактирование принимает difficulty и nullable templateId; WorldResponse возвращает доменные WorldId и StarId; TemplateId и IsArchived в ответ не входят. Все существующие доменные ID в HTTP-запросах и ответах (WorldId, PlayerId, PostId, CommentId, StarId, AuthorId, RekiEventId, SessionId, ключи навыков SkillId) передаются напрямую; binding и JSON/OpenAPI используют штатную генерацию Vogen. UUID в JSON имеют формат D; курсор — PostId. AuthorId всегда содержит префикс Player_ или Star_. Некорректные route/query ID, в том числе в публичной карточке, возвращают стандартный 400. Строковые ключи публикаций, повторов, wants, achievements и пока не реализованных челленджей сохраняют тип из действующей модели, без новых обёрток. Нулевой Player.PlayerId AND TemplateId=null определяют шаблон, доступный каталог дополнительно требует IsArchived=false. Создание сохраняет TemplateId из запроса без дополнительного чтения шаблона; редактирование сохраняет происхождение. Отсутствующая или числовая сложность вне easy/normal/hard сводится к normal при создании и редактировании.

Publication не хранит снимок баланса. При подтверждении расчёт и порог допуска хейта используют текущую World.Difficulty и действующий GameBalance. Изменение сложности влияет и на уже начатые незавершённые публикации; старые own после миграции используют normal без legacy-коэффициентов. Проверки безопасности, ресурсов и владения повторяются. Историю и результаты завершённых публикаций при replay не пересчитываем.

Миграция 2.5.0 удаляет старые одноразовые GenerateStarFeedPostJob из ticker_TimeTickers во всех статусах вместо преобразования payload, сохраняя остальные задания и cron-расписания. TickerQ остаётся на 10.4.0; настройка штатного retention отложена до публикации поддерживающей его версии. Миграция 2.5.0 восстанавливает старые шаблоны из SeedWorldTemplates.CreateTemplates, архивирует stage/academy/stream/own и сохраняет активные it/evening/sorcerers/houses. Словари соответствий старых ID и UUID существуют только в памяти одной транзакции. [План, фиксированные UUID и порядок выпуска](migrations/2.5.0-worlds.md).
