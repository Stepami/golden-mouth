# Представления OpenObserve

05.10.2026. Источники: log streams `product` и `backend`, стандартные OTel metrics и traces. В issue #35 поднимается сбор и хранение; автоматическое provision дашбордов и алертов не входит в MVP.

## Конкурсные показатели

| Показатель | Как считать | Источник |
|---|---|---|
| DAU | `count(distinct player_id)` по календарному дню, `activity_kind = real` | `product` |
| Обращения / DAU | число GenAI operations за день / DAU | `gen_ai.client.operation.duration` и `product` |
| Токены | сумма input/output token usage по модели и операции | `gen_ai.client.token.usage` |
| LLM-cost / DAU | `(input_tokens × input_price + output_tokens × output_price) / DAU`; цены хранятся в версии запроса/дашборда, а не в телеметрии | GenAI metrics + прайс модели |
| Ошибки | 5xx и Error/Critical по часу, route и exception type | HTTP metrics + `backend` |
| Нагрузка | RPS, p50/p95/p99 latency, active requests, GC, allocations, exceptions, thread-pool queue | ASP.NET Core + runtime metrics |

Тестовые и отладочные обращения не должны попадать в конкурсный расчёт. Production-события имеют `activity_kind = real`; тесты проекта не экспортируют OTLP.

## Поля продуктового stream

`ProductTelemetry` пишет плоские log attributes: `event_name`, `player_id`, `event_time_unix_ms`, `received_time_unix_ms`, `session_id`, `platform`, `screen`, `previous_screen`, `world`, `age_group`, `experiment_plus_offer` и разрешённые `prop_*`. Тексты постов, сообщений, комментариев, имена, Telegram ID и `initData` не экспортируются.

Для DAU и когорт используется `player_id`, для сессий — `session_id`. Эти поля допустимы в log stream, но не должны становиться labels OTel-метрик.

## Продуктовые представления

1. Онбординг: уникальные игроки по `onboarding_step` и первому `post_publish`; время от `session_start` до `post_result`.
2. Первая сессия: число `post_publish` на сессию, доля `prop_own_words`, `prop_viral` и `prop_flop`, время `screen_leave`.
3. Retention: наличие любого события игрока в D1/D3/D7 относительно первого `player_created` или `session_start`, в разрезах `world` и `age_group`.
4. Лимит и Реки+: первое действие после `limit_reached`, `plus_interest` на показ и разрез `experiment_plus_offer`.
5. Друзья: `invite_sent` → `invite_converted` → первый пост → D1; `challenge_started` и `challenge_finished`.
6. Ошибки: severity, event name, HTTP route/status, screen и безопасный exception type; переход из лога в связанный trace по trace id.

Цели продукта остаются в [analytics.md](analytics.md). OpenObserve заменяет только хранилище и UI аналитики; контракт `POST /events` и `POST /logs` для фронтенда не меняется.

## Панели раннего продукта (11.10.2026)

Воспроизводимый источник: `observability/dashboards/build.py`, `panel-sql/` и собранный `product.json`. Определения заменяют прежний «churn D1».

| Метрика | Определение / ограничение |
|---|---|
| Total observed | Уникальные непустые `player_id`, `activity_kind = real`, за 90 дней. Это наблюдаемые игроки, не число зарегистрированных аккаунтов в MongoDB. После удаления старых логов показатель может уменьшиться. |
| MAU / WAU | Игроки с событием за последние 30 / 7 × 24 часа относительно текущего времени сервера. До накопления истории охват ограничен доступной телеметрией; `telemetry_since_utc` показывает её начало. |
| DAU | Сегодня (неполный день) и вчера по UTC; отдельный график по дням выбранного диапазона. |
| Сегменты | `world`, `age_group`, `platform` разрешаются на уровне игрока из непустых атрибутов за 90 дней. При нескольких разных значениях — `multi-world`, `multi-age-group`, `multi-platform`; без значений — `unknown`. Игрок один раз в каждом измерении; строки разных измерений не суммируются. |
| D1 / D7 | Когорта первого наблюдаемого события за 90 дней; возврат в точный календарный день UTC +1 / +7. Это не доказанная дата регистрации. Знаменатель включает только созревшие когорты: целевой день строго раньше последнего дня доступной телеметрии. Незавершённая когорта имеет 0 eligible и NULL процента. |
| Weekly churn proxy | Среди активных в предыдущие полные 7 UTC-дней — доля неактивных в последние полные 7 UTC-дней. Все игроки и те же сегменты. Требуется начало истории не позже начала предыдущего окна (14 дней); при недостатке истории или нулевой базе процент NULL. Это недельная неактивность, не отмена подписки и не окончательный уход. |
| Активация | Число игроков с `post_publish` / `post_result` среди всех наблюдаемых за 90 дней. Охват событий; не упорядоченная воронка первой сессии. |
| Первое появление | Первое событие внутри выбранного диапазона. Подпись «новые регистрации» некорректна без `player_created` и полного исторического источника. |

Сводка, сегменты, когорты, churn и активация имеют собственный диапазон **90d**, чтобы глобальные 4w или 1d не обрезали MAU и когорты. Тренды и охват событий следуют глобальному диапазону. Явный диапазон конкретной панели в URL имеет приоритет: при его изменении нужно учитывать усечение истории. Сводные окна привязаны к текущему серверному времени, а не к концу исторического диапазона. Отсутствие событий может означать отсутствие активности либо сбой доставки; здоровую доставку проверяют в техническом дашборде.

### На что смотреть сначала

1. D1/D7 с числом созревших игроков, прежде всего без дробления на маленькие сегменты. Сравнение сегментов на нескольких игроках — гипотеза для разговора с игроками, не вывод об эффективности.
2. Публикация → показ результата: проверить потери доставки/ошибки, затем измерять время до **первого** результата в первой сессии. Нынешний охват этих событий не доказывает их порядок.
3. Повторная публикация на другой день — более сильный сигнал ценности, чем число экранных событий или MAU при одном запуске.
4. Проверить полноту `player_created`, `session_start`, `invite_converted`, `plus_shown`: без этих сигналов нельзя честно считать новые регистрации, первую сессию, приглашение → активацию и конверсию оффера.
5. Не смешивать тестовую/служебную активность с продуктовой. Фильтр `real` не гарантирует исключение команды, если её обычные сессии тоже помечены как реальные.

Не добавлять свободный текст и личные данные в события. Для lifetime total потребуется отдельный агрегированный источник из базы аккаунтов; retention по дате регистрации требует надёжного серверного `player_created`.
