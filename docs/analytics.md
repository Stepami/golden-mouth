## Что шлёт фронт

При загрузке приложения фронт анонимно вызывает `POST /sessions` и получает UUID строкой. Бэкенд выдаёт новый GUID без записи в Mongo. Фронт использует этот ID для аналитики и журналов ошибок до перезагрузки страницы; до получения ID события остаются в очереди.

`POST /events`, пачкой раз в 10 секунд и при закрытии через `fetch` с `keepalive: true` (`frontend/src/app/analytics.ts`). Запрос проходит аутентификацию собственным app Bearer:

```json
{ "session": "uuid", "platform": "ios|android|tdesktop|web",
  "experiments": { "plus_offer": "10" },
  "events": [{ "name": "screen_view", "t": 1759500000000, "screen": "02-3_result", "prev": "02-2_live", "props": {} }] }
```

`player` не принимается от клиента как доказательство личности. Бэкенд получает PlayerId из проверенного `sub` собственного JWT и при записи сам добавляет его обезличенный внутренний id. Внешняя авторизация проверяется при выдаче токенов; без действующего app Bearer событие не принимается. Telegram ID и `initData` в аналитику не записываются.

| Событие | Когда | Свойства |
|---|---|---|
| `active_time` | неперекрывающиеся интервалы видимого приложения до 60 секунд без действий; heartbeat 15 секунд, смена экрана, скрытие | ms: целое 1–30000; не считать фоновое время |
| `session_start`, `app_hidden`, `app_visible` | открытие, сворачивание, возврат | platform, ms_on_screen |
| `screen_view`, `screen_leave` | смена экрана | screen, prev, ms (время на экране) |
| `tap` | вкладка, главная / вторая кнопка экрана | id (`tab`, `cta_main`, `cta_second`), to |
| `onboarding_step` | шаги онбординга | step (age / world / channel / world_settings / done), ok, world, address, star |
| `post_publish`, `post_result` | пост и его итог | len, own_words; delta, viral, flop |
| `limit_reached` | упёрся в лимит | |
| `plus_interest`, `plus_bonus_only` | 04-2 | |
| `invite_sent`, `share` | позвать, поделиться | to (chat / story) |
| `event_answered`, `challenge_post` | событие дня, пост в зарубу | kind, own |
| `report`, `crisis_shown` | жалоба, кризис | reason, adult |

## Что пишет бэкенд сам

`player_created` (только при создании минимального профиля после первого входа, до онбординга; `prop_completed=false`, возраст ещё неизвестен), `onboarding_completed` (однократное завершение онбординга; возрастная группа и проверенный источник регистрации), `player_deleted` (после удаления данных и профиля; служебное событие), `world_created` (после сохранения мира: внутренний `world_id`, `template_id` = UUID шаблона (null для мира с нуля), `difficulty` = easy/normal/hard, возраст), `invite_converted`, `post_scored` (три шкалы, quality, дневной индекс расхода энергии в prop_post_index; ответы в треде тоже сдвигают индекс), `level_up`, `card_earned`, `stage_reached`, `hate_wave`, `challenge_started`, `challenge_finished`, `notification_sent`, `notification_opened`, `plus_shown`. Сервер видит то, чего не видит фронт: оценки модели, конверсию приглашений, уведомления.

## Метрики теста

D1 ≥ 40%, D7 ≥ 15%; K (честный: приглашённый дожил до D1) ≥ 0,3; постов за сессию; доля своих слов к 3-му дню; конверсия лимит → приглашение; `plus_interest` на показ 04-2.

## Где хранить и смотреть

| Что | Где хранится | Где смотрим |
|---|---|---|
| События поведения (`POST /events`) | OTel logs, OpenObserve stream `product`; бэкенд добавляет `player_id` и `reki.stream=product` | OpenObserve, представления из [dashboards.md](dashboards.md) |
| Ошибки фронта (`POST /logs`) | OTel logs, OpenObserve stream `backend` | OpenObserve по severity, event, screen, status и path |
| Ошибки бэкенда | Console + OTel logs в stream `backend`, связанные с trace/span | OpenObserve Logs и Traces |
| HTTP, runtime, MongoDB, LLM | Стандартные OTel metrics/traces | OpenObserve Metrics и Traces |

Почему так: один self-hosted OpenObserve принимает все три сигнала OTel и позволяет считать продуктовые показатели SQL-запросами. Отдельный Metabase в MVP дублировал бы хранение, доступы и эксплуатацию. Сторонние сервисы за рубежом не используем: аудитория 14+, 152-ФЗ.

`player_id` — созданный бэкендом обезличенный идентификатор. Он допустим в продуктовых логах во внутренней Compose-сети, но запрещён в metric labels из-за высокой кардинальности. После удаления профиля связь идентификатора с игроком исчезает. Срок хранения stream `product` — 90 дней, `backend` — 30 дней; политику retention настраивает команда в OpenObserve. Доступ только у команды.

## Нельзя собирать

Тексты постов, ответов, лички и описаний мира; ники и имена; Telegram ID и initData в событиях; год рождения, дата рождения и точный возраст (только диапазоны 14-17 / 18-24 / 25-34 / 35-44 / 45+; старый 18+ допускается как legacy); геолокацию.

Каждое клиентское событие после выбора созданного мира передаёт отдельное поле worldId — ID экземпляра, который записывается в AnalyticsEntry и атрибут лога world_id. Сервер проверяет принадлежность всех переданных миров игроку. До создания мира поле отсутствует; ID не подставляется в уже накопленные события. Категория баланса остаётся в props.world для группировки метрик.

## Уточнение аналитики 11.10.2026

Сервер сохраняет optional AgeBand из onboarding: 14-17 / 18-24 / 25-34 / 35-44 / 45+. BirthGroup отдельно остаётся 14-17 / 18+ для безопасности; диапазон обязан ему соответствовать. Клиент передаёт только диапазон, не год рождения. В атрибут age_group записывается AgeBand либо legacy BirthGroup. Старые взрослые профили без диапазона не восстанавливаются задним числом.

После первого успешного входа сервер пишет player_created; после заполнения профиля — onboarding_completed; повторные входы не создают регистрацию. После сохранения мира — world_created; post_scored, level_up и card_earned получают мир из экземпляра мира, а возраст из профиля игрока. Посты на игрока считаются по post_scored, не по попыткам post_publish. Gauge reki.players.registered читает число текущих профилей MongoDB раз в минуту и не содержит ID.

Distinct player_id не доказывают число людей: удаление/пересоздание профиля даёт новый ID. На дашборде общий счётчик Mongo отделён от наблюдаемой аудитории событий. Определения stickiness, среднего времени, распределений публикаций и темпа — в dashboards.md.

## Продуктовый дашборд v2 — #127

Все календарные дни аналитики — `Europe/Moscow` (UTC+3). Это календарные дни, не игровой сброс лимита в 09:00. Сегодняшний день помечается как неполный.

### Авторитетные события и поля

- `post_scored`: только сервер после успешного commit. `prop_id` — непрозрачный ID сохранённого поста, `prop_delta` — подписанный прирост игровых подписчиков. Повтор одной публикации считается по ID один раз. Старые события без этих полей сохраняются, но не дают измеренного прироста. Клиентский `post_result` не суммируется с серверным событием.
- `post_failed`: только сервер после отметки неуспешной генерации. `prop_id` — ID попытки публикации, повтор обработки не увеличивает число ошибок. Не является завершённым постом.
- `player_created`, `onboarding_completed`, `player_deleted`, `world_created`, `level_up`, `card_earned`, `post_scored`, `post_failed` не принимаются из клиентского batch: клиент не может подделать серверный результат для аналитики.
- `registration_source`: `direct` или `referral` в серверном `onboarding_completed`, по проверенному приглашению при заполнении профиля. Исторический `player_created` сохраняет прежний источник; новый вход ещё не определяет реферал. В профиле отдельного поля нет; остальные события не читают приглашение ради аналитики. Дашборд связывает источник с игроком по событиям завершения онбординга и исторической регистрации; у старых данных без измерения — `unknown`.
- Optional `launchSurface` в batch: `telegram-mini-app`, `browser`, `standalone`. Экспортируется как `launch_surface`; отсутствующее/неподдерживаемое значение — `unknown`. Способ запуска — наблюдение клиента, не доказательство идентичности. `platform` остаётся устройством/платформой Telegram. Старые события не классифицируются задним числом по iOS/Android. Сейчас авторизованная игра вне Telegram зависит от отдельного проекта Telegram Login/JWT; отсутствие standalone-событий не означает доказанный ноль пользователей.

До подтверждения созданного при входе профиля фронт буферизует события и логи (до 100 записей в каждой очереди). Отправка начинается после успешного `/me`, включая профиль с onboardingCompleted=false: шаги незавершённого онбординга доступны аналитике.

### Количество аккаунтов и удаление

Задача TickerQ `RefreshRegisteredPlayersJob` раз в минуту напрямую считает профили в MongoDB через `CountDocumentsAsync`. Singleton-джоба хранит последнее измерение и отправляет только gauge `reki.players.registered` (в PromQL — `reki_players_registered`), без перебора игроков, чтения миров или приглашений и без снимков профилей. Карточка «Всего аккаунтов в Mongo» показывает общий счётчик; фильтры продуктовых сегментов к нему не применяются. Отсутствие метрики не означает ноль.

После успешного создания мира, публикации поста, ответа с бонусом сервер пишет `world_audience_updated`: `player_id`, `world_id`, `template_id` (UUID шаблона или null), `difficulty` (easy/normal/hard), `subscriber_total`. Событие служебное (`activity_kind=inventory`) и не принимается с клиента. Дашборд берёт последнее событие по `_timestamp` для каждого мира, затем суммирует состояния по игроку. События не складываются друг с другом; версия мира не передаётся. Подписчики старых миров без такого события неизвестны до следующего изменения аудитории; `audience_known_accounts` показывает число профилей с доставленным состоянием. Покрытие внутри старого профиля может быть неполным, если обновились ещё не все его миры. Нет дополнительных чтений для построения события и нет Telegram ID или пользовательских текстов.

После успешной очистки связанных данных и удаления профиля сервер пишет `player_deleted` с `player_id` и `activity_kind=lifecycle`. Событие не является посещением, не влияет на DAU и не принимается от клиента. Все SQL-панели исключают ID с доставленным событием удаления из наблюдаемой аудитории, исторической активности и когорт. Повторная доставка удаления и поздние игровые события этого ID не возвращают его в расчёт; повторная регистрация создаёт новый ID. Старые удаления без такого события неизвестны: миграции или восстановления истории нет. SQL использует доступную историю событий за 90 дней, поэтому число наблюдаемых профилей может отличаться от общего счётчика Mongo. Прежние события снимков больше не используются.

### Семантика метрик

Воронка разделяет создание профиля (`player_created`) и завершение онбординга (`onboarding_completed`). Строка «Онбординг · новые регистрации» считает завершения только среди игроков с `player_created.prop_completed=false`: `users` — завершившие, `base` — новые регистрации, `conversion_pct` — их доля. Старые события player_created уже означали заполненный профиль и не подставляются в эту базу. Этапы ≥1/3/10 серверных постов сохраняют общую выбранную базу регистраций; знаменатель каждой строки показан явно. Отсутствие новых регистраций даёт NULL конверсии, а не ноль. Исторические ID без события регистрации показываются отдельно, не выдаются за регистрации. Retention D1/D3/D7 — точный календарный день после регистрации; в знаменатель включаются только завершённые дни. Источник исторического сегмента берётся из серверной регистрации; мир — из последних состояний миров, затем из известных игровых событий. Значение unknown не заменяет известный мир. Для старых профилей используется известный атрибут истории, с ограничениями.

Stickiness — сумма активных профиле-дней / число полных календарных дней / MAU за тот же интервал. Максимум 30 дней; первый неполный день всей истории исключён. Нулевые календарные дни учитываются в среднем. Показано фактическое покрытие: короткая история даёт предварительную оценку. Это история ID без профилей с доставленным событием удаления; не число уникальных людей.

При смене мира группировка результата публикации использует мир события поста. Глобальный фильтр «Мир» для профиля использует последние доставленные состояния миров, затем известный мир игровых событий; публикации группируются по миру события поста. Один профиль с разными способами запуска относится к `multi`; таблица устройств показывает охват по комбинациям, её строки нельзя складывать как уникальных людей.

Активное время — существующие foreground-чанки после взаимодействия, не время открытого окна. Среднее только по измеренным активным профиле-дням; покрытие показывается рядом. Исторический прирост до добавления серверного delta не восстанавливается из пользовательских текстов или демо: видны число всех постов и число постов с измеренным delta.

Для старой истории есть явный переключатель базы воронки/retention: «Первое наблюдение». Он использует первое подтверждённое посещение, исключая heartbeat и уведомления; это приближение, а не доказательство даты регистрации. По умолчанию выбрана подтверждённая регистрация. Переключатель не меняет определение текущего аккаунта, постов или активного дня.
## Техническая стоимость LLM

Существующие chat traces дополняются полем `gen_ai.usage.cost` с валютой `RUB`; это техническая телеметрия, не новое продуктовое событие. Для streaming `LlmSpendChatClient` передаёт `stream_options.include_usage = true` и читает `usage.cost` из чанка через SDK JsonPatch, пока GenAI-спан ещё открыт. Стоимость появится только если администратор шлюза включил `litellm_settings.include_cost_in_streaming_usage = true`; это не параметр клиентского запроса. Для обычного ответа `LlmSpendPolicy` читает заголовки стоимости. Обе обёртки используют `LlmSpendWriter`. Дополнительных запросов журнала и ожидания стоимости нет; если поле отсутствует, приложение не записывает стоимость. Начальный расход без детализации зарегистрирован отдельно в log stream `llm_cost_ledger`. В метрики не добавляются player/post/request IDs, ключи или тексты. Методика описана в [dashboards.md](dashboards.md#стоимость-шлюза).

## Загрузка изображений игры (#156)

`image_loaded`: фиксированный `asset` (`welcome_portrait`, `cover_evening`, `cover_sorcerers`, `cover_houses`, `cover_it`), `duration_ms`, `transfer_bytes`, `decoded_bytes` из Resource Timing. `image_failed`: тот же фиксированный `asset`. Без URL, текста или фотографий игроков. Нулевой transfer может означать кеш; отсутствующий Resource Timing не доказывает мгновенную загрузку. События идут через существующую очередь после появления игрока: неавторизованные посетители первого экрана не входят в эти агрегаты. Исторических замеров до этого изменения нет.

Для проверки задержек: в OpenObserve stream product фильтровать name=image_loaded, группировать по props.asset, считать p50/p95 duration_ms; image_failed проверять отдельно. Серверные API traces не измеряют загрузку статических файлов фронта.

### Порядок загрузки обложек (#158)

Обложки каталога, обзора и начала истории отображает общий `WorldCover`: браузер выбирает 640/960 px через srcset/sizes по ширине и плотности экрана. Первая карточка имеет high priority и начинает запрос параллельно загрузке шаблонов. Остальные карточки начинают загрузку через IntersectionObserver с небольшим запасом до видимой области; это предотвращает конкуренцию дальних карточек за соединение. Размер места для обложки постоянный, до декодирования видна спокойная подложка; появление учитывает reduced-motion. Hash URL сохраняет immutable cache между экранами. Оригиналы остаются источниками для будущих размеров.


С 2.5.0 (#215) world_id — UUID экземпляра в формате D; template_id обозначает происхождение, difficulty — механическую сложность. С #245 post_scored и связанные награды записываются после успешного commit создания поста; difficulty берётся для расчёта в POST. Генерация первого комментария идёт отдельно и не отправляет post_scored повторно. Существующие игровые оценки brave/humor/topic и quality сохраняются в post_scored; тексты, векторы и сырые выходы классификаторов токсичности/эмоций не передаются. Старые обозначения миров больше не отправляются как world/BalanceKey. Исторические внешние события не переписываются. При сравнении периодов нормализовать строковые GUID world_id (с дефисами и без) и учитывать, что ранние составные ID заменены детерминированными UUID по алгоритму миграции; исходные старые события сохраняются.
