# Дизайн-система и проверка интерфейса «Рек»

Проверка обязательна при правках UI без отдельного напоминания пользователя. Пути ниже даны от корня текущего worktree.

## Перед изменением

1. Прочитать `frontend/AGENTS.md` и актуальный контракт `docs/redesign/DESIGN-SYSTEM.md`. Использовать дизайн-систему Романа с последующими утверждёнными изменениями владельца продукта; не фиксировать в навыке копии палитры, размеров или механик, которые могут устареть.
2. Проверить реализацию: `frontend/src/v7/theme.css`, `night.css`, `design-tokens.json`, `ui/index.tsx` и `ui/ui.css`. Для затронутого экрана посмотреть его компоненты и подключённые стили. `frontend/public/assets/design-tokens.json` — публичная копия токенов; при изменении токенов сохранить её согласованность с исходником.
3. Найти подходящий общий компонент и его варианты до создания нового. Использовать общие компоненты, токены, шрифты и утверждённые изображения. Новый вариант добавлять в общий компонент, если это переиспользуемое поведение; не создавать локальный двойник кнопки, поля или диалога ради обхода системы. Новый компонент нужен, когда существующие не покрывают задачу.

Правила игры задают `docs/game-flow.md` и `docs/config/balance.json`. Галереи и старые макеты не разрешают возвращать исключённые механики. Если контракт и реализация расходятся в затронутом месте, обозначить расхождение и проверить актуальное утверждённое решение; не выдавать произвольное оформление за эталон. Если источников нет в текущей ветке, сообщить, что соответствие текущей системе не проверено, а не подменять её старой темой.

## Во время реализации

- Проверить типографику, семантические цвета, ритм отступов, размеры действий, иконки и изображения по текущему контракту. Частный CSS должен дополнять систему, а не переопределять её случайными значениями.
- Для затронутых компонентов проверить применимые состояния: обычное, выбранное, disabled, busy, focus, ошибка, пустые и длинные данные. Сохранять доступные подписи, клавиатурное управление и reduced motion.
- Изменённый общий компонент проверить и на использующих его экранах. Если добавлен переиспользуемый вариант или состояние, добавить пример в действующую галерею компонентов, чтобы его можно было проверить повторно.
- Системные тексты писать без рода. Ошибки API, неизвестные значения и ожидание не превращать в фиктивный успех.

## Визуальная проверка

1. Запустить именно изменённый worktree и отметить проверяемый коммит или наличие локальных правок. Для изолированной проверки использовать `frontend/DESIGN-PREVIEW.md`: из `frontend/` выполнить `npm run design`, открыть `/design.html`, пройти затронутый флоу и раздел «Компоненты». Это те же React-компоненты с демонстрационными данными; просмотр не доказывает работу API. На dev-сборке приложения также есть `/?visual-review`; исторический `/#system` не является единственным эталоном.
2. Снять и просмотреть скриншоты изменённых экранов и применимых состояний на ширинах 320, 390 и 430 px. Проверить переносы и увеличение текста до 200%, области нажатия, safe area, фокус и перекрытия фиксированными панелями; для полей — доступность действий при открытой клавиатуре. Проверить целые силуэты изображений и отсутствие горизонтального переполнения, кроме предусмотренных каруселей.
3. Сравнить с актуальным контрактом и утверждённым образцом затронутой поверхности: композицию, типографику, компоненты, состояния и поведение. Не считать визуально проверенным экран, который не был открыт и просмотрен. Не создавать новый эталон из результата собственной правки без утверждённого решения.
4. Если изменён пользовательский флоу обычного приложения, пройти затронутый сценарий с реальным backend в разрешённой среде. Дизайн-превью, мокап и успешная сборка эту проверку не заменяют. Если среда или браузер недоступны, выполнить доступную часть и явно указать оставшуюся проверку; не утверждать полное соответствие.

Старый `frontend/scripts/screens.sh` снимает галерею `?screen=` для `docs/screens/` в 390×844. Использовать его только при работе с соответствующим старым экраном. Старые изображения не являются эталоном текущей системы; размер PNG не доказывает, что экран загрузился правильно.

## Завершение

- Выполнить проверки репозитория: `.github/scripts/check-secrets.sh --all`; при изменениях фронта — `cd frontend && npx tsc -b && npm run build`. Если изменено дизайн-превью, также `npm run design:build`.
- В результате и PR кратко указать использованные общие компоненты/токены, просмотренные экраны и состояния, ширины, расположение скриншотов и оставшиеся ограничения. Различать визуальное соответствие, проверку поведения с API и успешную сборку.

Этот навык не разрешает новые issues, мерж, деплой или изменение механик за пределами согласованной задачи.
