# Нагрузочный тест чтений

k6 запускается одноразовым контейнером в существующем Compose-проекте `reki` и обращается к `http://backend:8080` по внутренней сети. При обычном `docker compose up` сервис `k6` не запускается: он находится в профиле `load-test`. Явный `docker compose run k6` активирует его автоматически. Установка k6 на хост не нужна; версия Docker image закреплена.

Сценарий проверяет API, а не полную загрузку экранов:

| Сценарий | Запрос | По умолчанию |
|---|---|---|
| `profile` | `GET /me` | 10 RPS |
| `channel` | `GET /posts/mine?worldId=…` | 10 RPS |
| `post` | `GET /posts/{postId}?worldId=…` | 10 RPS |
| `feed` | `GET /feed?worldId=…` | 10 RPS |

Суммарно — 40 RPS. В каждой итерации ровно один GET, без пауз и повторных попыток. `constant-arrival-rate` сохраняет заданную частоту независимо от времени ответа; для каждого сценария выделяется минимум 20 VU, при стандартных 10 RPS — 40 VU. Это запас относительно HTTP timeout 3 секунды. Если VU не хватает, тест фиксирует `dropped_iterations` и завершается с ошибкой.

## Подготовка

1. Запусти Docker и обычный стек проекта по инструкции в корневом README. Все обязательные переменные Compose должны оставаться доступны через окружение или локальный `.env`, который не хранится в Git. Нагрузочный тест не создаёт и не перезапускает backend.
2. Используй отдельный тестовый стенд с ресурсами и конфигурацией, близкими к production. k6 на том же хосте конкурирует с backend за ресурсы; результаты такого прогона зависят и от генератора.
3. В приложении заверши онбординг тестового аккаунта, создай мир и хотя бы один собственный пост; выбери пост с сохранёнными комментариями. В канале и ленте должны быть данные.
4. В DevTools → Network → Fetch/XHR выбери успешный запрос API. Из заголовка `Authorization` скопируй только часть после `TMiniApp ` — сырой `initData`, не декодируя и не меняя его. Это работает и с локальным Telegram emulator во frontend.
5. Открой канал: `worldId` возьми из query string `GET /posts/mine?worldId=…` (или `id` из ответа `GET /worlds`). Открой пост с комментариями: его ID возьми из пути `GET /posts/{postId}?worldId=…` (или `postId` из ответа канала).

Авторизация, мир и пост должны относиться к одному аккаунту и тому backend, который сейчас запущен в Compose. `initData` — секрет авторизации: не добавляй его в скрипт, Git, issue или отчёт. Backend проверяет подпись и срок действия; при 401 обнови значение через приложение. Прогон с массовыми 401 не оценивает нужные операции.

Перед нагрузкой `setup()` последовательно проверяет четыре ручки: HTTP 200, JSON ожидаемой формы, непустые канал/ленту и выбранный пост с комментариями. При ошибке нагрузка не начинается. Предварительные запросы помечены `endpoint=preflight` и не учитываются в порогах отдельных ручек.

## Запуск из корня репозитория

PowerShell:

```powershell
$env:INIT_DATA = Read-Host 'Raw initData, без TMiniApp'
$env:WORLD_ID = Read-Host 'ID тестового мира'
$env:POST_ID = Read-Host 'ID поста с комментариями'

# Короткая проверка: по 1 RPS, 30 секунд.
$env:RATE = '1'
$env:DURATION = '30s'
docker compose run --rm --no-deps -T k6
$LASTEXITCODE

# Основной прогон: по 10 RPS, 10 минут.
$env:RATE = '10'
$env:DURATION = '10m'
docker compose run --rm --no-deps -T k6
$LASTEXITCODE
```

В bash передай те же переменные через `export`; код завершения доступен в `$?`. `RATE` — положительное целое число RPS **на каждую ручку**. `DURATION` — положительное целое число с суффиксом `s`, `m` или `h`. Значения по умолчанию: `10` и `10m`. Для проверки стабильности после успешного основного прогона можно повторить его с `DURATION=30m`.

Если стек запускается с явными `-f`, `--env-file` или другим `-p`, используй тот же набор аргументов перед `run`, чтобы попасть в тот же проект и сеть. Например, для production-конфигурации: `docker compose -f compose.yml -f compose.production.yml run --rm --no-deps -T k6` (с теми же переменными окружения, что у работающего стека).

Контейнер обращается прямо к backend: этот прогон не измеряет внешний HTTPS, gateway или frontend proxy. Он не требует публикации дополнительных портов.

## Результаты и критерии

В конце выводится таблица по ручкам: число запросов, p95, p99, процент HTTP/network failures, процент HTTP 200 и пропущенные итерации. Полная агрегированная сводка сохраняется в `load-tests/results/summary.json`. Каждый запуск перезаписывает файл: скопируй нужный отчёт перед следующим прогоном. Отчёты исключены из Git. Скрипт не печатает заголовки авторизации, тела ответов или идентификаторы аккаунта; URL не используются как метки метрик. Перед передачей отчётов всё равно проверь содержимое.

На Linux каталог `load-tests/results` должен быть доступен на запись пользователю контейнера (UID 1000). Если UID хоста другой, можно передать `--user "$(id -u):$(id -g)"` в `docker compose run`.

Начальные пороги теста, а не утверждённый продуктовый SLA:

| Метрика по каждой ручке | Условие |
|---|---|
| `http_reqs` | Не меньше `RATE × длительность в секундах` |
| `http_req_duration` | p95 < 500 мс, p99 < 1000 мс |
| `http_req_failed` | < 1% |
| `checks` (HTTP 200) | > 99% |
| `dropped_iterations` по сценарию | 0 |

За 10 минут на 10 RPS ожидается 6000 запросов на ручку, 24000 суммарно, плюс четыре предварительных запроса. Общая средняя RPS может быть немного ниже 40 из-за предварительной проверки и завершения последних запросов: ориентируйся также на числа по ручкам. p95 — время, в которое уложились 95% запросов; среднее не заменяет перцентили.

Код завершения 0 означает успешное выполнение и прохождение порогов. Ненулевой код бывает также при ошибке подготовки, авторизации, Docker или записи отчёта: проверь весь вывод, наличие `Preflight passed`, выполнение всех сценариев и отсутствие interrupted iterations. Отсутствующая метрика (`n/a`) или незавершённый прогон не доказывают прохождение теста.

## Фоновая генерация ленты

Тест сохраняет поведение приложения. По `docs/config/balance.json` (`feed.open_probability`) чтение ленты может поставить задачу генерации поста через LLM. При текущей вероятности 0.25 и 10 RPS это в среднем 150 задач в минуту, 1500 за 10 минут, плюс возможные повторы. Предварительная проверка ленты также может поставить задачу. Это реальные обращения к настроенному провайдеру и записи в тестовую MongoDB; прогон не очищает созданные данные.

В OpenObserve и телеметрии работающего стенда следи за CPU, памятью, GC, задержками MongoDB, ошибками и длительностью LLM, количеством ожидающих задач и временем ожидания. Если необходимых метрик очереди нет, оцени её отдельно по состоянию TickerQ: HTTP-отчёт её не измеряет. Быстрый GET при постоянно растущей очереди не доказывает устойчивость всего сервиса. Прогон с отключённой генерацией, если отдельно подготовлен такой стенд, доказывает только производительность чтений; этот сценарий ничего не отключает и не меняет баланс.

Тест одного аккаунта проверяет повторные чтения одних данных. Для вывода о множестве игроков нужен отдельный прогон с пулом аккаунтов, миров и постов разного размера. Зафиксируй конфигурацию стенда, объём данных, режим генерации и длительность вместе с результатом.

Документация: [k6 constant-arrival-rate](https://grafana.com/docs/k6/latest/using-k6/scenarios/executors/constant-arrival-rate/), [Compose profiles](https://docs.docker.com/compose/how-tos/profiles/).
