# Основной чат и подагенты «Рек»

Основной агент отвечает перед пользователем за цель, границы, решения, интеграцию и проверенный финиш. Пользователь не должен переносить поручения и результаты между исполнителями. При расхождении с общими навыками приоритет имеют проектные AGENTS.md, включая правила о тестах. Применяй минимальность ponytail; этот навык не расширяет разрешения на issues, мерж, деплой или общую БД.

## Выбрать объём делегирования

- Небольшую понятную правку выполняй самостоятельно. Не создавай исполнителя только ради формального разделения ролей.
- Для существенной связной реализации обычно достаточно одного исполнителя и приёмки основным агентом. Независимую проверку добавляй при конкретных рисках: авторизация, данные, сложный контракт или повторные регрессии.
- Независимые части можно поручить параллельно; обычно достаточно 1–2 подагентов одновременно. Перед запуском проверь зависимости и владельцев файлов и общих ресурсов. Подагенты не делегируют дальше без согласованной с родителем необходимости.
- Для узкого read-only поиска или проверки по явным критериям предпочитай доступную gpt-6-luna с reasoning_effort=high. Для реализации по умолчанию наследуй модель родителя; более сильную модель или повышенное усилие выбирай при обоснованной сложности. Используй только доступные настройки, без переключения провайдера или сетевого маршрута. При отсутствии подходящего дешёвого варианта выполни работу основной моделью.
- По умолчанию передавай краткое задание с fork_turns=none. Наследование всей переписки оправдывай необходимым контекстом: оно увеличивает объём работы и само по себе не даёт экономии.

## Дать исполнителю достаточное задание

Передай цель и ожидаемое поведение, ограничения, актуальный SHA и источники решений, разрешённые файлы/ресурсы, нужные проверки и критерии завершения. Укажи разрешённые действия и границы записи. Достаточно короткого текста со ссылками на нужные файлы; не копируй все логи и историю чата.

У каждой ветки, рабочей копии и общего ресурса — один владелец записи. Общие ресурсы включают DEV, запуск тяжёлой проверки и внешний дашборд, даже если код находится в разных worktree. Несколько независимых реализаций веди в отдельных worktree; интеграцией и общей выкладкой управляет основной агент. Перед передачей существующей работы сохрани checkpoint и подтверди прекращение записи прежним владельцем.

В нативной команде основной агент явно выдаёт области записи и назначает единственного интегратора общего ресурса; остальные исполнители не делают общий sync или выкладку. При неясном или конфликтующем владении останови запись в спорный ресурс, продолжай доступную независимую работу и сообщи точную блокировку. Новый механизм блокировок без необходимости не создавай.

Сборки и ресурсоёмкие проверки выполняются только на Mini. Проверяй фактический хост; при недоступности Mini сообщи блокировку. Не переключай общий DEV и не запускай несколько тяжёлых проверок одного результата без необходимости. Перед Docker-сборкой проверь свободное место; после неё убери ненужный build cache и свои временные ресурсы, сохранив данные и чужую работу.

## Принять и довести результат

Исполнитель возвращает кратко: что изменено, commit/SHA, результаты нужных проверок и оставшиеся ограничения. Основной агент читает diff, сверяет критерии задачи и проверяемые свидетельства на этом SHA. Одного утверждения «готово» недостаточно; число согласных агентов не заменяет проверки.

Принимай минимальное достаточное решение: сначала существующие API, компоненты и правила проекта. Проверки выбирай по риску и требованиям репозитория. Уже успешные проверки повторяй при изменениях, сбоях или нерешённых вопросах. При повторении одной причины сбоя исправляй подход, окружение или процесс вместо слепого повтора.

Основной агент отвечает за обновление PR/согласованной issue и разрешённый выпуск. Различай готовый код, проверки, одобрение, мерж, деплой и приёмку живой версии. Внутренняя приёмка не заменяет обязательное code owner review и отдельное разрешение на выпуск. Ожидание человека обозначай как ожидание с понятным следующим владельцем; не обещай фонового наблюдения без проверенного механизма доставки.

## Когда нужны отдельные пользовательские чаты

- Независимые задачи с разными владельцами и без конфликтующей записи в файлы, контракт или общий ресурс.
- Отдельное исследование или альтернативная оценка без записи в реализацию; решения передаются основному владельцу задачи.
- Новый этап после завершения либо явной передачи предыдущего: краткий checkpoint с решениями, SHA, проверками и остатком. Одну задачу не продолжают два основных чата одновременно.

Один основной чат — точка общения по связанной задаче, а не требование бесконечно хранить весь проект в одной переписке. Новые пользовательские чаты создавай только по прямому запросу; технические подзадачи веди нативными подагентами. Уже работающих отдельных CLI-исполнителей не заменяй автоматически: для них используй codex-session-coordinator и подтверждённую передачу владения.
