# v7: четыре сюжетных мира

Состояние на 03.11.2026. Продолжение frontend #205 / PR229. Это подключение авторской завязки к существующей игре; серверного сюжетного исполнителя ещё нет.

## Пользовательский маршрут

Каталог → Вечерело → Начать игру → «Твой профиль в мире» → включить «Улица на чужом снимке» → выбрать одного из трёх персонажей или своего → создать отдельный мир → лента → «Открыть первый день» → тема → обычный редактор → публикация → настоящие ответы в обсуждении.

Выбор готового героя исключает его из NPC и добавляет авторский четвёртый слот. Во всех четырёх вариантах остаются игрок и три собеседника. Собственный герой сохраняет введённые имя, канал и роль. Сохраняются ограничения безопасности загруженного шаблона и его настройка драмы. Старые экземпляры и остальные шаблоны не переписываются.

Первый день содержит три авторские темы и критерии, но не галочки выполнения. Нет фиктивных ответов, прогресса, наград или автоматического открытия второго дня. Публикация и ответ используют существующую энергию и обычные серверные эффекты. Сюжетный QuestId не передаётся как WantId. Подсказка не заменяет текст игрока и не перезаписывает черновик.

Связь нового экземпляра с pack/version/campaign сохраняется на этом устройстве в пространстве аккаунта и UUID мира. При возобновлении проверяются серверные описание, контекст и состав; отсутствующая/устаревшая связь или изменённый состав возвращают обычный UI. Перенос этой связи между устройствами требует backend-контракта. Сбой локального сохранения показывается пользователю.

## Контент и происхождение

`frontend/src/v7/story/worlds.json` — выборка из подготовленного `reki-four-worlds-dev-pack-2026-11-03`: метаданные пакета, четыре роли «Вечерело», цели и первые три темы каждой роли, настройки новых миров. Подготовленные успешные реплики, XP и награды исключены. Реальный UUID шаблона сохранён. Никакие дополнительные NPC не выдаются за серверный каталог.

### Отдельные разрывы входа, уже существующие до пилота

- Выход возвращает старт frontend; настоящую серверную сессию не завершает. Нужны согласованные семантика выхода и отзыв сессии с учётом Telegram.
- Возраст сохраняется существующим onboarding как AgeBand при первой регистрации. Минимум14 сохранён из действующего контракта, новое решение о пороге не принято.
- Согласие сейчас локальное. Для подтверждаемого согласия нужны версия документа, момент принятия, субъект и серверное сохранение/чтение; дизайн checkbox не заменяет такой контракт.
- Интересы и ранжирование локальны. Для синхронизации между устройствами нужны настройки профиля; сегодняшний порядок — редакционные веса, не серверная рекомендация.
- Градус драмы на входе готового мира скрыт; используется настройка шаблона. Отдельный экран настроения — продуктовый вопрос, не недостающий сюжетный метод.

## Панель серии и ресурсов

В ленте добавлены настоящая серия из `Player.streak.days`, семь серверных отметок и окно наград действующего game-flow (3/7/14/30). Это не сюжетный прогресс. Текущий mapper backend строит `week` как первые min(7, days) отметок, поэтому они не подписаны календарными днями и по ним не вычисляется «сегодня». Для полного календаря нужны даты активности, today/paused и серверные статусы полученных наград; общий `nextReward` сейчас содержит шаблонный текст.

Номер дня сюжета показывается только для явно подключённого пилота первого дня; для обычного мира клиент не выдумывает номер дня.

Кристаллы имеют подсказку на hover/keyboard focus; на телефоне нажатие открывает окно обмена на энергию и усиление сюжетного XP. Бустеры имеют отдельную точку входа. Баланс/инвентарь не подменяются нулём; операции отключены с «Скоро». Курсы и проценты из предлагаемой новой механики не выдаются за действующий баланс.

Дополнения к API gaps: чтение реального баланса кристаллов и инвентаря; серверный каталог доступных обменов с ценой/эффектом/версией; атомарные идемпотентные обмен и резервирование/применение бустера к конкретному действию. Проверять владение, остаток, истечение и policyVersion; повтор или отказ модерации не должен повторно списывать предмет. Это предложения контрактов, маршруты ещё не существуют. Backend не менялся.

## XP в профиле персонажа

По уточнению пользователя03.11: числитель — весь накопленный XP за игру этим персонажем; знаменатель — остаток, доступный для улучшения навыков. Траты уменьшают только знаменатель. Это две разные величины, не прогресс уровня и не суммарный балл из100.

Текущий API возвращает только skill.level/progress. Из них нельзя восстановить точный пожизненный XP или выделить кошелёк. Поэтому в основном профиле XP пока «— / —» и настоящие игровые навыки; кнопка «Открыть пробу распределения XP» запускает явно помеченную локальную пробу. Сумма36 — пример10+12+14 из предложенной механики, не награда за прошедший сюжетный день. Пробные уровни1–100 не заменяют серверные1–10. Стоимость +1:2+.08×(текущий уровень−1)XP, по подготовленному mechanics.json. Применение подтверждается, отмена не тратит XP, исходный total не уменьшается. Остаток и пробные уровни сохраняются только на этом устройстве, отдельно по аккаунту и экземпляру персонажа. Публикации не начисляют в пробу фиктивный XP.

Необходимый API: per-character lifetimeXP, spendableXP, pendingXP, уровни новой системы, maxLevel, таблица цен и policy/stateVersion; атомарное идемпотентное применение распределения с requestId и ожидаемой версией. Сервер проверяет цену, остаток, принадлежность персонажа и лимиты, возвращает полный новый снимок кошелька/навыков. UI не вычисляет настоящий остаток из старых шкал. Перенос старого прогресса и момент разблокировки pendingXP требуют согласованного правила; frontend-проба это решение не принимает.

Проверка XP-профиля: Safari320px — общий/доступный36/36; выбор+1 в двух навыках требует4XP; после применения36/32, уровни2/2/1. Повторное применение без выбора disabled. Четыре теста проверяют общий кошелёк, растущую стоимость, потолок100, недостаток средств и повреждённое локальное состояние. Предусмотрен возврат к настоящим игровым навыкам без изменения сервера.

## Цель, первый пост и состояния ленты

По скриншотам пользователя03.11 цель персонажа и развитие навыков разделены на две смысловые карточки. Во второй: назначение Смелости/Юмора/В тему и связь высокого навыка с более острыми квестами. Усложнение следующих сюжетных этапов отмечено как будущее, не как действующий серверный зачёт.

Новый экземпляр после создания открывает цели, затем первый редактор. В пилоте первый пост получает авторскую редактируемую заготовку из соответствующего ролевого варианта. Пустой текст не отправляется. Существующий черновик или незавершённая отправка не заменяются заготовкой. Неизменённая заготовка передаёт ownWords=false; редактирование — true. Прочие миры сохраняют свой настоящий firstPrompt как подсказку без выдуманного авторского сценария.

Нажатие «Опубликовать» переводит в ленту. До подтверждения видны состояние «Готовим отклики» / «Проверяем публикацию» и текст отправки, но не утверждение успешной публикации. Неизвестный исход проверяется по прежнему publicationId, не новым POST; после reload сохранённый незавершённый запрос доступен для проверки. Подтверждённый отказ оставляет редактируемый черновик.

После настоящего result видны краткая карточка, аудитория, снимки прогресса навыков до/после обновления персонажа, «Все изменения» и переход к комментариям. Числа из response, а не из макета. Это текущие уровни/progress, не новый XP-кошелёк. Последний подтверждённый результат сохраняется локально отдельно по аккаунту и миру; уведомление можно закрыть, карточка остаётся. В деталях используются whys/ribbons/views API; несуществующие изменения отношений не придумываются.

QA Safari: обе смысловые карточки и заготовка, отправка→ожидание в ленте, настоящее подтверждение +43 подписчика, энергия9→8; прогресс навыков15→18%,70→74%,42→67% (округлённые снимки), раскрытие207просмотров и переход к посту с ответом Изабеллы. Созданных новых миров в этом проходе нет, отправлен один тестовый пост в прежнем QA-мире. Мобильная поверхность430px проверена в обычном Safari; responsive-инспектор Safari на320px потребовал переключения режима, это не доказательство ошибки React.

### Диагностика отказа генерации 03.11, 21:35 МСК

DEV-лог подтверждает: generation завершилась `InvalidOperationException: The model returned unknown or missing tool arguments`, `StarToolCallParser.ParseReaction → EnsureExactKeys`. Для `react` ожидается ровно поле `emoji`; фактический ответ модели не соответствовал набору аргументов. По текущему FailureOf это `technical_failure`, а не `content_rejected`. Не установлено, какое именно поле лишнее/пропущено; текст игрока повторно не отправлялся.

Исправлена классификация frontend-сообщения: технический сбой, небезопасная сгенерированная реакция и отклонение пользовательского содержания теперь различаются по failure.code. Раньше любое присутствие failure ошибочно объявлялось непройденной проверкой содержания. Это исправление сообщения, не устранение серверной причины. Для backend нужна отдельная проверка соответствия tool schema/stream assembly/LLM ответа строгому парсеру; не ослаблять safety-валидацию ради принятия неизвестных полей. Новая issue и backend-изменения не создавались.

## Отдельная карточка Хогвартса

По прямому уточнению пользователя «Спасти Хогвартс» вынесен в отдельную активную карточку каталога рядом с обычной Школой. Карточка сразу выбирает сюжетный вариант; после intro открываются Гарри/Гермиона/Рон/свой герой без дополнительного checkbox. У обычной Школы остаются Гоша/Георгина/Роман, переключатель Хогвартса оттуда убран. Сохранённые связанные экземпляры сценария отображаются с названием «Спасти Хогвартс».
