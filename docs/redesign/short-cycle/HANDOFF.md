# Передача для реализации и вопросы

Редакторское предложение по #205 от 06.11.2026. [Сценарии](WORLDS.md) не утверждают серверную готовность. Новых issues, контрактов API и миграций этот пакет не вводит.

## Роме: один образец, затем четыре адаптации

Предлагаемый первый образец — IT: его завязка ближе всего к существующему общему пресету, нет проблемы подмены школьного AU. Выбор образца остаётся за владельцем продукта и Ромой.

1. Онбординг мира: одна завязка, роль собственного персонажа, главная цель. Затем назначенный системой первый квест с понятным вопросом и источником исходных фактов.
2. В ленте/редакторе оставить текущий квест и возможность поста/комментария. Примеры — помощь начать, не обязательный дословный ответ. Не добавлять селектор «какой квест закрыть», счётчик «ход 1 из 3» или карту дней.
3. После действия показать реакцию и два независимых результата: что изменилось в навыках и что выяснилось по квесту. Например: «Условие среды уточнено. Ещё нужно учесть стоимость и исправления». Если действие сохранено, а оценка идёт — не объявлять отказ/закрытие преждевременно.
4. После завершения текущего квеста показать короткий итог и назначенный сервером следующий шаг. Главная цель остаётся той же. Не прибавлять локально кристаллы, подписчиков или навыки.
5. Сохранить автоматические серверные навыки, энергию/кристаллы и ежедневную серию; убрать XP, ручные кнопки, XP-бустеры и карту. Во время ожидания API использовать явно обозначенные иллюстративные состояния вне реальной экономики.

Короткие исходные тексты и реакции для четырёх адаптаций находятся в WORLDS. Школьный сценарий требует отдельной корректной привязки NPC до показа как действительного мира. Чужие существующие прохождения не переписывать новым онбордингом.

## Степану: смысловая модель, без навязывания DTO

Для квеста нужны сценарная версия, мир/персонаж игрока, исходные доступные факты, текущие подтверждённые условия и критерий завершения. Конкретные поля/хранение/API определяет существующая архитектура backend.

В каждый квест входят несколько условий из WORLDS. Условия могут подтверждаться в разных действиях; один полный ответ тоже допустим. Порядок из примера — демонстрация, не жёсткая линейная последовательность. Система должна учитывать предыдущее подтверждённое содержание, а не требовать каждый раз переписать весь план.

| Вход | Как трактовать |
|---|---|
| Собственный сохранённый пост/комментарий | Кандидат на оценку; сохранение само по себе не подтверждает смысл и не закрывает квест |
| Игрок написал «NPC согласился» | Не является согласием NPC |
| NPC подтвердил только одну часть | Не расширять это на весь проект, дом, школу или гарантированный результат |
| NPC отказал | Сохранять отказ и границы; использовать предусмотренный альтернативный путь, не переписывать согласие |
| Действие проявило навык, но не условие квеста | Оценка навыка независима; квест остаётся текущим |
| Повтор доставки / перезагрузка | Не создавать повторный расход, рост, награду или завершение из-за клиентского повтора |
| Оценка технически не получена | Показывать ожидание/техническую ошибку, не семантический провал |

Иллюстративные смысловые состояния: «назначен», «есть подтверждённая часть», «завершён». Это не обязательный новый enum. «Есть часть» не является старым partial, автоматически закрывающим квест. Прежние XP-веса и семидневное открытие NPC не переносить в движок без решения.

Ответ для UI должен позволять отделить реакцию, изменения трёх навыков, состояние/пояснение квеста и реальные изменения ресурсов. Речь о необходимых данных, не обещании существующего endpoint. Для сохранения/генерации использовать принятый итоговый контракт постинга и комментариев, а не создавать ещё один путь отправки ради этого пакета.

| Как и когда списывается энергия при сохранении/оценке/ошибке? | Степан сводит постинг и комментарии с кошельком; общий расход 1 за ход остаётся правилом |
| Какой квест считается этапом с кристаллами и сколько выдаётся? | Денис определяет границу/награду; не подменять этап каждым сообщением |
| Что определяет ежедневную серию, границу суток и получение награды? | Отдельно свести ежедневные действия со Степаном. Не использовать автоматически дни старой кампании |
| Когда доступны остальные NPC и следующий квест? | Первый собеседник нужен сразу для примера; будущие появления и назначения определяет движок. Старый unlockOrder не доказывает готовность |

## Проверка будущей реализации

Это сценарии приёмки, сейчас не выполненные runtime-тесты. Новые автотесты в этой документационной задаче не добавлялись.

- Во всех четырёх мирах видны роль, главная цель, исходные факты и назначенный квест; ID мира и NPC не заменены совпадающим именем.
- После первого неполного действия квест остаётся активным, но проявленный навык может вырасти по правилам сервера.
- Последующий комментарий продолжает тот же квест; подтверждённые части не теряются при возврате в приложение.
- Альтернативный порядок и собственные формулировки принимаются по смыслу; один достаточный ход не блокируется искусственным ожиданием ещё двух.
- Приписанное игроком согласие NPC не засчитывается. Ограниченное согласие и отказ отображаются корректно; альтернативный путь не требует принуждения NPC.
- Завершение первого квеста не объявляет достижение главной цели, поступление денег, успешный тест или отправку обоза.
- Техническое ожидание не показывается как провал. Повтор доставки не создаёт второй результат и расход.
- Нет XP, ручной прокачки и карты мира. Навыки и ресурсы не подменены локальной демонстрацией.
- Общая энергия, обмен и ежедневная серия проверены на настоящем совместимом API отдельно от редакторских текстов.

## Что готово этим пакетом

Сверены четыре завязки и привязки к исходникам; подготовлены четыре многоходовых первых квеста с постами/комментариями, реакциями, альтернативами, критериями и границами. Открытые решения перечислены выше. Визуальная приёмка, утверждение текстов, полный ролевой корпус и реализация движка/нового UI в результат не входят.
