# Продуктовая аналитика

03.10.2026. Зачем: понять, как играют, где бросают и что тянет вернуться, чтобы решать по данным, а не по симуляции. Числа баланса крутим в [config/balance.json](config/balance.json), эксперименты включаем флагами. Журнал ошибок отдельно: `POST /logs` ([backend-spec.md](backend-spec.md), раздел 9).

## Вопросы, на которые отвечаем

| Вопрос | Как смотрим |
|---|---|
| Где бросают онбординг? | воронка `onboarding_step`: age → world → channel → world_settings → done (звезда) → первый `post_publish` |
| Доходят ли до первого поста и итога за первую минуту? | время от `session_start` до первого `post_result` |
| Затягивает ли ход? Сколько постов за сессию, на каком бросают? | `post_publish` по номеру поста за день; последний экран перед `app_hidden` |
| Пишут ли сами или берут «Подскажи»? Когда переходят на своё? | доля `own_words` по номеру поста и дню игры |
| Что делают на лимите? | после `limit_reached`: `invite_sent` / `plus_interest` / лента / уход |
| Возвращаются ли? Что держит? | D1, D3, D7 по когортам дня старта; что было в последней сессии у вернувшихся и у ушедших (нить, залёт, хейт, пустой день) |
| Работают ли друзья? | K: приглашённых, сделавших первый пост, на одного игрока; заруба и дуэль у пар против одиночек |
| Какой мир выбирают и где лучше удержание? | `onboarding_step: world` и D7 по миру |
| Не давит ли хейт? | D1 после дня с хейт-волной против без; переключения градуса драмы |
| Сколько хотят Реки+ и какой оффер лучше? | `plus_interest` на тех, кто увидел 04-2, по флагу `plus_offer` (10 / 20) |
| Какие экраны непонятны? | время на экране (`screen_leave.ms`) и возвраты «назад» сразу после входа |

## Что шлёт фронт

`POST /events`, пачкой раз в 10 секунд и при закрытии через `fetch` с `keepalive: true` (`frontend/src/app/analytics.ts`). Запрос проходит обычную TMA-аутентификацию:

```json
{ "session": "uuid", "platform": "ios|android|tdesktop|web",
  "experiments": { "plus_offer": "10" },
  "events": [{ "name": "screen_view", "t": 1759500000000, "screen": "02-3_result", "prev": "02-2_live", "props": {} }] }
```

`player` не принимается от клиента как доказательство личности. Бэкенд получает Telegram `user.id` только из подписанного `initData`, находит соответствующего игрока и при записи сам добавляет его обезличенный внутренний id. Нет валидного Telegram `user` — событие не принимается. Telegram ID и `initData` в аналитику не записываются.

| Событие | Когда | Свойства |
|---|---|---|
| `active_time` | неперекрывающиеся интервалы видимого приложения до 60 секунд без действий; heartbeat 15 секунд, смена экрана, скрытие | ms: целое 1–30000; не считать фоновое время |
| `session_start`, `app_hidden`, `app_visible` | открытие, сворачивание, возврат | platform, ms_on_screen |
| `screen_view`, `screen_leave` | смена экрана | screen, prev, ms (время на экране) |
| `tap` | вкладка, главная / вторая кнопка экрана | id (`tab`, `cta_main`, `cta_second`), to |
| `onboarding_step` | шаги онбординга | step (age / world / channel / world_settings / done), ok, world, address, star |
| `post_publish`, `post_result` | пост и его итог | len, own_words; delta, viral, flop |
| `limit_reached` | упёрся в лимит | |
| `plus_interest`, `plus_bonus_only` | 04-2 | |
| `invite_sent`, `share` | позвать, поделиться | to (chat / story) |
| `event_answered`, `challenge_post` | событие дня, пост в зарубу | kind, own |
| `report`, `crisis_shown` | жалоба, кризис | reason, adult |

## Что пишет бэкенд сам

`player_created` (группа возраста; событие создаётся до появления мира), `invite_converted`, `post_scored` (три шкалы, quality, номер поста за день), `level_up`, `card_earned`, `stage_reached`, `hate_wave`, `challenge_started`, `challenge_finished`, `notification_sent`, `notification_opened`, `plus_shown`. Сервер видит то, чего не видит фронт: оценки модели, конверсию приглашений, уведомления.

## Метрики теста

D1 ≥ 40%, D7 ≥ 15%; K (честный: приглашённый дожил до D1) ≥ 0,3; постов за сессию; доля своих слов к 3-му дню; конверсия лимит → приглашение; `plus_interest` на показ 04-2.

## Где хранить и смотреть

| Что | Где хранится | Где смотрим |
|---|---|---|
| События поведения (`POST /events`) | OTel logs, OpenObserve stream `product`; бэкенд добавляет `player_id` и `reki.stream=product` | OpenObserve, представления из [dashboards.md](dashboards.md) |
| Ошибки фронта (`POST /logs`) | OTel logs, OpenObserve stream `backend` | OpenObserve по severity, event, screen, status и path |
| Ошибки бэкенда | Console + OTel logs в stream `backend`, связанные с trace/span | OpenObserve Logs и Traces |
| HTTP, runtime, MongoDB, LLM | Стандартные OTel metrics/traces | OpenObserve Metrics и Traces |

Почему так: один self-hosted OpenObserve принимает все три сигнала OTel и позволяет считать продуктовые показатели SQL-запросами. Отдельный Metabase в MVP дублировал бы хранение, доступы и эксплуатацию. Сторонние сервисы за рубежом не используем: аудитория 14+, 152-ФЗ.

`player_id` — созданный бэкендом обезличенный идентификатор. Он допустим в продуктовых логах во внутренней Compose-сети, но запрещён в metric labels из-за высокой кардинальности. После удаления профиля связь идентификатора с игроком исчезает. Срок хранения stream `product` — 90 дней, `backend` — 30 дней; политику retention настраивает команда в OpenObserve. Доступ только у команды.

## Нельзя собирать

Тексты постов, ответов, лички и описаний мира; ники и имена; Telegram ID и initData в событиях; год рождения, дата рождения и точный возраст (только диапазоны 14-17 / 18-24 / 25-34 / 35-44 / 45+; старый 18+ допускается как legacy); геолокацию.

Каждое клиентское событие после выбора созданного мира передаёт отдельное поле worldId — ID экземпляра, который записывается в AnalyticsEntry и атрибут лога world_id. Сервер проверяет принадлежность всех переданных миров игроку. До создания мира поле отсутствует; ID не подставляется в уже накопленные события. Категория баланса остаётся в props.world для группировки метрик.

## Уточнение аналитики 11.10.2026

Сервер сохраняет optional AgeBand из onboarding: 14-17 / 18-24 / 25-34 / 35-44 / 45+. BirthGroup отдельно остаётся 14-17 / 18+ для безопасности; диапазон обязан ему соответствовать. Клиент передаёт только диапазон, не год рождения. В атрибут age_group записывается AgeBand либо legacy BirthGroup. Старые взрослые профили без диапазона не восстанавливаются задним числом.

После успешного создания сервер пишет player_created; post_scored, level_up и card_earned получают мир из экземпляра мира, а возраст из профиля игрока. Посты на игрока считаются по post_scored, не по попыткам post_publish. Gauge reki.players.registered читает число текущих профилей MongoDB раз в минуту и не содержит ID.

Исторические distinct player_id не доказывают число людей: удаление/пересоздание профиля даёт новый ID. На дашборде текущая база аккаунтов отделена от исторических профилей. Определения stickiness, среднего времени, распределений публикаций и темпа — в dashboards.md.

## Продуктовый дашборд v2 — #127

Все календарные дни аналитики — `Europe/Moscow` (UTC+3). Это календарные дни, не игровой сброс лимита в 09:00. Сегодняшний день помечается как неполный.

### Авторитетные события и поля

- `post_scored`: только сервер после успешного commit. `prop_id` — непрозрачный ID сохранённого поста, `prop_delta` — подписанный прирост игровых подписчиков. Повтор одной публикации считается по ID один раз. Старые события без этих полей сохраняются, но не дают измеренного прироста. Клиентский `post_result` не суммируется с серверным событием.
- `post_failed`: только сервер после отметки неуспешной генерации. `prop_id` — ID попытки публикации, повтор обработки не увеличивает число ошибок. Не является завершённым постом.
- `player_created`, `level_up`, `card_earned`, `post_scored`, `post_failed` не принимаются из клиентского batch: клиент не может подделать серверный результат для аналитики.
- `registration_source`: `direct` или `referral` из сохранённой серверной связи `InviteeId` в `invites`, не из произвольного клиентского поля. У старых событий без измерения — `unknown`.
- Optional `launchSurface` в batch: `telegram-mini-app`, `browser`, `standalone`. Экспортируется как `launch_surface`; отсутствующее/неподдерживаемое значение — `unknown`. Способ запуска — наблюдение клиента, не доказательство идентичности. `platform` остаётся устройством/платформой Telegram. Старые события не классифицируются задним числом по iOS/Android. Сейчас авторизованная игра вне Telegram зависит от отдельного проекта Telegram Login/JWT; отсутствие standalone-событий не означает доказанный ноль пользователей.

До создания игрока фронт буферизует события и логи (до 100 записей в каждой очереди). Отправка начинается после успешного `/me` или `/onboarding`, поскольку ручки телеметрии требуют существующего игрока.

### Инвентаризация текущих аккаунтов

Сервис `RegisteredPlayersMetrics` раз в минуту перебирает поток игроков через `IGameStore.GetPlayersAsync`, читает их миры и считает профили за тот же обход. Он отправляет gauge общего количества и минимальные события `profile_snapshot` с `activity_kind=inventory`. Поля: внутренний псевдонимный `player_id`, мир, возрастной диапазон, источник приглашения, виртуальные подписчики, `snapshot_time_unix_ms`. Подписчики суммируются по всем мирам игрока; мир — общий `BalanceKey`, `multi-world` при разных ключах или `unknown`, если миров ещё нет. Нет Telegram ID, имён, ников, текстов постов, ключей или initData.

Завершение набора — `profiles_snapshot_complete` с временем снимка и `registered_count`, без ID игрока. Дашборд выбирает только полный набор (количество уникальных профилей равно expected), не старше 3 минут, с запасом 10 секунд для доставки. Нулевой полный снимок означает 0; отсутствующий/просроченный — NULL. Снимки не являются посещением и не влияют на DAU, когорты, посты, время или retention. Текущие DAU/WAU/MAU пересекают активность с этим набором; удалённый профиль не остаётся текущим аккаунтом.

### Семантика метрик

Воронка — подтверждённые регистрации с `player_created` → ≥1/3/10 серверных постов, единая база. Исторические ID без события регистрации показываются отдельно, не выдаются за регистрации. Retention D1/D3/D7 — точный календарный день после регистрации; в знаменатель включаются только завершённые дни. Источник и мир исторического сегмента берутся из события регистрации, если оно есть; для старых профилей используется известный атрибут истории, с ограничениями.

Stickiness — сумма активных профиле-дней / число полных календарных дней / MAU за тот же интервал. Максимум 30 дней; первый неполный день всей истории исключён. Нулевые календарные дни учитываются в среднем. Показано фактическое покрытие: короткая история даёт предварительную оценку. Это история ID, включая удалённые профили; не число уникальных людей.

При смене мира группировка результата публикации использует мир события поста. Глобальный фильтр «Мир» для исторической когорты — мир регистрации (для старых без регистрации — известный мир истории); текущие аккаунты фильтруются по текущему миру. Эти базы намеренно подписаны отдельно. Один профиль с разными способами запуска относится к `multi`; таблица устройств показывает охват по комбинациям, её строки нельзя складывать как уникальных людей.

Активное время — существующие foreground-чанки после взаимодействия, не время открытого окна. Среднее только по измеренным активным профиле-дням; покрытие показывается рядом. Исторический прирост до добавления серверного delta не восстанавливается из пользовательских текстов или демо: видны число всех постов и число постов с измеренным delta.

Для старой истории есть явный переключатель базы воронки/retention: «Первое наблюдение». Он использует первое подтверждённое посещение, исключая heartbeat и уведомления; это приближение, а не доказательство даты регистрации. По умолчанию выбрана подтверждённая регистрация. Переключатель не меняет определение текущего аккаунта, постов или активного дня.
