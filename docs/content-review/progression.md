# Навыки, аудитория и темп развития

Версия `review-2026-10-20.6`, предложение #192/#195 для [PR #196](https://github.com/Stepami/golden-mouth/pull/196). [Автоматы](stories.md) · [Баланс](balance-check.md) · [Знания](knowledge.md)

## Что работает сейчас

В [PostProgressionCalculator](../../backend/src/Reki.Application/Posts/PublishPostCommand/PostProgressionCalculator.cs) качество публикации Q = clamp((turn.Brave + turn.Humor + turn.Topic) / 3, 0, 1). Это оценки текущего текста, не накопленные уровни игрока. Q влияет на рост и вероятность залёта. Накопленные уровни определяются опытом профиля; в текущем расчёте роста они напрямую не участвуют. quality_bonus_max = 0.21 и unlocks есть в balance.json, но текущий SkillBalance/калькулятор не подключают их как исполнение приёмов. Не обещать уже работающий бонус за уровень.

Опыт получает основной навык поста (максимальная оценка, при равенстве приоритет brave, затем humor, затем topic), остальные по 15%. База — 1 и 0.15. Первые 3 единицы дневного расхода дают ×2; свой текст ×1.3; выполненное желание ×1.3. В текущем временном режиме тем wantId не отправляется, бонус желания не предполагается. XP только при индексе EnergyUsed + 1 ≤ 10; ответ увеличивает EnergyUsed, но XP не даёт. Пороги уровней 2–10: 8, 20, 36, 56, 80, 110, 150, 200, 270. Запас и расход общие для миров.

### Условие и эффект возможности

eligible = snapshot.skill_level ≥ unlock_level AND author_available AND decision(author,P) = TALK AND knowledge_allowlist содержит detail_id этого предложения. На запуск одно q_skill по capability_id. Автор и порог берутся из версии карточки/config, не из клиента. Отсутствующий unlock или неоднозначность — ошибка данных, а не выдуманный уровень.

После сохранения q_skill модуль OFFERED принимает точный ROOT(q_skill,author,r_skill,c_skill) с valid story_ref пока запуск ACTIVE либо обычный свободный ROOT при ACTIVE, PAUSED или после финала. В обоих случаях USED уникален по (run_id,capability_id); operation_id обеспечивает повтор той же квитанции, источник STORY/FREE сохраняется. Перед ответом перепроверяются автор, якорь и актуальная личная политика: для c_skill требуется TALK. При отказе привязанный запрос отклоняется до списания; обычный свободный ответ может состояться по текущей механике, но не создаёт c_skill/USED и не снимает CLOSED. После CANCELLED новые эффекты модуля не учитываются; сама ветка остаётся обычной. Если история на паузе, свободный ответ доступен и влияет только на общий контакт/capability, не закрывает основной этап. Текст не оценивается как инсайд или пародия. Эффект USED — запись факта/дополнительного контакта и готовый ответ NPC, а не экономическая награда. Если reply и main-step конкурируют, у каждого своя привязка; один receipt не закрывает оба.

Открытая информация добавляется из сохранённых q_skill и c_skill с разными object_id: source = NPC, episode_fact_id, seq. Деталь c_skill не раскрывается до ответа игрока. «Использовал возможность» и «узнал факт» различаются: факт становится доступен после публикации соответствующего NPC-объекта, не после того, как игрок якобы понял текст. Знания не размножаются от повторных просмотров; просмотр не является новым событием. Следующая встреча может сослаться на этот конкретный контакт без повторного представления, но не считать героев друзьями.

## Масштаб аудитории

Пороги берутся из stages.views/strike/new_line: сейчас 1000/5000/10000. Это предложение формы NPC-ответа, не новое правило роста и не замок основного сюжета. Снимок подписчиков берётся после последнего обязательного оплаченного действия, до внутренних NPC-шагов результата. Свободный рост, случившийся позже, не меняет выбранный scope.

| Scope | Условие | Обязательные объекты результата |
| --- | --- | --- |
| LOCAL | subs < 1000 | result_main — комментарий главного NPC под p_last. В конфликте result_other — отдельное собственное TALK/SEPARATE второго NPC под тем же p_last. |
| FEED | 1000 ≤ subs < 5000 | result_main — отдельный NPC-пост с исходным PostId/описанием темы. В конфликте result_other — комментарий второго NPC под этим постом. |
| WIDE | 5000 ≤ subs < 10000 | Как FEED, но второй участник публикует отдельный пост о своей позиции вместо комментария. При третьем разрешённом NPC — один его комментарий. Если собеседник один, он оставляет один дополнительный вопрос под своим result_main; не создаётся новый герой. |
| NEXT | subs ≥ 10000 | Все объекты WIDE и next_question — один новый пост главного NPC по зацепке следующей встречи. Это открытый разговор, не запуск ещё не написанной главы. |

Порядок авторов фиксирован: главный = hook_npc; в конфликте другой = второй участник этой пары. Наблюдатель = первый ID из списка участников, не вошедший в обязательных авторов результата. Один автор/назначение получает один объект, дубли не создаются. В одно-NPC истории NEXT создаёт новый вопрос того же героя. Тексты примера «главный ответ» и «следующая встреча» заданы в карточке; outcome и голос подставляются без присвоения слов P.

NPC не переносит авторство текста игрока на себя. Отсылка к исходному обсуждению — новый собственный пост NPC, не пользовательский репост. Все ссылки валидируются в текущем мире. Форма кликабельной ссылки требует поддержки исполнителя/рендеринга; до неё можно дать обычное упоминание игрового автора без обещания работающего репоста. Views, рост подписчиков и XP от этих NPC-объектов не начисляются. Большой канал расширяет видимость, но не заставляет противника согласиться.

## Доверие, достижения и последствия

Готовность NPC учитывает контакты и собственные сохранённые решения из relationships.md. Высокий уровень не снимает CLOSED, не превращает врага в друга и не заменяет взаимное согласие. Не прячем отказ за «плохим» текстом игрока.

В текущем этапе используются только сохранённые достижения этого мира на старте. В этом этапе только first_viral используется как вариация вводной фразы: при IsOpen в снимке старта первый подготовленный NPC-объект получает префикс «Этот канал уже попадал в общую ленту». Ровно один раз на запуск, без смены исхода; если достижение закрыто, префикс отсутствует. Это предложение исполнителя; ten_thousand, skill_mastery и star_card дополнительных доступов в этих вступлениях не дают. Достижения и числовой Relation по-прежнему считает обычный код. Отдельные новые доступы для остальных достижений остаются вопросом дальнейших глав.

## Что подтверждают материалы Status

[Скриншоты 27–30 и 23–24](https://github.com/edtechhackers-agents/reki-concept/blob/e7fc50853908874100749a68c8ab3921146ad242/research/screens-status.md) показывают: распределение skill points, меняющиеся по миру названия навыков, веху с требованиями Engagement Bait 2 и Subtle Self-Promotion 3, XP и отдельные изменения аудитории/отношений после поста. Из них нельзя вывести формулу успеха, влияние каждого навыка на ответы или устройство автоматов. Для «Рек» предложена другая проверяемая связь: уровень даёт NPC-возможность, аудитория меняет публичность, память меняет готовность к следующему разговору. Это наше предложение, не восстановленный код Status.

## Решения, которые ещё нужны

- Согласовать девять NPC-возможностей как применение текущих уровней и их видимую ценность. Они пока не заменяют полноценную реализацию названных приёмов.
- Решить судьбу ×2 награды/риска hot_post, прямого влияния уровня на качество и репостов. Без отдельного решения множителей нет.
- Проверить темп XP по смешанным ролям и фактическую пользу дополнительных разговоров. Расчёты в balance-check.md — сценарии, не прогноз удержания.
- Согласовать показ старого Relation, новой готовности и памяти, не вводя две непонятные пользователю шкалы.
