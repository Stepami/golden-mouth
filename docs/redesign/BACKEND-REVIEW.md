## Короткий сценарий для проверки контрактов

1. **Новый аккаунт:** сервер возвращает10/10энергии и10кристаллов. Смена мира не повторяет выдачу. Для старого аккаунта отдельно определяется конверсия остатка.
2. **Персонаж:** выбран действительный серверный template/instance/actor; UI-ветка «Спасти Хогвартс» не подменяет UUID School. Обычные старые персонажи продолжают открываться.
3. **Первый ход:** готовый редактируемый текст → явная публикация → ожидание → подтверждённое сохранение. Повтор после обрыва использует тот же requestId.
4. **Комментарий:** тот же цикл результата, что у поста; списать1энергию один раз. Возможность закрыть квест определяется разрешённым actionKind и содержанием, а не самим фактом комментария.
5. **Исход:** success/partial/failed + причина + связь с действием/квестом. Технический failed генерации не равен сюжетному неуспеху. Случайный текст не должен получать «успех» за наличие HTTP200.
6. **День:** три квеста → один перевод накопленного XP дня в доступный; totalXP не уменьшается после ручного улучшения навыка. Повторный ответ/перезагрузка не повторяют награду.
7. **Ресурсы:** при0энергии отправка отвергается без потери черновика/бустера; +1через600с до10; обмен3кристаллов пополняет **до10**, не добавляет10 сверх остатка.
8. **Подарок/реакция:** один claim аккаунта за календарный день; inbox возвращает стабильное событие с автором и deep-link. Повторная доставка не дублирует награду/уведомление.

## Чек-лист технических решений

- [ ] Проверить draft233: атомарность списания/начисления, requestId, CAS/stateVersion, конкурентные публикации и обмен.
- [ ] Подтвердить snapshot: amount/cap, nextEnergyAtUtc, regenSeconds, crystals, stateVersion, exchangeQuote; рассмотреть serverNowUtc для часов клиента.

- [ ] Проверить совместимость старого `/me.energy`, onboarding, ежедневной job, Plus и rollback старого runtime.
- [ ] Зафиксировать решение по старым остаткам>10 и бонусной энергии. Не обрезать данные без явной политики конверсии.

### 2. Квесты и результаты постов/комментариев — #192 / #177 / #193

- [ ] Определить persistent storyRun с версией сценария, world/actor/day/quest и разрешёнными переходами.
- [ ] Связать технический результат публикации с отдельным questOutcome, доказательствами и grantId; предусмотреть чтение после обрыва/повтора.
- [ ] Оценка учитывает критерий задания; actionKind ограничивает допустимые пост/комментарий. Не зачитывать любую запись как любой квест.
- [ ] Partial/failure содержат объяснение и разрешённый следующий шаг. Точные критерии и продуктовые пороги фиксирует владелец продукта, backend реализует проверку.
- [ ] Убрать технические ошибки вызова AI-инструментов из категории «не пройдена проверка содержания».

Пример потребности интерфейса (предложение полей, не утверждённый wire DTO):

```json
{
  "actionId": "action-example",
  "actionKind": "comment",
  "questOutcome": {
    "questId": "quest-example",
    "status": "partial",
    "title": "Уточнить условия",
    "reason": "Условие названо, но нет подтверждающего источника.",
    "evidence": [{"kind": "missing_requirement", "key": "source"}],
    "xp": 5
  },
  "audienceDelta": 3,
  "grantId": "grant-example"
}
```

Числа в примере иллюстративные, не новый баланс. На текущем frontend parser принимает status/title/reason/xp; IDs/evidence/grantId и единый протокол post/reply потребуют согласованного DTO. Сейчас delta комментария вычисляется из снимков аудитории — нужен серверный action-specific delta, иначе параллельные действия могут смешать изменения.

### 3. XP и бустеры — #192 / #205

- [ ] Отделить totalXP, pendingXP дня, spendableXP и стоимость улучшения. День состоит из3квестов; release и spend идемпотентны.
- [ ] Не повышать навыки автоматически в новом режиме. Определить конверсию legacy XP/skill progress; локальные начисления не импортировать как доверенные.
- [ ] Серверный инвентарь с effect/ownedCount; бустер резервируется и списывается один раз только по согласованному результату действия. Ошибка/отмена не теряет предмет.
- [ ] Сюжет/песочница проверяются сервером: песочница не выдаёт сюжетный XP и не тратит сюжетный бустер.
- [ ] Согласовать единицы/точность XP и округление дробного бонуса до генерации клиента; текущая локальная модель использует сотые XP внутри.

### 4. Серия, контакты и inbox — #192 / #205

- [ ] Calendar timezone, право на подарок, claimId и ledger на аккаунт. Решить подарок энергии при полном запасе; не выдавать заново при смене мира/устройства.
- [ ] Разделить короткие сюжетные открытия персонажей и реальную подписку: вернуть факт/условие события и авторитетный счётчик.
- [ ] Источник подписчиков NPC: неизвестное поле nullable, не фиктивное число. У собственной аудитории — серверная величина.
- [ ] Реакции/упоминания: eventId, cursor/read state, actor/relation, world/post/comment link, доступ к чужому миру. Не выводить упоминания эвристикой из случайного текста.
- [ ] Возраст/согласие/предпочтения: требуется ли persistent запись и какой контракт. Продуктовый возрастной порог не выбирать в рамках технического ревью.

## Что ожидается по итогам ревью

Для каждого раздела достаточно указать: **существующий контракт / принять кандидат / нужна правка**, источник кода или DTO, конкретный риск и следующий backend-шаг. Для внедрения дополнительно нужны порядок совместимости/rollback и проверки отказа/повтора. Новые issues автоматически не создаются: использовать #205/#192/#177/#193; #121 — приглашения, не серия.

Frontend-замечания не являются обязательным этапом согласования. Backend-ревью также не разрешает merge/deploy/общую миграцию само по себе. Стандартный production workflow меняет оба сервиса, поэтому frontend-only выпуск нельзя выполнять через него без выделения соответствующего способа выкладки.
