## 1. Главный принцип: модель пишет текст, код считает игру

| Делает LLM | Делает код |
|---|---|
| Генерирует текст отдельного комментария выбранной звезды | ML-оценки трёх навыков, причины отписок, подписчики, залёт, опыт, уровни, отношения, лимиты |
| Пишет комментарии фанатов и звёзд, ответы в личке, тексты событий | Кто и когда комментирует, сколько ответов, когда событие |
| Дописывает черновик игрока в голосе канала («Подскажи») | Фильтр 14+, кризис, жалобы, антифрод |
| Собирает правила своего мира из описания | Какие правила можно править (правило 14+ нельзя) |

Первый комментарий к посту и ответы в треде используют один генератор обычного текста без tool calls. Оценки, emoji и обязательного комментатора backend определяет до LLM. Отложенные действия `repost`, `dm`, `start_event(type)` описаны отдельно. Модель не меняет экономику.

### LLM-клиент

- В Application используется абстракция `Microsoft.Extensions.AI.IChatClient`; конкретный провайдер подключается только в Infrastructure через `Microsoft.Extensions.AI.OpenAI`.
- Провайдер предоставляет OpenAI-compatible API. Для MVP используем Chat Completions; переход на Responses API требует отдельного решения и подтверждённой поддержки провайдером.
- Решено 05.10.2026: так как весь игровой контент русскоязычный, основная модель MVP — `gigachat3.5-432b-a28b` без reasoning. Бюджетный fallback — `deepseek-v4-flash` в non-thinking режиме; в MVP переключаем его вручную через конфигурацию, без каскадного повторного вызова. Reasoning-вариант GigaChat оставляем только кандидатом для редких сложных задач. Исследование и тарифный снимок: [llm-model-research.md](llm-model-research.md).
- Base URL, Bearer token и имя модели приходят только из typed options: `Llm__BaseUrl`, `Llm__ApiKey`, `Llm__Model`. Production-значений в репозитории, Compose-файлах, issue и логах нет. Compose передаёт настройки провайдера в backend из переменных окружения `LLM_BASE_URL`, `LLM_PAT`, `LLM_MODEL`; выбор модели для локального запуска также остаётся вне репозитория.
- API вызывается только бэкендом. Фронт не получает URL провайдера, токен или прямой доступ к модели.
- Обычный игровой ход выполняется без reasoning с явными `Temperature` и `MaxOutputTokens`. Для ограниченной генерации и вызова tools достаточно `IChatClient`; многошаговый agent loop в MVP не нужен.
- Prompt каждого хода состоит из двух `System`-сообщений: неизменяемой policy платформы и JSON-данных настроек игрока, правил своего мира и безопасной памяти. Эти данные не могут менять policy, каталог, доступные tools или экономику. Готовые миры используют текущие серверные правила. Голос канала принадлежит игроку, голос звезды — каталогу. Текущий пост или сообщение остаётся `User`-вводом. Изменение доступной игроку настройки применяется уже к следующему вызову модели.
- Ответ модели считается недоверенным вводом: аргументы tools и структурированный JSON проверяются по JSON Schema, все поля строгого контракта обязательны, `additionalProperties: false`; неизвестные поля и любые числа экономики игнорируются.
- Timeout и отмена запроса выполняются вокруг `IChatClient`; генератор комментария возвращает SSE через Mediator `IStreamCommand`. Части ответа не сохраняются в отдельную коллекцию. Ошибка провайдера или небезопасный ответ не отменяет уже созданный пост; текст исключения игроку не раскрывается.
- В telemetry и логи не попадают Bearer token, полный URL провайдера, HTTP body, тексты игрока и ответы модели. Разрешены имя модели, latency, usage, finish reason и безопасный код ошибки.

## 2. Ход: ML-пост и отдельный комментарий (#245, 08.11.2026)

У `PostsController` общий route-префикс `/posts`; маршруты действий заданы относительно него. Лента находится на `GET /posts/feed`, прежний `/feed` удалён. Остальные внешние пути постов не меняются.

1. Клиент отправляет `POST /posts?worldId=…` с `{ text, ownWords, wantId }`. Хендлер последовательно получает игрока и мир, проверяет доступ, вход по действующим правилам 14+ и энергию. Новый POST не принимает publicationId/requestId и не реализует replay, конкурентные проверки или recovery-состояния; каждый успешный запрос создаёт новый пост.
2. Готовые `INliScorer` и `IClassifier` оценивают текст, `IFlopTest` проверяет ругань, повтор, грусть и тревогу. Хендлер добавляет `off_topic` при Topic = 0, если другой причины нет; `PostProgressionCalculator` рассчитывает прогрессию по итоговой причине. `IStarVectorStore` выбирает обязательного первого комментатора. Оценка, поиск повторов и выбор автора выполняются до сохранения. Стор звёзд и Mongo-репозиторий принимают `GamePost` и сами рассчитывают нужные эмбеддинги; хендлер не передаёт векторы. При `InsertPostAsync` внутри UoW репозиторий рассчитывает и сохраняет техническое поле `posts._embedding`.
3. Хендлер явно вызывает репозитории внутри существующего `IUnitOfWork`: пост, энергия, прогресс и действующие награды сохраняются вместе. После commit отправляются телеметрия и существующая фоновая реакция. Ответ JSON: `{ post, result, predictedAuthorId }`; комментариев первоначально нет, `result.bestComment` nullable, hook отсутствует.
4. Frontend показывает сохранённые просмотры, реакции и итог анимацией. Для обязательного автора последовательно вызывает `POST /posts/:id/replies/generation` с `sourceCommentId=null`, затем `POST /posts/:id/replies` с `commentId=null`, чтобы сохранить полученный текст. Корневой комментарий начинает тред. Ошибка генерации не отменяет созданный пост и его экономику; повторного POST создания, polling статуса и подтверждения moderation нет.
5. Комментарий игрока сохраняется через существующий replies API с `{ authorId, requestId, commentId, text }`; ответ `{ commentId, authorId, post, energyLeft, subscribers }`. `AddReply` сохраняет один комментарий без LLM. Для игрока одновременно списывает энергию и начисляет действующий бонус; дополнительный ответчик уже подбирается векторным хранилищем и сохраняется в `GameComment.AdditionalReplierId`. Существующий ключ повтора комментария не распространяется на создание поста.
6. Общий SSE принимает `{ authorId, sourceCommentId, additional }`. Nullable `sourceCommentId` обозначает первый корневой комментарий, а ID — сохранённый комментарий игрока и его ветку. SSE возвращает только текст выбранного автора и статусы `generating/completed/failed`, не сохраняет посты и не меняет экономику. Реплики адресата и дополнительной звезды генерируются и сохраняются отдельно. Дополнительная реплика — корень; адресат отвечает комментарию игрока.

Вход проверяет `PlayerSafetyGuard.EnsureInputAllowedAsync`; сгенерированный и присланный для сохранения текст звезды проходит действующие проверки 14+. Кризисная пауза сохраняется независимо от создания поста. Ошибка ML не считается отсутствием причины и не подменяется ростом. Небезопасная реплика не сохраняется; внутренние ошибки и тексты моделей не попадают в ответ ошибки или телеметрию.

Старые `posts/publications`, `posts/publications/:id`, `posts/publications/:id/moderation`, runtime-модели и репозитории Publication удалены. Миграция 2.6.1 удаляет коллекцию `publications` с индексами после исторических миграций. Миграция 2.6.2 добавляет filter-поля WorldId/AuthorId в существующий векторный индекс для HNSW-поиска. Миграция 2.6.3 переносит Telegram-привязки в ExternalUserIds и заменяет уникальный индекс, сохраняя PlayerId и прогресс. После переноса миграция удаляет все сохранённые токены и авторизации через сервисы OpenIddict; регистрация клиентского приложения и индексы сохраняются. Существующие посты, комментарии и применённый прогресс сохраняются; старым постам без emoji один раз назначается сохранённое значение из 🔥, ❤️, 👎, 🤔. Новый журнал публикаций не создаётся.

### Тред: авторы, AI-контекст и энергия

- `AuthorKind`: Player / Star. `AuthorId` — Vogen над строкой `Player_ID` / `Star_ID`; Mongo хранит ту же строку через сгенерированный BSON serializer, как для остальных ID. Автор разрешается по полному `AuthorId` из владельца мира или его звёзд; исходный ID и тип берутся из найденного автора, отдельных свойств `Kind` / `Id` у `AuthorId` нет. Разделитель при валидации — первый `_`, остальные `_` принадлежат ID. Валидация принимает только точные префиксы `Player_` / `Star_` и непустой ID. Сгенерированные Vogen `Parse` / `TryParse` реализуют `IParsable<AuthorId>` и используют ту же валидацию. `PlayerId.ToAuthorId()` и `StarId.ToAuthorId()` создают тип явно через `AuthorId.Create`.
- `GamePost`: обязательный `WorldId`, `AuthorId`, `Version` и единственный массив `Comments`. Доступ определяется владельцем мира, авторство проверяется отдельно. `ThreadReplies`, `ThreadReply` и `CommentOperation` отсутствуют.
- `GameComment`: `Id`, nullable `ParentCommentId`, nullable `RequestId`, `AuthorId`, `Text`, `Hidden`, `Reactions`, nullable `AdditionalReplierId`. `CommentReaction`: `AuthorId`, `Emoji`. Имена, аватары, роли, `Star`, `Me`, глубина, расход энергии и сумма бонуса в комментариях не хранятся. API разрешает автора из `World.Player` / `World.Stars`, сравнивая сохранённый `AuthorId` с результатом `PlayerId.ToAuthorId()` / `StarId.ToAuthorId()`, вычисляет `Me` относительно текущего игрока и глубину по цепочке родителей. Для отсутствующего автора возвращает данные `WorldStar.DeletedAccount`: имя «Удалённый аккаунт», пустые аватар, ник и роль; `Star = false` не позволяет предлагать ответ отсутствующей звезде. В `authorId` такого ответа остаётся полное сохранённое значение `AuthorId` без разбора строки, чтобы различать авторов реакций. Это применяется к ленте, комментариям, реакциям и повторной выдаче результата публикации. Ответ разрешён только автору из текущего `World.Stars`.
- Корень — глубина 0. Игрок отвечает выбранному комментарию звезды, выбранная звезда отвечает игроку; каждый ответ увеличивает глубину на 1. Разговор можно продолжать без ограничения глубины. Дополнительная реплика другой звезды — новый корень. Сервер проверяет принадлежность обеих звёзд миру и 14+.
- Контекст LLM для треда: пост, цепочка выбранной ветки, сохранённый комментарий игрока, личность звезды и правила мира. Сервер задаёт автора до генерации; модель возвращает только текст до 500 символов без tool calls, оценок поста, hook и памяти лички. Дополнительную звезду выбирает существующий IStarVectorStore по близости к комментарию, исключая адресата; её ID сохраняется в AdditionalReplierId до SSE, текст генерируется отдельным вызовом. Модель не управляет энергией или бонусом.
- `PlayerProfile.EnergyUsed` заменяет `PostsUsed`. Пост стоит `energy.post_cost = 1`, ответ — `energy.comment_cost = 1`; AI входит в эту стоимость. Общий запас всех миров сохраняет прежние лимиты и бонусы из `posts.*`. Счётчик сбрасывается в 09:00 МСК. Рост и опыт поста учитывают `EnergyUsed`, поэтому комментарии сдвигают дневной бюджет прогрессии. `PlayerProfile.Energy` хранит готовый остаток; `EnergyUsed` — расход только для прогрессии. API `/me` и onboarding возвращают `energy` вместо `postsLeft` / `postsCap`; Ответ сохранения комментария возвращает `energyLeft`; SSE генерации передаёт только текст и автора. Расчёт доступности действия использует только `Energy`.
- Миграция 2.2.0 переносит авторов, связи родителей, ключи и старые реакции из `ThreadReplies`, удаляет заменённые поля, переименовывает счётчик без оплаты старых комментариев, заполняет массивы/версии, обновляет индекс `WorldId, CreatedAtUtc`. Встроенные `Publication.Result.Post` мигрируются тоже. Неопределимые/неоднозначные авторы, циклы, потерянные родители и дубли ключей останавливают миграцию для явного разбора исходных данных; runtime-исправлений нет. Она сохраняет `AuthorId` строкой, принимает исторические поля, прежний вложенный `{ Kind, Id }` и готовые строки, проверяет принадлежность миру и допускает повторный запуск. Для строкового рефакторинга изменена сама 2.2.0, новая версия не вводится.

## 3. ML-оценка поста

`INliScorer` даёт независимые Entailment-оценки смелости и юмора. Для оценки «в тему» `TensorPrimitives.CosineSimilarity` рассчитывает cosine между эмбеддингами GamePost и World. Сериализатор мира использует название, описание и роль игрока; вектор мира не сохраняется в доменной модели. Порог `difficulties.<difficulty>.topic_min_cosine` равен 0.35/0.5/0.65 для easy/normal/hard и не зависит от драмы. При cosine >= порога Topic = 1, ниже порога Topic = 0. Эта оценка участвует в quality и опыте; при Topic = 1 разбор показывает отметку «В тему», при Topic = 0 — «Не в тему». Topic = 0 вызывает отписки по общей формуле; при отсутствии другой причины в `GamePost.FlopReason` сохраняется `off_topic`. NotEntailment не означает доказанное противоречие. Quality остаётся средним трёх оценок с существующим ограничением 0…1; основной навык получает прежний основной опыт, остальные — побочный. Модификаторы опыта и роста сохраняются.

`IClassifier` возвращает токсичность и эмоции. Проверки `IFlopTest` выявляют агрессивную ругань (`min(insult, anger)` собственной речи без оформленных цитат), близкий собственный повтор, выраженную грусть и тревогу. Для повторов `$vectorSearch` с HNSW выбирает ограниченный набор кандидатов в истории того же игрока/мира. WorldId/AuthorId входят в pre-filter поисковой стадии и индекс как filter-поля. Из vectorSearchScore восстанавливается raw cosine для существующего порога. Наличие хотя бы одного кандидата выше порога означает повтор (`history.Count > 0`); проверок чисел и NLI нет. Полного перебора истории и запасного exact-поиска нет. Пост передаётся моделям целиком, без нарезки на окна; NLI нужен только для смелости и юмора. Пороги сложности/драмы, приоритеты и формула небольшой потери находятся в `balance.json:difficulties` и [ml-scoring.md](ml-scoring.md).

```csharp
public interface IFlopTest
{
    int Priority { get; }

    Task<FlopTestResult> IsFlopAsync(GamePost post);
}

public sealed record FlopTestResult(bool IsFlop, string Reason)
{
    public static readonly FlopTestResult Ok = new(false, string.Empty);

    public static FlopTestResult Flop(string reason) => new(true, reason);
}
```

Реализации для ругани, повтора, грусти и тревоги внедряются как `IEnumerable<IFlopTest>` и сами предоставляют приоритет и результат с причиной. Скорер использует последовательный async LINQ: сортирует по `Priority`, ожидает каждую проверку и завершает перечисление на первом `IsFlop=true`; конкретные типы тестов ему не нужны. Проверка без причины возвращает `FlopTestResult.Ok`. Хендлер определяет итоговую причину как `score.FlopReason ?? (score.Topic > 0 ? null : "off_topic")`, передаёт её наличие в расчёт прогрессии и сохраняет в `GamePost.FlopReason`. Причина остаётся null только при Topic = 1 и отсутствии других срабатываний. При срабатывании применяется один flop без залёта и без сложения штрафов. Без причины действует прежний положительный расчёт. Отдельного случайного flop нет.

Emoji и разбор формирует код по оценкам. Плашки поясняют результат без дополнительного LLM-вызова и выдуманного числового вклада каждой причины. Промежуточные scores/тон не сохраняются в посте и не выдаются API. Итоговые просмотры, реакции, delta и выбранный автор сохраняются; LLM получает пост и контекст для текста комментария.

## 4. Завершение хода

## 7. Безопасность

- **Возраст:** год рождения и точный возраст не храним. `BirthGroup` остаётся `14-17` / `18+` для безопасности; optional `AgeBand` в onboarding и профиле — `14-17`, `18-24`, `25-34`, `35-44`, `45+` для аналитики, с проверкой соответствия BirthGroup. Младше 14: ничего не сохраняем.
- **Фильтр 14+** на входе (пост, ответ, описание своего мира) и на выходе (текст модели): сексуальный контент, насилие, наркотики, самоповреждение как тема для шуток, травля по внешности. Сработал на входе: мягкий отказ «так не получится, попробуй по-другому», пост не тратится. На выходе: подтверждённая ошибка без перегенерации и списания поста.
- **Кризис:** признаки суицидальных мыслей в любом тексте игрока → игра на паузе, экран 06-2 (14–17, телефон доверия 8-800-2000-122) или 06-3 (18+), хейт выключен на 7 дней. Детектор: классификатор + список фраз; лучше ложное срабатывание, чем пропуск.
- **Конфликт при проверке лички:** если состояние игрока изменилось во время сохранения кризисной паузы, `POST /dm/:starId` возвращает 409; генерация ответа и сохранение переписки не выполняются.
- **Жалоба:** реплика скрыта сразу у пожаловавшегося, разбор за 24 часа, журнал жалоб.
- **Удаление аккаунта:** стирает всё по игроку, включая память звёзд и аналитику с привязкой к ID.

## 9. Аналитика и логи (для теста)

Продуктовая аналитика (вопросы, события, воронки, хранение): [analytics.md](analytics.md). Ниже журнал ошибок.

Ошибки фронт шлёт пачкой на `POST /logs` (`frontend/src/app/log.ts`), события поведения отдельно на `POST /events` (`frontend/src/app/analytics.ts`). Оба метода проходят обычную TMA-аутентификацию и при закрытии отправляются через `fetch` с `keepalive: true`; идентификатор игрока бэкенд определяет по подписанному Telegram `user`, а не принимает от клиента. Каждая принятая ошибка превращается в структурированное событие Serilog и попадает через `MongoDBBson` в общую коллекцию `logs`: `Level`, `UtcTimeStamp`, `RenderedMessage`, `TraceId` и `SpanId` остаются на верхнем уровне, а поля из message template и enrichers (`Event`, `Player`, `Screen`, `Platform`, `Version`, `Status`, `Path`) лежат во встроенном BSON-объекте `Properties`. Параллельную плоскую схему для клиентских логов не создаём. В записях **нет текстов игрока, ников, Telegram ID и initData**: только код экрана, обезличенный id, числа, длины (`len:123`). Ошибки: `js_error`, `promise_rejection`, `render_error` (экран «Что-то пошло не так»), `api_error` (5xx как error, 4xx как warn), `sse_error`; одна и та же ошибка не чаще раза в минуту. Бэкенд хранит логи 30 дней и удаляет их вместе с аккаунтом.

События фронта (`POST /events`): `session_start`, `screen_view`, `screen_leave`, `tap`, `app_hidden`, `app_visible`, `onboarding_step` (age / world / channel / world_settings / done), `post_publish` (len, own_words), `post_result` (delta, viral, flop), `limit_reached`, `plus_interest`, `plus_bonus_only`, `invite_sent`, `share` (chat / story), `event_answered`, `challenge_post`, `report`, `crisis_shown`. Серверные события, полный список с полями и метрики теста: [analytics.md](analytics.md) («Что пишет бэкенд сам»), формат записи для дашбордов: [dashboards.md](dashboards.md).
Метрики теста: D1 ≥ 40%, D7 ≥ 15%, K (честный: приглашённый дожил до D1), доля упёршихся в лимит и что они выбрали, на каком посте впервые пишут своими словами, клик «Хочу Реки+».

## 11. API для фронта

Авторизация игровых методов: `Authorization: Bearer <app access JWT>`. Проверка выполняется OpenIddict validation с локальным сервером; внутренний PlayerId берётся из claim `sub` через синхронное свойство `IRekiContext.PlayerId`. Внешний ID используется при входе и регистрации для поиска игрока. Вход не создаёт профиль и не меняет прогресс. `POST /sessions` остаётся анонимным GUID аналитики. Сырой `initData`, Telegram `id_token` и refresh не логируем и не сохраняем в игровых документах.

Обмены токенов используют form-urlencoded и публичный `client_id=reki-app` (внешний префикс `/api/v1/`):

| Метод | Доказательство и поля | Ответ |
|---|---|---|
| `GET /auth/external/tg/client-id` | Анонимный запрос; ID извлекается SDK Telegram.Bot из префикса токена бота | Числовой Telegram Client ID (JSON number) |
| `POST /auth/external/tg/miniapp` | `Authorization: TMiniApp <raw initData>`; `client_id`, `grant_type=urn:reki:grant:telegram-mini-app` | OpenIddict token JSON |
| `POST /auth/external/tg/widget` | `Authorization: Bearer <Telegram Login JS id_token>`; `client_id`, `grant_type=urn:reki:grant:telegram-login` | OpenIddict token JSON |
| `POST /auth/external/vk` | `Authorization: Bearer <VK access_token>`; `client_id`, `grant_type=urn:reki:grant:vk` | OpenIddict token JSON либо `registration_required` с base64 внешнего ID |
| `POST /auth/external/yandex` | `Authorization: Bearer <Яндекс access_token>`; `client_id`, `grant_type=urn:reki:grant:yandex` | OpenIddict token JSON либо `registration_required` с base64 внешнего ID |
| `POST /auth/refresh` | `client_id`, `grant_type=refresh_token`, `refresh_token`; access не нужен | Новая пара OpenIddict token JSON |
| `POST /auth/logout` | `refresh_token`; access не нужен | 204; отозвана текущая refresh-сессия |

**VK ID (#236):** OneTap возвращает `code` и `device_id`; фронт обменивает их через `Auth.exchangeCode` с PKCE и передаёт `access_token` в `ExternalVkAuthController`. Сервер запрашивает VK `/oauth2/user_info` с настроенным VK application ID и берёт внешний ID только из `user.user_id`. Для нового пользователя возвращается `registration_required`; существующий Basic-онбординг создаёт полный профиль, после чего фронт повторяет VK-вход. Онбординг, собственные access/refresh токены и игровой API сохраняют текущий механизм master. Внешний токен не логируется и не сохраняется в игровых документах; локальная проверка `id_token` не используется.

**Яндекс ID (#265):** кнопка `YaAuthSuggest` получает OAuth `access_token` с `response_type=token`; фронт передаёт его в `POST /auth/external/yandex`. Сервер запрашивает API Яндекс ID `/info`, проверяет `client_id` против настройки `Yandex:ClientId` и получает внешний идентификатор из `id`. Используются отдельные схема и grant Яндекса, общий `IAuthSessionService` и существующий онбординг. Внешнее подтверждение хранится только в памяти вкладки до завершения онбординга или истечения срока; игровые access/refresh токены и их отзыв работают как для VK. Недействительный токен не создаёт сессию; профиль до онбординга не создаётся. Внешний токен не записывается в логи и игровые документы. Публичный Client ID из постановки используется по умолчанию на бэкенде и фронте. В Compose его можно переопределить через `YANDEX_CLIENT_ID`; значение должно совпадать с публичным `yandexClientId` фронта.

Token JSON содержит `token_type=Bearer`, `access_token`, `expires_in`, `refresh_token`. Внешний вход проверяет подтверждение выбранного провайдера и ищет существующего игрока через IExternalUserIdProvider. Его контракт — `Task<ExternalUserId?> GetExternalUserIdOrNullAsync(CancellationToken cancellationToken)`: подтверждённый ID либо null. Telegram-провайдеры возвращают ID из проверенного контекста, VK- и Яндекс-провайдеры вызывают API соответствующего сервиса и проверяют ответ. Провайдеры создают типизированный ExternalUserId, общий код входа не конструирует префиксы. Контроллер передаёт провайдер и client_id в `IAuthSessionService.IssueAsync`; сервис получает внешний ID и возвращает `IssueResult(bool Ok, string? Error, ClaimsPrincipal? Identity)`. При `registration_required` Identity содержит только внешний ID без аутентифицированной сессии; общий API-маппер переносит его в закодированный параметр ошибки. При успехе Identity содержит обычный principal игровых токенов. Если игрока нет, маршрут возвращает HTTP 400 с JSON {"error":"registration_required","external_user_id":"<base64 UTF-8 ExternalUserId>"}, без токенов и записи профиля. Бэкенд кодирует ExternalUserId в base64 UTF-8. Фронт передаёт полученное значение без повторного кодирования в POST /auth/onboarding как Authorization: Basic <external_user_id>. Отдельная схема декодирует полную строку ID, без подписи, шифрования и повторной проверки Telegram. Фронт проходит онбординг и повторяет вход; существующий игрок сразу получает токены. Mini App проверяется штатным `TgMiniAppAuth` (схема и policy `TMiniApp`) и policy ожидаемого grant type. Telegram Login JS проверяется отдельным JwtBearer с issuer, audience из `Telegram.Bot.BotId`, подписью, сроком и policy ожидаемого grant type; формат токена бота не является публичным контрактом Telegram. Refresh также требует только policy `grant_type=refresh_token`, без действующего access. Игровые контроллеры явно требуют policy `RekiAppJwt` с OpenIddict validation. Собственный JWT содержит `sub = PlayerId`. Контекст предоставляет синхронный PlayerId из токена; чтение идентичности не обращается к MongoDB. Игрок и его миры лениво загружаются независимо по этому ID. Внешние идентификаторы используются только при входе и регистрации. Refresh и отзыв хранятся OpenIddict в существующей MongoDB. Совместимость с предыдущей схемой токенов не поддерживается. Текущие значения сроков: 15 минут и 30 дней; постоянные ключи подписи и шифрования поступают только из environment.

**Привязка профиля (#268):** `POST /merge` принимает `FromPlayerId` в JSON-теле, `ToPlayerId` берётся только из текущего игрового контекста. `MergePlayers(FromPlayerId, ToPlayerId)` загружает оба профиля, сохраняет внешние идентификаторы исходного, вызывает `DeletePlayer(FromPlayerId)`, добавляет сохранённые идентификаторы целевому доменной операцией без дублей и сохраняет его через `ReplacePlayerAsync`. Совпадение ID отклоняется с 409, целевой профиль не удаляется. `DeletePlayer` получает явный PlayerId; обычный `DELETE /me` передаёт ID текущего контекста. Очистка данных, сессий и событие `player_deleted` относятся к удаляемому профилю. Новых событий аналитики нет.

Фронт хранит второй игровой JWT и refresh отдельно от активной сессии, запрашивает `GET /me` под вторым JWT и использует ID из ответа как `fromPlayerId`. JWT для извлечения ID не декодируется. Подтверждение доступно только после успешного `/me`; `/merge` использует текущий JWT, не выдаёт новую сессию и не получает второй JWT. После успеха фронт обновляет текущий профиль без сброса мира и черновиков и очищает временные данные второго входа. Провайдер запоминается при новых успешных входах и сохраняется после refresh/перезагрузки; у старых сессий без этой метки провайдер неизвестен, поэтому показываются все способы до следующего входа.

Согласованное ограничение прототипа: сервер доверяет `fromPlayerId` и не подтверждает владение этим профилем. По контракту #268 второго доказательства владения и одноразовых разрешений нет. Удаление исходного профиля и сохранение целевого выполняются последовательно: ошибка сохранения после удаления не откатывает удаление.

### Генерация карточек для сторис

Публичная ссылка строится из случайных внутренних ID игрока и поста. Она доступна любому, кто её знает, пока существуют игрок и пост. Маршрут проверяет принадлежность поста игроку и возвращает 404 для неверной пары и удалённых данных. Telegram загружает PNG без заголовка Authorization.

При реализации динамических PNG рендерер принимает целевой `Stream` и `CancellationToken`, а endpoint пишет результат через `HttpResponse.Body` / `BodyWriter`: готовая картинка не возвращается из Application как `byte[]`, не копируется через `MemoryStream.ToArray()` и не хранится в MongoDB. Если выбранный PNG-кодировщик требует seekable stream или выполняет только синхронную запись, используем ограниченный pooled/recyclable stream и затем `CopyToAsync` в response; синхронный I/O Kestrel глобально не включаем.

- `ArrayPool<byte>` / `MemoryPool<byte>` используем только для временных managed-буферов, которые реально нужны кодировщику. Буфер возвращается в `finally` только после завершения всех async-операций и не сохраняется в кеше после возврата в pool.
- Native-ресурсы рендера освобождаются детерминированно. Шрифты и SVG-иконки входят в backend image; на системные шрифты и emoji Linux не полагаемся.
- Число одновременных рендеров ограничено; ожидание уважает request cancellation. Публичный PNG отдаётся с `Cache-Control: no-store`, чтобы удалённые данные не сохранялись в HTTP-кеше.
- Перед выпуском проверяем под параллельной нагрузкой время p95, managed allocations, process RSS/native memory и освобождение ресурсов после отменённых запросов. Нагрузка не должна приводить к неограниченному росту очереди или памяти.

## 10. Окружение

Production-настройки LLM (`Llm__BaseUrl`, `Llm__ApiKey`, `Llm__Model`), токен бота и строка Mongo приходят только из переменных окружения сервера или защищённого secret store (#26). Отсутствующая обязательная настройка останавливает startup без вывода её значения. Локальный Compose использует те же переменные окружения, не меняя контракт конфигурации приложения. Фронт получает только same-origin runtime config для `/api/v1` и не знает адресов внутренних сервисов.

`docs/config/balance.json` включается в backend Docker image как `/app/config/balance.json`. Бэкенд читает и валидирует его при startup; отсутствующий или невалидный файл останавливает запуск. После внедрения #184 стандартный `reloadOnChange` уведомляет `IOptionsMonitor<GameBalance>` через прямую DI-регистрацию `ConfigurationChangeTokenSource<GameBalance>`; immutable `GameBalanceOptionsFactory` сохраняется. По уточнению ревью #223 от 28.10.2026 потребители получают монитор через DI и читают `CurrentValue` в локальную переменную метода, без передачи баланса параметрами и без кеширования в singleton. Если reload приходится между вызовами обработчика и вспомогательных методов, значения могут различаться; атомарного снимка на весь ход нет. Новый POST использует актуальный баланс; сохранённые посты при чтении не пересчитываются. Уже выданная энергия не пересчитывается; следующий дневной сброс читает новые значения. Ручная замена runtime-файла без рестарта описана в [backend/README.md](../backend/README.md#manual-runtime-balance-update-184). Правка временная: те же значения сохраняются в репозитории для следующего image. Изменение времени сброса требует рестарта для согласования с расписанием; автоматической перестройки расписаний нет. API управления, writable volume и собственный watcher не добавляются.

Личка передаёт выбранное обращение и последние 12 сообщений с исходными user/assistant ролями. В prompt попадают до 20 коротких фактов памяти; инструкция вместо факта отбрасывается при сохранении и чтении. Неизвестный или чужой мирy ID возвращает 404 до вызова модели.

Текстовые поля мира, история и исходный контент остаются данными, а не инструкциями. В фоновой генерации заданный сервером `StarId` определяет единственного автора; остальные звёзды служат контекстом. Назначение автора сервером и повторная проверка его наличия перед сохранением сохраняются.

### Настройки и Реки+ (#104)

PATCH /settings принимает optional address (she/he/nick); POST /plus-interest принимает optional {interest: bool}, без тела interest=true для совместимости. Переход `plus: false → true` сразу добавляет разницу запасов Plus и Free в `Energy`; повторное `plus: true` не начисляет снова. Отключение Plus сохраняет текущую энергию до ежедневного сброса. PlusNotifyRequested отделён от однократного бонуса PlusInterestClaimed; запрос bonus-only не включает уведомление. Обе записи используют CAS по версии профиля с ограниченным повтором. Оплата этим API не реализуется. Поля notifications/quiet сохраняются для совместимости и не управляют доставкой уведомлений. Проверки: [settings audit](audits/settings-2026-10-08.md).

При онбординге Telegram-канал добавляется по Telegram userId. Web Push регистрируется через PUT /me/notification-channels/web-push; канал другого типа сохраняется. ### Консолидация миров (1.2.0 / 2.0.0)

`players` хранит внутренний PlayerId, ExternalUserIds[] типизированных внешних привязок, возрастную группу, обращение, навыки, общие дневные лимиты, Plus, рефералы и NotificationChannels. Коллекция notifications хранит Pending/Sent с SendAt и готовым текстом; Sent удаляются TTL-индексом через 30 дней от SendAt. `worlds` хранит экземпляры миров игрока. `world_templates` хранит готовые шаблоны; обе коллекции используют доменный класс `World`, у шаблонов `PlayerId` равен нулевому ID. Связь с шаблоном и активный мир в документе игрока не сохраняются.

Документ мира содержит канал (имя, ник, роль, аватар), стиль аватарки, голос, драму, подписчиков, прогресс публикаций, желания и достижения. Массивы звёзд (включая `StarTrait`, отношение и его дневной прогресс), ролей, правил и контента встроены в каждый мир и шаблон. Звёзды берутся из выбранного экземпляра мира; отдельного `StarCatalog` нет.

Удаление звезды при полном PUT мира убирает её из `Stars`, сохраняя посты, комментарии, реакции, переписку и память. `ArchivedStars` не используется: миграция `2.4.3` удаляет это поле целиком из `worlds` и `world_templates`, а также удаляет `AppearanceProfile` и `AgeBand` у действующих звёзд. Повторное добавление того же ID в тот же мир восстанавливает авторство по сохранённым `AuthorId` и доступ к переписке; отношение начинается с нуля. Пока звезда отсутствует, новые обращения к ней отклоняются. На фронте пустой сид показывает стандартный кружок с `?`, а возможность ответа определяется наличием автора в текущем составе мира.

Фронт получает шаблоны без авторизации через `GET /worlds/templates` и заполняет описание мира. POST /auth/onboarding получает ExternalUserId через отдельную Basic-схему и создаёт только полностью инициализированного игрока: возрастную группу, обращение, стартовые навыки и энергию, настройки и реферальную атрибуцию. В запросе нет PlayerId или данных мира. ExternalUserId декодируется из Basic-заголовка; JSON тела содержит только данные профиля. Метод возвращает 200 OK без тела. Мир и звезда в его запрос не входят. После успешного создания игрока фронт повторяет внешний вход, получает JWT с sub = PlayerId, загружает профиль через GET /me и отдельным запросом POST /worlds создаёт первый мир; при ошибке этого запроса повторяется только создание мира. `GET /me` возвращает только игрока. `GET /worlds` возвращает полные документы принадлежащих игроку миров, включая звёзд, роли и правила; фронт выбирает нужный экземпляр из этого ответа. Отдельных запросов мира и его правил нет. `POST /worlds` создаёт дополнительный экземпляр из полного описания. В запросе создания мира фронт передаёт описание мира со звёздами, ролями, правилами и контентом; выбор шаблона только заполняет этот объект на фронте. TemplateId содержит UUID исходного доступного шаблона или null для создания с нуля; каталог возвращает только активные шаблоны, POST сохраняет переданный TemplateId без повторной загрузки шаблона; доступ к созданию с нуля проверяется отдельно. PUT сохраняет исходный TemplateId. Сервер всегда назначает новый ID и владельца, выставляет начальных подписчиков и обнуляет прогресс. Онбординг доступен только новому игроку. Для существующего игрока запрос отклоняется с 409 без изменений игрока и миров; дополнительные миры создаются только через POST /worlds. Для операций, которым нужен мир, `worldId` обязателен и передаётся явно в маршруте либо query-параметре; заголовки и автоматический выбор мира не используются.

Миграция `1.2.0` создаёт коллекцию шаблонов с вложенными объектами непосредственно в C#; JSON-файлы при её выполнении не читаются. Миграция `2.0.0` создаёт полный мир каждого существующего игрока из шаблона, выбранного по старому полю `Player.World`, переносит поля и прогресс игрока и привязывает публикации, посты, треды, события и память звёзд к экземпляру мира. Повторное выполнение не перезаписывает изменённые шаблоны и игровые данные.

Миграция `2.0.1` заполняет отсутствующие и BSON-null обязательные массивы пустыми массивами в постах, памяти звёзд, событиях, публикациях, мирах и шаблонах. Существующие массивы и остальные поля сохраняются; повторное выполнение безопасно. Также она восстанавливает отсутствующий/null Experience навыков и старый нулевой Experience выше первого уровня из сохранённых Level/Progress по зафиксированным порогам опыта. Доменные модели читают эти свойства напрямую, без обходов старой схемы.

Решено 12.10.2026: доменный `World` хранит описание и интерфейсные метаданные в `Interface: WorldInterface`, владельца, настройки канала и прогресс — в `Player: WorldPlayer`. Сложность типизирована `WorldDifficulty` в домене и передаётся числом 1–3 в HTTP; драма типизирована `WorldDrama`, в HTTP используется строковый enum. `Presets`, `Handle`, `TotalPostsPublished`, `PostsSinceViral`, `ConsecutiveFlops` удалены. Для аватара остаётся единственный `Avatar`. Миграция 2.0.2 переносит поля обоих видов документов, преобразует драму и заменяет индекс владельца на `Player.PlayerId`, сохраняя звёзд и прогресс. HTTP-описание мира остаётся плоским; запрос создания принимает `avatar`. Залёт определяется вероятностью с выбором по ID поста; с #245 причины отписок определяет ML вместо случайного провала. Первый пост определяется отсутствием `Player.LastPostAtUtc`.

### Расширение аналитики #127

`POST /events` принимает optional `launchSurface` (`telegram-mini-app`, `browser`, `standalone`), старые клиенты остаются совместимы. Серверные события результата не принимаются из клиентского batch. `post_scored` экспортирует непрозрачный ID сохранённого поста и подписанный `SubscriberDelta`; после неуспешной генерации сервер пишет `post_failed` с ID попытки. Размеры наград и игровой баланс не меняются.

Число аккаунтов для аналитики задача TickerQ `RefreshRegisteredPlayersJob` получает раз в минуту через Mongo CountDocumentsAsync и отправляет gauge, без перебора профилей и чтений миров/приглашений. После очистки связанных данных и удаления профиля пишет player_deleted с activity_kind=lifecycle; SQL-панели исключают этот ID из всех расчётов по событиям. Мир и виртуальные подписчики фиксируются после записи мира/поста/ответа через world_audience_updated с activity_kind=inventory и не считаются активностью. Снимки профилей не отправляются; старые удаления без события неизвестны. Подробная семантика и поля — [analytics.md](analytics.md#продуктовый-дашборд-v2--127).

### Удаление мира и поста

`DELETE /worlds/{worldId}` в одной транзакции удаляет мир и его посты по ID без проверки владельца. `DELETE /posts/{postId}` напрямую удаляет пост по ID без проверки владельца и возвращает 204, в том числе если пост не найден. Маршрут удаления мира возвращает 204, в том числе если мир не найден. Удаление поста также удаляет вложенные комментарии. После удаления мира фронт открывает список миров; после удаления поста обновляет список канала или ленты.

### Пагинация постов мира (#209, #211)

`GET /posts/feed` и `GET /posts/mine` принимают через `[FromQuery]` общую модель `WorldPostsRequest` из `Reki.Api/Requests/Posts`: обязательный `worldId`, необязательный `cursor` (UUIDv7 поста), `pageSize` (по умолчанию 10). Лента включает посты игрока и AI-звёзд выбранного мира; канал — только собственные посты игрока. Доступ к миру проверяется до чтения. Имена параметров заданы штатными `[FromQuery(Name = ...)]`, присутствие `worldId` — `[BindRequired]`, размер по умолчанию для OpenAPI — `[DefaultValue]` с той же константой, что используется в инициализаторе свойства.

Обе ручки возвращают общий `PageResponse<T>`: `{ items, nextCursor }`. Элементы имеют прежние типы `FeedItemResponse` и `ChannelPostResponse`. Репозиторий сортирует по `Id DESC`; при заданном курсоре выбирает `Id < cursor`, без `Skip`. UUID хранятся в BSON Standard, поэтому порядок соответствует байтам UUIDv7. Миграция 2.4.8 заменяет индекс по времени индексами `(WorldId, _id DESC)` и `(WorldId, AuthorId, _id DESC)`. Также миграция 2.4.8 удаляет устаревший `ix_invites_player` по полю `PlayerId`; актуальные индексы по `InviterId` и `InviteeId` сохраняются. Повторная миграция ID не требуется: UUIDv7 уже введены миграцией 2.4.6.

Весь цикл страницы выполняет репозиторий: читает `pageSize + 1`, при наличии дополнительной записи удаляет её через `List.RemoveAt` и возвращает ID последнего оставшегося поста как `nextCursor`. Если продолжения нет, `nextCursor` равен `null`; пустая выборка возвращает HTTP 200 с пустым `items` и `nextCursor: null`. Подсчёта общего количества и дополнительной коллекции для отсечения нет. Некорректный курсор, UUID другой версии, неположительный `pageSize`, нечисловые значения и переполнение размера выборки возвращают HTTP 400 `ValidationProblemDetails`. Отдельный продуктовый максимум размера страницы не установлен; техническое ограничение — диапазон Int32 для `pageSize + 1`.

Первый запрос и обновление выполняются без курсора. Клиент передаёт полученный `nextCursor` в следующий запрос, пока он не станет `null`. Следующая страница загружается автоматически при приближении к концу списка. Обновление жестом вниз от начала списка заменяет накопленные страницы первой. Кнопок пагинации нет. При ошибке загруженные посты остаются видны; повтор выполняется обновлением жестом. Повторные запросы блокируются на время загрузки, дубли удаляются по `postId`, запросы предыдущего мира отменяются. Ключи кеша страниц обновлены для нового контракта; совместимость старых ссылок на заменённые ID не поддерживается, постоянной таблицы соответствий нет.

`WorldPostsQuery` требует явные `Cursor` и `PageSize`; внутренние сценарии генерации и публикации читают первую страницу без курсора размером 3 и 20 соответственно. POST-ручки не получают новых query-параметров. Чтение ленты сохраняет прежнюю постановку фоновой генерации. Генерация ID и идемпотентность джобы, `GetPostAsync` и `InsertPostAsync` остаются прежними. Payload фоновой генерации содержит стабильный `PostId` и обязательный `CreatedAtUnixMilliseconds` типа `long`. ID и Unix-время в миллисекундах создаются из одного значения часов при постановке задания. `CreatedAtUtc` поста восстанавливается через `DateTimeOffset.FromUnixTimeMilliseconds`; задержки и повторы не меняют ID и время. Старые задания без числовой метки не поддерживаются и завершаются ошибкой десериализации.

### Фоновая лента звёзд (#148, #188)

После успешной публикации и сохранённого ответа в треде, а также с вероятностью `feed.open_probability` при чтении ленты, backend ставит одноразовый TimeTicker через type-safe `AddAsync<GenerateStarFeedPostJob, StarFeedRequest>`. Параметры содержат типизированные Vogen ID игрока, мира и будущего поста, а также Unix-время создания в миллисекундах (`long`). ID поста создаётся через UUIDv7 при постановке и сохраняется в payload. Payload также хранит `SourceEvent` (FeedOpened/PostPublished/CommentPublished), `SourcePostId` и `SourceCommentId` с доменными PostId/CommentId. Открытие ленты создаёт самостоятельный пост; успешная публикация — реакцию на сохранённый пост игрока; ответ — реакцию на сохранённый комментарий игрока с исходным постом и веткой. Проверяется принадлежность миру и авторство игрока; удалённый/скрытый/чужой источник завершает реакцию без самостоятельного поста. Источник повторно проверяется после AI. У старых заданий 2.5.0 без этих дополнительных полей остаётся поведение самостоятельного поста; источник задним числом не восстанавливается.

После выбора звезды отдельно читаются последние 20 её постов по существующему индексу `ix_posts_world_author_id` и 10 постов общей ленты. Активность других авторов не вытесняет собственную историю звезды. Генератор Application за `IStarTurnGenerator` получает отдельные JSON-блоки собственных публикаций, общей ленты и источника. История помечает автора, StarId (null для игрока) и isOwn. Для комментария передаются его текст, исходный пост, до восьми последних элементов пути к родителю и до восьми уже сохранённых непосредственных ответов; скрытая ветка не используется. Для реакции на пост передаются до восьми видимых комментариев. Все тексты считаются недоверенными данными. Инструкции самостоятельного поста и реакции разделены; запрещены повторы собственных ситуаций/формулировок и пересказ готового ответа в ветке. Джоба только загружает, проверяет и сохраняет; промпты и `IChatClient.GetResponseAsync` остаются в Application. Безопасность, параметры модели, экономика и публичный HTTP-контракт сохраняются.

Перед сохранением текст сравнивается с выбранной собственной историей без учёта регистра и различий пробельных символов. Дословный дубль пропускается с успешным завершением задания, без перегенерации или технического retry. Сохраняемый текст не нормализуется. Проверка не гарантирует смысловую уникальность и не координирует параллельные задания; улучшение разнообразия оценивается отдельно на реальной модели.

`RekiTimeTicker` задаёт три retry с интервалами 30/120/600 секунд до сохранения задания. Технические ошибки передаются TickerQ; небезопасный/пустой ответ и удалённый мир завершаются через `TerminateExecutionException` без повторов. ID результирующего поста сохраняется в payload и остаётся одинаковым на всех попытках джобы; проверка существования перед AI и уникальный Mongo `_id` исключают повторную публикацию. Повтор успешного HTTP-действия не ставит новое задание. Задания хранятся в существующей MongoDB. Между бизнес-коммитом и постановкой нет общей транзакции: отказ постановки, возвращённый TickerQ как неуспешный result, логируется, не отменяет действие игрока, но может потерять эту возможность фоновой генерации. `ScheduleFromPostAsync` и `ScheduleFromCommentAsync` ставят соответствующие задания без вероятностного гейта; `ScheduleFromFeedAsync` ставит его при random < feed.open_probability. CancellationToken.None через эти методы не передаётся; неожиданные исключения шедулер не перехватывает. MongoPostRepository выполняет обычный InsertPostAsync; ошибки вставки передаются TickerQ. Лента загружается одним GET /posts/feed; GET /posts/mine нужен только экрану канала. Детали поста содержат authorId, флагов разрешений нет. Без backend frontend возвращает пустую ленту. Новых продуктовых событий нет.

### Фоновые задачи TickerQ (#146)

Расписания и история исполнений хранятся в той же MongoDB через `alexjamesbrown.TickerQ.MongoDB`. Задача `ResetGameDayJob` запускается ежедневно в 09:00 МСК (`Europe/Moscow`), массово обновляет только игроков и миры со старым дневным периодом и увеличивает версии документов. Она обнуляет расход `EnergyUsed`, выставляет `Energy` по Free/Plus балансу с активной наградой за зарубу, сбрасывает выполненные желания и дневной прирост отношений звёзд; бонус отдыха следует текущему балансу. При старте задачи обслуживания не запускаются; следующий запуск по расписанию обрабатывает устаревшие периоды. Индексы дневных периодов создаёт миграция 2.3.0 без изменения документов. Чтения игрока и миров больше не нормализуют день и не записывают документы. Повторный запуск для того же периода безопасен. Миграция 2.4.0 читает `IOptionsMonitor<GameBalance>.CurrentValue` один раз через DI и переводит прежний лимит минус расход в неотрицательный остаток `Energy`, сохраняя расход и дневной период. Прежние `DailyBonus` и `ChallengeDailyBonus` удаляются; существующая `Energy` при повторе не пересчитывается. `ChallengeBonusUntilUtc` остаётся сроком повторных начислений, их размер берётся из баланса. Уже использованные инвайты не переигрываются.

Трейсы TickerQ, структурированные технические логи и gauge `reki.players.registered` отправляются через существующий OpenTelemetry/OTLP. Подробнее о настройках — [backend/README.md](../backend/README.md#scheduled-maintenance-tickerq).

## Пользовательский контекст и lifetime обработчиков

Mediator и handlers зарегистрированы singleton. `GameDayPeriod` и `ChallengeLifecycle` также singleton; scoped HTTP-сервисы не внедряются в их конструкторы. Внутри операции handler получает локальный `IRekiContext` через singleton `IRekiContextAccessor.Context`. Сам контекст живёт в scoped DI одного HTTP-запроса и хранит только текущий профиль игрока и словарь его миров.

Конструктор контекста не обращается к БД. `Player` и `Worlds` ленивые; повторные обращения переиспользуют загрузку. Чтение только профиля не загружает миры. Существующий `Reload()` сбрасывает lazy-задачи; потребитель заново получает `Player` и `Worlds`, когда нужен свежий пользовательский снимок. После LLM в треде профиль и миры обновляются через контекст, пост читается отдельно, затем повторяются проверки энергии, безопасности, цели ответа и принадлежности миру. Граница коммита — MongoDB-транзакция через `IUnitOfWork`. DAL выполняет прямые записи без `Try`, проверок числа совпавших документов и ручных исключений; ошибки драйвера прерывают транзакцию. Проверки `Version`, статуса публикации и `RequestId` при записи не используются. Последовательный повтор запроса обрабатывается существующими проверками сохранённого ключа в Application.

Промежуточные запросы текущего игрока и его миров удалены. `/me` и `/invitation` сохраняют самостоятельные handlers и готовые DTO. Контекст не хранит посты, переписку, события, соперников или приглашения. Ежедневный сброс энергии и подготовка миров выполняются существующими jobs.

Обычные чтения ленты, канала и деталей поста проверяют выбранный мир в `Context.Worlds`. Store читает посты по проверенному `WorldId`, отдельный пост фильтруется одновременно по ID поста и мира. Повторная загрузка мира в Mongo при этих чтениях не нужна. Публичная карточка сохраняет отдельную проверку владельца по явному `PlayerId`; онбординг получает ExternalUserId из отдельной Basic-схемы через controller и создаёт профиль без игрового JWT. Вызовы, которым нужен только ID, используют синхронный Context.PlayerId без загрузки Player. Соперники и фоновые jobs продолжают читать store по явным ID без обязательного HTTP-контекста.

## Единая сложность и UUID миров — 2.5.0 (#215)

World.Id — WorldId<Guid>, TemplateId — WorldId?, BSON UUID Standard subtype 4; в JSON UUID в формате D. Difficulty находится на уровне World; API и balance.difficulties используют easy/normal/hard. В BSON стандартный EnumSerializer хранит имена Easy/Normal/Hard. BalanceKey и Interface.Difficulty удалены. Создание/редактирование принимает difficulty и nullable templateId; WorldResponse возвращает доменные WorldId и StarId; TemplateId и IsArchived в ответ не входят. Все существующие доменные ID в HTTP-запросах и ответах (WorldId, PlayerId, PostId, CommentId, StarId, AuthorId, RekiEventId, SessionId, ключи навыков SkillId) передаются напрямую; binding и JSON/OpenAPI используют штатную генерацию Vogen. UUID в JSON имеют формат D; курсор — PostId. AuthorId всегда содержит префикс Player_ или Star_. Некорректные route/query ID, в том числе в публичной карточке, возвращают стандартный 400. Строковые ключи повторов комментариев, wants, achievements и пока не реализованных челленджей сохраняют тип из действующей модели, без новых обёрток. Нулевой Player.PlayerId AND TemplateId=null определяют шаблон, доступный каталог дополнительно требует IsArchived=false. Создание сохраняет TemplateId из запроса без дополнительного чтения шаблона; редактирование сохраняет происхождение. Отсутствующая или числовая сложность вне easy/normal/hard сводится к normal при создании и редактировании.

С #245 новый POST рассчитывает результат по текущей World.Difficulty и действующему GameBalance. Отдельной сущности незавершённой публикации и подтверждения больше нет. Изменение сложности влияет на следующие посты; сохранённые результаты не пересчитываются. Проверки доступа, ресурсов и безопасности остаются в простом прикладном сценарии.

Миграция 2.5.0 удаляет старые одноразовые GenerateStarFeedPostJob из ticker_TimeTickers во всех статусах вместо преобразования payload, сохраняя остальные задания и cron-расписания. ### Фронт Web Push (#291, 12.11.2026)

Фронт использует сгенерированный из backend #293 метод `registerWebPush` и DTO `WebPushSubscriptionRequest` через существующий авторизованный transport. Успешное сохранение — только после `200`. Публичный `webPushPublicKey` берётся из runtime config и соответствует отправителю; приватный ключ фронту не передаётся. Нет дополнительных GET статуса/ключа или DELETE.

Worker принимает `{title: "Реки", body: Notification.Content, url: "/"}`, ограничивает переход origin приложения и показывает фиксированное название «Реки». В Telegram frontend не вызывает requestWriteAccess и не проверяет статус бота. Backend-расписание, каналы, миграция и отправители этим frontend PR не меняются.

## Репосты и цитаты (#205, 13.11.2026)

- `PUT /posts/{postId}/repost?worldId=…` публикует или восстанавливает обычный репост оригинального поста героя. `DELETE` по тому же пути отменяет. Возвращают `postId`, `active`, `subscriberDelta` (награда только этого запроса), `energyLeft`, `subscribers`. Для отмены допустим также ID собственной записи репоста: оригинал может быть удалён.
- В одной MongoDB-транзакции перечитываются профиль, принадлежащий ему мир и оригинал. Ссылка `RepostId` на оригинале и поля `RepostActive`, `IsRepost`, `RepostHidden` на документах обеспечивают устойчивую идемпотентность. Повтор транзакции перечитывает данные, поэтому параллельные запросы не тратят энергию и не выдают награду повторно. Нет дополнительных коллекций, индексов или миграций: чтение по ID/миру использует существующие индексы.
- Первая публикация тратит `energy.post_cost`; прирост рассчитывается по разделу «Репосты» game-flow и `repost.growth_multiplier`. Не вызывает обычный publish/progression, инвайт, ежедневные задания, навыки, кристаллы или AI-генерацию. Достижение порога аудитории сохраняет доступ к созданию своего мира, как при обычном посте. Восстановление и повтор не меняют энергию/награды. Отмена меняет только видимость. Атомарность критична: сбой вставки откатывает расход и награду.
- `POST /posts` принимает необязательный `quotedPostId`. Проверяются существование оригинала, герой в текущем мире, отсутствие вложенной цитаты и непустой собственный текст. В первой версии `wantId` вместе с цитатой недопустим. Собственный текст остаётся `GamePost.Text`, ссылка — `QuotedPostId`; текст оригинала не копируется в документ. Действующий `ownWords` относится только к своему тексту.
- NLI, эмоции, безопасность и near-copy обрабатывают только собственный текст. Вектор темы использует оригинал + собственный текст. Реакция героя получает оригинал как контекст данных. Обычные посты без `quotedPostId` сохраняют прежнее поведение. Публикация цитаты не повторяется автоматически при неизвестном результате.
- Feed/Channel/Post DTO дополнены `quote: {postId,author,avatar,text} | null`, `isRepost`; feed также `canRepost`, `reposted`. Оригиналы читаются пакетно по ID в проверенном мире. Отсутствующий оригинал/автор возвращает null в полях автора и текста. Отменённые репосты исключаются из страниц до применения лимита/курсора. Старые записи с отсутствующими полями продолжают читаться.
