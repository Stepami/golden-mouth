# Представления OpenObserve

05.10.2026. Источники: log streams `product` и `backend`, стандартные OTel metrics и traces. В issue #35 поднимается сбор и хранение; автоматическое provision дашбордов и алертов не входит в MVP.

## Конкурсные показатели

| Показатель | Как считать | Источник |
|---|---|---|
| DAU | `count(distinct player_id)` по календарному дню, `activity_kind = real` | `product` |
| Обращения / DAU | число GenAI operations за день / DAU | `gen_ai.client.operation.duration` и `product` |
| Токены | сумма input/output token usage по модели и операции | `gen_ai.client.token.usage` |
| LLM-cost / DAU | `(input_tokens × input_price + output_tokens × output_price) / DAU`; цены хранятся в версии запроса/дашборда, а не в телеметрии | GenAI metrics + прайс модели |
| Ошибки | 5xx и Error/Critical по часу, route и exception type | HTTP metrics + `backend` |
| Нагрузка | RPS, p50/p95/p99 latency, active requests, GC, allocations, exceptions, thread-pool queue | ASP.NET Core + runtime metrics |

Тестовые и отладочные обращения не должны попадать в конкурсный расчёт. Production-события имеют `activity_kind = real`; тесты проекта не экспортируют OTLP.

## Поля продуктового stream

`ProductTelemetry` пишет плоские log attributes: `event_name`, `player_id`, `event_time_unix_ms`, `received_time_unix_ms`, `session_id`, `platform`, `screen`, `previous_screen`, `world`, `age_group`, `experiment_plus_offer` и разрешённые `prop_*`. Тексты постов, сообщений, комментариев, имена, Telegram ID и `initData` не экспортируются.

Для DAU и когорт используется `player_id`, для сессий — `session_id`. Эти поля допустимы в log stream, но не должны становиться labels OTel-метрик.

## Продуктовый дашборд: решения по данным

Обновлено 11.10.2026. Источник — SQL в `observability/dashboards/panel-sql/`, сборщик `build.py`, готовый `product.json`. Каждая панель отвечает на вопрос, а не просто показывает число событий.

| Вопрос | Панель и определение | Что решаем |
|---|---|---|
| Сколько профилей сейчас существует? | `max(reki_players_registered)`: точный CountDocuments MongoDB, обновление раз в минуту. Gauge без ID из meter `Reki.Product`. До релиза / при отсутствии замера нет данных, а не 0. | Текущий размер базы аккаунтов. |
| Каков наблюдаемый охват? | Уникальные непустые `player_id` в real-телеметрии за 90d, MAU30 / WAU7 rolling, DAU сегодня/вчера UTC. Отправка уведомления и heartbeat `active_time` не означают посещение. | Охват и тенденция DAU; текущий день неполный. |
| Возвращаются ли часто? | Stickiness = DAU вчера / уникальные активные профили за 30 полных дней перед сегодняшним UTC-днём ×100. Все, миры и возраст; база рядом. Это ежедневный DAU/MAU, не cohort retention. | Проверять частоту возвращения. При истории короче месяца оценка предварительная. |
| Сколько создают контента? | Последние 7 полных UTC-дней: `post_scored` / активные профили; `post_scored` / активные игроко-дни. Серверное подтверждение, не клиентский клик `post_publish`. | Меняется ли глубина игры, а не только число посещений. |
| Кто играет интенсивнее? | Два 100%-ных столбчатых распределения: по миру и по возрасту, группы 0 / 1 / 2–4 / 5–9 / 10+ серверных постов за активный игроко-день. Знаменатель включает дни с посещением и нулём постов. | Где больше «зашёл и ушёл», где возникает регулярная публикация. Это доли активных дней, не доли уникальных людей. |
| Сколько времени активно играют? | Среднее и медиана суммы `active_time.ms` на измеренный активный игроко-день. Рядом measured_player_days. Только после релиза нового измерителя: NULL до данных. | Длительность вовлечения; сравнивать вместе с постами и покрытием. Не общее время открытой вкладки и не длительность сессии. |
| До каких шагов доходят? | Отдельные столбцы доли профилей с ≥1 / ≥3 / ≥10 `post_scored` за 90d, включая нулевую активность. Пороги не складываются. | Где перестают публиковать. Когорты разного возраста, поэтому это охват, не честное причинное сравнение. |
| Каков темп прогресса? | Медиана часов от первого наблюдаемого события до третьего подтверждённого поста **только среди дошедших**, число дошедших и база. Также доли с любым `level_up` и `card_earned`. | Темп раннего прохождения. Не завершение игры; награда может быть любой, уровень — любого навыка. |
| Возвращается ли новая когорта? | D1/D7 по дню первого наблюдения за 90d, точный календарный день возврата UTC. Целевой день строго раньше последнего дня доступной телеметрии; незавершённый знаменатель 0, процент NULL. | Проверять удержание после первого знакомства. Первое наблюдение не обязательно дата регистрации. |
| Кто перестал заходить? | Недельная неактивность: активен в предыдущие полные 7 UTC-дней, отсутствует в последние 7. Все, миры, возраст. NULL до 14 дней истории или при нулевой базе. | Следить за выпадением активной базы. Это не окончательный уход и не отмена подписки. |

Сводные панели сканируют собственный диапазон **90d**, чтобы глобальные 4w не обрезали MAU, историю сегментов и когорты; временные окна 7/30 дней применяются внутри SQL. DAU-тренд следует глобальному диапазону. Окна привязаны к текущему серверному времени, не к концу исторического выбора. Явные panel-time параметры URL могут усечь историю и исказить эти показатели.

### Идентификаторы и сегменты

`player_id` создаётся сервером и берётся из профиля подписанного Telegram-аккаунта, не из клиентского поля. В MongoDB уникальный индекс `TelegramUserId`; повторные сессии и устройства одного профиля не увеличивают distinct count. Однако удаление и повторная регистрация создают новый `player_id`. Старые логи не содержат Telegram ID: связать такие исторические профили с одним человеком нельзя. Поэтому исторические MAU/DAU/когорты — **ID профилей**, а не доказанное число уникальных людей. Текущая база аккаунтов показывается отдельно прямым gauge MongoDB.

Возраст для аналитики: `14-17`, `18-24`, `25-34`, `35-44`, `45+`; год рождения и точный возраст остаются на устройстве. Старое `18+` маркируется `18+ (legacy)`; оно не распределяется по новым диапазонам. Если у профиля есть новый диапазон, старые события с `18+` не создают ложный mixed-сегмент. Игровая безопасность по-прежнему использует BirthGroup `14-17` / `18+`.

Мир и возраст разрешаются на уровне профиля из непустых атрибутов. Несколько разных известных значений — `multi-world` / `multi-age-group`; отсутствие — `unknown`. Каждый профиль один раз в каждом измерении. Строки «все», мира и возраста не суммировать между собой. Проценты малых сегментов — гипотезы, а не вывод об эффективности; всегда смотреть на базу.

### Время и полнота данных

`active_time` — неперекрывающиеся интервалы видимого приложения. Heartbeat раз в 15 секунд, сброс при смене экрана и скрытии; после 60 секунд без pointerdown/keydown/scroll счёт останавливается. Один интервал не более 30 секунд, сервер отбрасывает нечисловые, отрицательные, нулевые и слишком большие значения. Возврат после простоя не начисляет время простоя. Редкие интервалы при задержке таймера могут недосчитать время; потерянные клиентские события также дают недосчёт. Фон, старые screen_leave и весь интервал между session_start/app_hidden не подменяют этот показатель.

Начало и завершение приложения не равны 30-минутным сессиям. Число raw events и суммарные screen_view/tap не используются как глубина игры. Убраны декоративные охваты событий, счётчик сессий и неоднозначный график «новых игроков в выбранном диапазоне». Диагностика доставки остаётся в Logs и техническом дашборде.

Новые возрастные диапазоны, active_time, player_created и gauge текущей базы требуют релиза frontend/backend. Без релиза графики на существующих сигналах работают, а новое время и текущая база остаются без данных. Никакие исторические значения не выдумываются. Тестовые сессии команды с `activity_kind = real` всё ещё попадают в расчёт; для исключения нужны отдельные надёжные признаки.
