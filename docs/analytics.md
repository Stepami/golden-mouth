## Что шлёт фронт

При загрузке приложения фронт анонимно вызывает `POST /sessions` и получает UUID строкой. Бэкенд выдаёт новый GUID без записи в Mongo. Фронт использует этот ID для аналитики и журналов ошибок до перезагрузки страницы; до получения ID события остаются в очереди.

`POST /events`, пачкой раз в 10 секунд и при закрытии через `fetch` с `keepalive: true` (`frontend/src/app/analytics.ts`). Запрос проходит аутентификацию собственным app Bearer:

```json
{ "session": "uuid", "platform": "ios|android|tdesktop|web",
  "experiments": { "plus_offer": "10" },
  "events": [{ "name": "screen_view", "t": 1759500000000, "screen": "02-3_result", "prev": "02-2_live", "props": {} }] }
```

`player` не принимается от клиента как доказательство личности. Бэкенд получает PlayerId из проверенного `sub` собственного JWT и при записи сам добавляет его обезличенный внутренний id. Внешняя авторизация проверяется при входе и регистрации; без действующего app Bearer событие не принимается. Внешние идентификаторы Telegram/VK, `initData` и токены провайдеров в аналитику не записываются.

## Что пишет бэкенд сам

`player_created` (группа возраста; событие создаётся до появления мира), `player_deleted` (после удаления данных и профиля; служебное событие), `world_created` (после сохранения мира: внутренний `world_id`, `template_id` = UUID шаблона (null для мира с нуля), `difficulty` = easy/normal/hard, возраст), `invite_converted`, `post_scored` (три шкалы и quality), `level_up`, `card_earned`, `stage_reached`, `hate_wave`, `challenge_started`, `challenge_finished`, `notification_sent`, `notification_opened`, `plus_shown`. Сервер видит то, чего не видит фронт: оценки модели, конверсию приглашений, уведомления.

D1 ≥ 40%, D7 ≥ 15%; K (честный: приглашённый дожил до D1) ≥ 0,3; постов за сессию; доля своих слов к 3-му дню; конверсия лимит → приглашение; `plus_interest` на показ 04-2.

## Где хранить и смотреть

| Что | Где хранится | Где смотрим |
|---|---|---|
| События поведения (`POST /events`) | OTel logs, OpenObserve stream `product`; бэкенд добавляет `player_id` и `reki.stream=product` | OpenObserve, представления из [dashboards.md](dashboards.md) |
| Ошибки фронта (`POST /logs`) | OTel logs, OpenObserve stream `backend` | OpenObserve по severity, event, screen, status и path |
| Ошибки бэкенда | Console + OTel logs в stream `backend`, связанные с trace/span | OpenObserve Logs и Traces |
| HTTP, runtime, MongoDB, LLM | Стандартные OTel metrics/traces | OpenObserve Metrics и Traces |

Почему так: один self-hosted OpenObserve принимает все три сигнала OTel и позволяет считать продуктовые показатели SQL-запросами. Отдельный Metabase в MVP дублировал бы хранение, доступы и эксплуатацию. Сторонние сервисы за рубежом не используем: аудитория 14+, 152-ФЗ.

`player_id` — созданный бэкендом обезличенный идентификатор. Он допустим в продуктовых логах во внутренней Compose-сети, но запрещён в metric labels из-за высокой кардинальности. После удаления профиля связь идентификатора с игроком исчезает. Срок хранения stream `product` — 90 дней, `backend` — 30 дней; политику retention настраивает команда в OpenObserve. Доступ только у команды.

## Нельзя собирать

Тексты постов, ответов, лички и описаний мира; ники и имена; Telegram ID и initData в событиях; год рождения, дата рождения и точный возраст (только диапазоны 14-17 / 18-24 / 25-34 / 35-44 / 45+; старый 18+ допускается как legacy); геолокацию.

Каждое клиентское событие после выбора созданного мира передаёт отдельное поле worldId — ID экземпляра, который записывается в AnalyticsEntry и атрибут лога world_id. Сервер проверяет принадлежность всех переданных миров игроку. До создания мира поле отсутствует; ID не подставляется в уже накопленные события. Категория баланса остаётся в props.world для группировки метрик.

## Уточнение аналитики 11.10.2026

Новые аккаунты регистрируются только с 18 лет. В age_group отправляется диапазон, вычисленный из текущего серверного UTC-года и BirthYear: 18-24 / 25-34 / 35-44 / 45+. Сам год в события, логи и метрики не включается. Миграция 2.7.8 назначает старым профилям год по сохранённой группе; исторические события не переписываются.

После успешного POST /auth/onboarding сервер пишет player_created; это одновременно создание игрока и завершение регистрации. Вход только выдаёт токены существующему игроку и не создаёт событие регистрации; после сохранения мира — world_created; post_scored, level_up и card_earned получают мир из экземпляра мира, а возраст из профиля игрока. Посты на игрока считаются по post_scored, не по попыткам post_publish. Gauge reki.players.registered читает число текущих профилей MongoDB раз в 30 минут и не содержит ID.

Distinct player_id не доказывают число людей: удаление/пересоздание профиля даёт новый ID. На дашборде общий счётчик Mongo отделён от наблюдаемой аудитории событий. Определения stickiness, среднего времени, распределений публикаций и темпа — в dashboards.md.

### Авторитетные события и поля

- `post_scored`: только сервер после успешного commit. `prop_id` — непрозрачный ID сохранённого поста, `prop_delta` — подписанный прирост игровых подписчиков. Повтор одной публикации считается по ID один раз. Старые события без этих полей сохраняются, но не дают измеренного прироста. Клиентский `post_result` не суммируется с серверным событием.
- `post_failed`: только сервер после отметки неуспешной генерации. `prop_id` — ID попытки публикации, повтор обработки не увеличивает число ошибок. Не является завершённым постом.
- `player_created`, `player_deleted`, `world_created`, `level_up`, `card_earned`, `post_scored`, `post_failed` не принимаются из клиентского batch: клиент не может подделать серверный результат для аналитики.
- `registration_source`: `direct` или `referral` только в серверном `player_created`, по проверенному приглашению при регистрации. В профиле отдельного поля нет; остальные события не читают приглашение ради аналитики. Дашборд связывает источник с игроком по событию регистрации; у старых данных без измерения — `unknown`.
- Optional `launchSurface` в batch: `telegram-mini-app`, `browser`, `standalone`. Экспортируется как `launch_surface`; отсутствующее/неподдерживаемое значение — `unknown`. Способ запуска — наблюдение клиента, не доказательство идентичности. `platform` остаётся устройством/платформой Telegram. Старые события не классифицируются задним числом по iOS/Android. Сейчас авторизованная игра вне Telegram зависит от отдельного проекта Telegram Login/JWT; отсутствие standalone-событий не означает доказанный ноль пользователей.

До создания игрока фронт буферизует события и логи (до 100 записей в каждой очереди). Отправка начинается после регистрации, получения игрового JWT и успешного `/me`, поскольку ручки телеметрии требуют игровой Bearer. Один `registration_required` не разрешает отправку событий.

### Количество аккаунтов и удаление

Задача TickerQ `RefreshRegisteredPlayersJob` раз в 30 минут напрямую считает профили в MongoDB через `CountDocumentsAsync`. Singleton-джоба хранит последнее измерение и отправляет только gauge `reki.players.registered` (в PromQL — `reki_players_registered`), без перебора игроков, чтения миров или приглашений и без снимков профилей. Карточка «Всего аккаунтов в Mongo» показывает общий счётчик; фильтры продуктовых сегментов к нему не применяются. После запуска backend метрика появится после первого выполнения джобы; её отсутствие не означает ноль.

После успешного создания мира, публикации поста, ответа с бонусом сервер пишет `world_audience_updated`: `player_id`, `world_id`, `template_id` (UUID шаблона или null), `difficulty` (easy/normal/hard), `subscriber_total`. Событие служебное (`activity_kind=inventory`) и не принимается с клиента. Дашборд берёт последнее событие по `_timestamp` для каждого мира, затем суммирует состояния по игроку. События не складываются друг с другом; версия мира не передаётся. Подписчики старых миров без такого события неизвестны до следующего изменения аудитории; `audience_known_accounts` показывает число профилей с доставленным состоянием. Покрытие внутри старого профиля может быть неполным, если обновились ещё не все его миры. Нет дополнительных чтений для построения события и нет Telegram ID или пользовательских текстов.

При слиянии профилей (#268) существующее событие `player_deleted` относится только к удаляемому профилю второго входа; нового события нет. Сохраняемый профиль остаётся в аналитике под прежним ID.

После успешной очистки связанных данных и удаления профиля сервер пишет `player_deleted` с `player_id` и `activity_kind=lifecycle`. Событие не является посещением, не влияет на DAU и не принимается от клиента. Все SQL-панели исключают ID с доставленным событием удаления из наблюдаемой аудитории, исторической активности и когорт. Повторная доставка удаления и поздние игровые события этого ID не возвращают его в расчёт; повторная регистрация создаёт новый ID. Старые удаления без такого события неизвестны: миграции или восстановления истории нет. SQL использует доступную историю событий за 90 дней, поэтому число наблюдаемых профилей может отличаться от общего счётчика Mongo. Прежние события снимков больше не используются.

### Семантика метрик

Воронка — подтверждённые регистрации с `player_created` → ≥1/3/10 серверных постов, единая база. Исторические ID без события регистрации показываются отдельно, не выдаются за регистрации. Retention D1/D3/D7 — точный календарный день после регистрации; в знаменатель включаются только завершённые дни. Источник исторического сегмента берётся из серверной регистрации; мир — из последних состояний миров, затем из известных игровых событий. Значение unknown не заменяет известный мир. Для старых профилей используется известный атрибут истории, с ограничениями.

Stickiness — сумма активных профиле-дней / число полных календарных дней / MAU за тот же интервал. Максимум 30 дней; первый неполный день всей истории исключён. Нулевые календарные дни учитываются в среднем. Показано фактическое покрытие: короткая история даёт предварительную оценку. Это история ID без профилей с доставленным событием удаления; не число уникальных людей.

При смене мира группировка результата публикации использует мир события поста. Глобальный фильтр «Мир» для профиля использует последние доставленные состояния миров, затем известный мир игровых событий; публикации группируются по миру события поста. Один профиль с разными способами запуска относится к `multi`; таблица устройств показывает охват по комбинациям, её строки нельзя складывать как уникальных людей.

Активное время — существующие foreground-чанки после взаимодействия, не время открытого окна. Среднее только по измеренным активным профиле-дням; покрытие показывается рядом. Исторический прирост до добавления серверного delta не восстанавливается из пользовательских текстов или демо: видны число всех постов и число постов с измеренным delta.

Для старой истории есть явный переключатель базы воронки/retention: «Первое наблюдение». Он использует первое подтверждённое посещение, исключая heartbeat и уведомления; это приближение, а не доказательство даты регистрации. По умолчанию выбрана подтверждённая регистрация. Переключатель не меняет определение текущего аккаунта, постов или активного дня.
## Техническая стоимость LLM

Существующие chat traces дополняются полем `gen_ai.usage.cost` с валютой `RUB`; это техническая телеметрия, не новое продуктовое событие. Для streaming `LlmSpendChatClient` передаёт `stream_options.include_usage = true` и читает `usage.cost` из чанка через SDK JsonPatch, пока GenAI-спан ещё открыт. Стоимость появится только если администратор шлюза включил `litellm_settings.include_cost_in_streaming_usage = true`; это не параметр клиентского запроса. Для обычного ответа `LlmSpendPolicy` читает заголовки стоимости. Обе обёртки используют `LlmSpendWriter`. Дополнительных запросов журнала и ожидания стоимости нет; если поле отсутствует, приложение не записывает стоимость. Начальный расход без детализации зарегистрирован отдельно в log stream `llm_cost_ledger`. В метрики не добавляются player/post/request IDs, ключи или тексты. Методика описана в [dashboards.md](dashboards.md#стоимость-шлюза).

## Загрузка изображений игры (#156)

`image_loaded`: фиксированный `asset` (`welcome_portrait`, `cover_evening`, `cover_sorcerers`, `cover_houses`, `cover_it`), `duration_ms`, `transfer_bytes`, `decoded_bytes` из Resource Timing. `image_failed`: тот же фиксированный `asset`. Без URL, текста или фотографий игроков. Нулевой transfer может означать кеш; отсутствующий Resource Timing не доказывает мгновенную загрузку. События идут через существующую очередь после появления игрока: неавторизованные посетители первого экрана не входят в эти агрегаты. Исторических замеров до этого изменения нет.

Для проверки задержек: в OpenObserve stream product фильтровать name=image_loaded, группировать по props.asset, считать p50/p95 duration_ms; image_failed проверять отдельно. Серверные API traces не измеряют загрузку статических файлов фронта.

### Порядок загрузки обложек (#158)

Обложки каталога, обзора и начала истории отображает общий `WorldCover`: браузер выбирает 640/960 px через srcset/sizes по ширине и плотности экрана. Первая карточка имеет high priority и начинает запрос параллельно загрузке шаблонов. Остальные карточки начинают загрузку через IntersectionObserver с небольшим запасом до видимой области; это предотвращает конкуренцию дальних карточек за соединение. Размер места для обложки постоянный, до декодирования видна спокойная подложка; появление учитывает reduced-motion. Hash URL сохраняет immutable cache между экранами. Оригиналы остаются источниками для будущих размеров.


С 2.5.0 (#215) world_id — UUID экземпляра в формате D; template_id обозначает происхождение, difficulty — механическую сложность. С #245 post_scored и связанные награды записываются после успешного commit создания поста; difficulty берётся для расчёта в POST. Генерация первого комментария идёт отдельно и не отправляет post_scored повторно. Существующие игровые оценки brave/humor/topic и quality сохраняются в post_scored; тексты, векторы и сырые выходы классификаторов токсичности/эмоций не передаются. Старые обозначения миров больше не отправляются как world/BalanceKey. Исторические внешние события не переписываются. При сравнении периодов нормализовать строковые GUID world_id (с дефисами и без) и учитывать, что ранние составные ID заменены детерминированными UUID по алгоритму миграции; исходные старые события сохраняются.

### own_words — решение 13.11.2026 (#297)

В post_publish передаётся тот же флаг, что в POST /posts. Готовая идея устанавливает false; любые неполные правки сохраняют false. Только фактическое пустое поле или «Очистить» возвращают true. Ручной ввод совпадающего текста не переводит true в false. Отмена замены и восстановление черновика сохраняют флаг. Доля false измеряет использование вставленной готовой идеи, а не отсутствие правок; прямое сравнение с прежней семантикой «любая правка — свои слова» требует учёта даты изменения. Новые события не вводятся.

### Репосты и цитаты — #205

`post_publish`, `post_result` и серверный `post_scored` имеют `publication_kind=post|repost|quote`. Сервер определяет вид по `RepostId` и пустому/непустому собственному тексту. Оригинальные тексты не отправляются. Старые события без поля считаются обычными постами. Отдельные события `post_repost` / `post_repost_undo` не добавляются: репост — обычная публикация. Конверсию 1→2→3 авторских поста считать отдельно от `repost` и `quote`.

### Личная отметка поста — #302

После подтверждённого сохранения (в том числе через GET после потерянного ответа) frontend отправляет существующее событие `tap` с `to=post_mark`, `own=true|false` — сохранённое состояние личной отметки, `id` — непрозрачный ID поста. Ошибка без подтверждения не создаёт событие успеха. Смена игрока/мира во время запроса не переносит событие в новую сессию. ### A/B первого экрана — #205, 14.11.2026

Эксперимент `entry_v1` использует существующий счётчик Яндекс.Метрики `114170439`. POST `/events` принимает до регистрации только ограниченные события лендинга, описанные ниже; остальные события требуют app Bearer.

В коде подключены четыре JavaScript-цели. **До рекламного запуска их необходимо создать в настройках этого счётчика**, выбрав тип «JavaScript-событие» и точные идентификаторы:

| Идентификатор | Когда отправляется |
|---|---|
| `landing_view` | Лендинг действительно показан неавторизованному посетителю. Один раз на монтирование страницы, без дубля эффекта React StrictMode. |
| `landing_continue` | Нажата «Начать играть», открыт прежний экран авторизации. Повторный клик не дублируется. |
| `landing_auth_complete` | После нажатия получен app-доступ или сервер подтвердил внешнюю идентичность для регистрации. Это подтверждение входа, не завершение создания мира. Восстановление уже действующей сессии само по себе не создаёт цель. |
| `landing_first_post` | Сервер подтвердил создание первого обычного поста после участия в лендинге. Репосты, цитаты, комментарии, нажатие «Опубликовать» и ошибки запроса не засчитываются. Повторные посты в том же эксперименте не создают цель снова. |

Параметры целей: `landing_experiment=entry_v1`, `landing_variant=worlds|hogwarts|infobiz|evening|houses` (реально показанный экран), `landing_initial_variant` (исходная группа), `landing_switched=true|false`, `landing_source=link|direct`, а также прошедшие фильтр короткие UTM-коды. После «Начать играть» передаётся `landing_world_id` — ID выбранного шаблона из публичного API; он сохраняется для следующих шагов воронки. Явный параметр ссылки имеет приоритет над сохранённым экраном; без него показывается разводящая `worlds` с источником `direct`, независимо от ранее показанного варианта. При переключении обновляются вариант и UTM из новой ссылки, сохраняются исходная группа и отметка уже учтённого первого поста. Такие посетители получают `landing_switched=true`; их исключают из чистого сравнения, чтобы не приписывать конверсию другому экрану. Смена группы начинает новую попытку входа, а не продолжает незавершённую попытку предыдущего варианта. Очистка хранилища или другой браузер создают новое участие. Это клиентское измерение по подтверждённому ответу, не серверный реестр всех сохранённых постов: потерянный ответ может дать недоучёт.

Цели отправляются только production-сборкой. DEV-предпросмотр исключён из целей и локального закрепления. Нажатия, подтверждение входа и первый пост дополнительно используют существующее внутреннее событие `tap`, где `id` совпадает с именем цели, `kind` — вариант. Они доставляются в OpenObserve только после появления профиля; полный знаменатель в OpenObserve доставляется анонимными событиями через `/events` без ожидания профиля.

Метрика сравнения — уникальные посетители с `landing_first_post` / уникальные посетители с `landing_view`, по одной группе и рекламной кампании, с фильтром `landing_switched=false` (у исторических событий до исправления допустимо отсутствие поля). «Первый» здесь — первый подтверждённый обычный пост после участия в эксперименте, не обязательно первый за всю жизнь старого аккаунта. Промежуточные конверсии: `landing_view` → `landing_continue` → `landing_auth_complete` → `landing_first_post`.

Граница атрибуции: один браузер. Если на прежнем экране авторизации пользователь выбирает переход во внешний Telegram Mini App или продолжает с другого устройства, сквозной перенос посетителя и группы не реализован. Не выдавать такие переходы за измеренные конверсии. Провайдеры входа и их кнопки сохранены.


### Сбор A/B входа в OpenObserve

POST `/events` сохраняет существующий предел AnalyticsBatchRequest: до 100 событий. Специальные rate limit и size limit этим PR не добавляются. Фронт отправляет события лендинга по одному; используется прежний контракт session, platform, experiments, events с name, t, screen и props.
До авторизации обрабатываются только landing_view, landing_continue, landing_auth_complete,
landing_world_selected, landing_character_selected, landing_reaction_viewed; остальные события игнорируются без загрузки профиля и миров. Для landing-событий проверяются имя, UUID посетителя/попытки/события, варианты, bool, источник, время и формат известных UTM. Неизвестные свойства не экспортируются.
Идентификаторы посетителя, попытки и события — случайные UUID. Тексты, имена, контакты, IP и полные URL не должны передаваться. UTM должны быть короткими кодами кампаний до 64 символов; фильтр символов не гарантирует отсутствия личных данных и не подтверждает подлинность посещения.

Событие `landing_profile_link` через тот же POST `/events` требует обычный JWT: сервер сам добавляет существующий
player_id и возраст профиля. Идентификатор игрока из клиентских props игнорируется. Анонимная попытка связать профиль и недействительный app-токен получают 401.
Первый обычный пост подтверждается post_scored, а не публичным событием клиента.
Входные события имеют activity_kind=entry, связь — attribution: они не
увеличивают DAU и число зарегистрированных профилей. Авторизация и показ реакции
остаются браузерными сигналами; связь профиля и публикация проверяются сервером.

Фронт сохраняет до 20 неподтверждённых событий не старше 24 часов; повторная
отправка использует тот же event_id. События отправляются по одному: ошибки сети и 429 повторяются, а 400 удаляет только неверное событие и не теряет следующие корректные события. Счётчики используют уникальных посетителей/попытки, а не число записей.
Без доступного localStorage идентификация сохраняется только в памяти страницы.
Метрика продолжает получать прежние цели параллельно, но не является обязательным
источником продуктовой воронки после выпуска этого сбора.

Сборщик `/events` принимает пять вариантов посадочных: `worlds`, `hogwarts`, `infobiz`, `evening`, `houses`, включая исходную группу. Остальные значения отклоняются.

После запуска число посещений и конверсии по рекламным кампаниям сверяются между OpenObserve и Яндекс.Метрикой. UTM сами по себе не доказывают подлинность отдельного посещения; фактическая сверка ещё не выполнена.

### Аналитика уведомлений

`notification_sent` отправляется в product только после успешного ответа Telegram
или сервиса Web Push. Это принятие сервисом, не гарантия доставки на устройство.
Поля: `player_id`, `prop_id` (ID уведомления), `prop_kind=telegram|webpush`,
`event_time_unix_ms`; `activity_kind=delivery`, чтобы отправка не увеличивала DAU.
Не логируются текст, chatId, endpoint или ключи подписки.

`notification_opened` с `kind=webpush` и `id` уведомления записывается после клика
по Web Push и появления авторизованного профиля: при фокусе уже открытого окна
или запуске нового. URL-маркер удаляется после учёта открытия. Открытия Telegram
не измеряются: у текущего текстового сообщения нет отдельного отслеживаемого
перехода. Исторические отправки и открытия не восстанавливаются.

`comment_created` — сервер успешно сохранил комментарий или ответ игрока вместе
со списанием энергии. Событие отправляется после commit, только для автора-игрока;
AI-ответы и повтор requestId не учитываются. Поля: `id` (ID комментария),
`kind=comment|reply`, мир, шаблон, сложность и возраст. Текста комментария нет.
Клиентский /events не принимает это событие как подтверждение сохранения.

### Диагностика пути до первого ответа

События до входа с посадочной идут в Яндекс Метрику с одним `entry_id`. Цели текущей кампании `landing_continue` и `landing_auth_complete` по-прежнему относятся к пути «Начать играть». Прямой вход размечается отдельными целями. Текущий набор анонимных событий OpenObserve сохраняется: сервер принимает только существующий список, поэтому новые шаги до входа там не появятся.

| Шаг | Событие и разрез |
| --- | --- |
| Выбор входа на посадочной | `landing_continue` — «Начать играть», `landing_login_click` — «Войти» |
| Посадочная до клика | `landing_catalog_result`, `landing_catalog_retry`, `landing_world_action`: загрузка каталога, повтор, выбор или переход к миру |
| Показ экрана входа | `landing_auth_view` |
| Действие входа | `landing_auth_provider_selected`, `landing_auth_resume`; провайдер и тип действия, где их сообщает интерфейс |
| Результат провайдера | `landing_auth_provider_result`: подтверждение от провайдера, ошибка, известная отмена или ошибка загрузки виджета |
| Результат обмена с API | `landing_auth_verified`: действующий аккаунт или нужна регистрация; `landing_auth_exchange_error`: обмен не удался |
| Продолжение регистрации | `landing_age_view`, `landing_age_consent`, `landing_age_continue`: показ, действие с согласием и переход дальше |

После появления профиля OpenObserve получает `screen_view` и `tap` с явными ID действий: выбор мира, персонажа, настроения, открытие первого редактора, вход в разговор, выбор героя, отправка ответа, следующий пост, возврат к обучению и получение награды. Стандартные нижние кнопки видны как `cta_main`/`cta_second` в разрезе `screen`. Действия из внешних виджетов видны только там, где SDK отдаёт сигнал. Тексты, год рождения, токены и сырые ошибки в новых событиях не передаются.

Для обучения `onboarding_step` различает подтверждённые `world_saved`, `post_saved`, `reply_saved`, начало ответа `reply_started`, результат начальной реакции `initial_reaction_result` и выдачи `reward`. Ошибки сохранения и генерации имеют `ok=false` и, где доступно, HTTP-статус или `unconfirmed`.

Предложение новой истории передаёт в `onboarding_step` шаги `next_story_shown`, `next_story_accepted`, `next_story_dismissed`, `next_story_role`, `next_story_world_saved`, `next_story_post_saved`. `template_id` — ID предложенного или выбранного шаблона. `kind` при принятии — `same_world`, `other_world` или `catalog`, при выборе роли — `preset` или `custom`. Для готовой роли `star` содержит ID персонажа из шаблона. Сохранение поста отмечается после подтверждения обычной публикации в новом экземпляре мира.

### Гостевая пробная история (#352)

`landing_continue` остаётся кликом по главной кнопке посадочной, `landing_auth_complete` — подтверждённым завершением входа на пути с выбранным миром. В Метрике добавляются `landing_guest_start`, `landing_guest_screen`, `landing_guest_action`, `landing_guest_save_click`, `landing_registration_view` и `landing_registration_consent`. Разрезы `guest_world`, `guest_hero`, `guest_screen`, `guest_action` позволяют отличить просмотр шага от нажатия: выбор героя, начало истории, редактор, пробная публикация, разговор, отправка ответа и получение пробной награды. `landing_login_account_missing` отдельно отмечает вход без найденного аккаунта. Первая пробная публикация и ответ остаются локальными и не создают событий серверного поста или комментария. После регистрации черновик переносится в созданный мир, первый реальный пост и ответ считаются по существующим серверным событиям.

Гостевая карточка результата (#356) использует существующие цели Метрики: `landing_guest_screen` с `guest_screen=02-3_result` и `landing_guest_action` с `guest_action=open_conversation`, далее `send_demo_reply`. Гостевой показ и ответ остаются в гостевой воронке. Сохранение реальных постов и комментариев подтверждают отдельные серверные события в OpenObserve; демо-действия не включаются в метрики сохранённых действий и D1. Анимация, плакаты и виброотклик не передают отдельные события.

### Цели продукта в Яндекс Метрике

Счётчик `114170439` получает `registration_complete` после успешного создания профиля, в том числе после гостевой игры. Повтор с `409` не учитывается. `login_complete` относится к успешному новому входу в существующий профиль через Telegram Mini App, Telegram Login, VK или Яндекс. Обновление токена и выдача первых токенов после регистрации цели не дают. `invite_friend_click` относится к нажатию кнопки перехода к приглашению. Копирование ссылки и открытие окна отправки уже со страницы приглашения эту цель не повторяют.

Цели используют сохранённые UTM и вариант посадочной, если они доступны. Для `dau` в настройках счётчика требуется точное совпадение идентификатора, чтобы `invited_friend_dau` учитывалась отдельно.

После подтверждённого сохранения мира, публикации или комментария игрока браузер передаёт тип и ID действия через same-origin `POST /analytics/goals`. Основное действие не ждёт аналитику. Nginx по фиксированному запросу к `product` OpenObserve возвращает только имена целей. Если события ещё нет в телеметрии, браузер коротко повторяет запрос после `202`. Доступ к OpenObserve остаётся на сервере. Ручка принимает только ID игровых действий за последние 15 минут, ограничивает частоту запросов и возвращает коды целей; это не проверка авторизации игрока.

`post_1_daily` и `post_3_daily` относятся к первой и третьей обычной публикации профиля во всех мирах за календарные сутки МСК. `dau` относится к первому за сутки успешному созданию мира, публикации (включая репост и цитату) или комментарию игрока. `invited_friend_dau` относится к первому такому действию после подтверждённой регистрации по приглашению; регистрация должна быть в пределах 90 дней истории. Демо-действия гостя учитываются после сохранения в профиле. Запрос дедуплицирует серверные события по ID, а браузер сохраняет обработанные действия локально. Очистка хранилища, другие устройства, отсутствующая или поздняя телеметрия могут изменить учёт. Имена целей связываются с UTM, сохранёнными в момент действия. Прежние игровые API и их ответы не меняются.

Для дедупликации событий прогресса используем `player_id + world_id + prop_id`, где `prop_id` состоит из даты карточки, типа, цели и нового значения. Снимок подтверждает изменение прогресса, но не связывает его с конкретным кликом. Текстов, имён и ID звёзд в полях нет.

Порядок обычных публикаций считаем по серверному `post_scored` с `prop_publication_kind=post` и уникальным ID поста после `player_created`. Комментарии и репосты могут быть сохранёнными действиями между первым и вторым постом. Методика и окна — в [описании воронки](dashboards.md#задания-дня-321).
