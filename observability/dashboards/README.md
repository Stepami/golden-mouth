# Дашборды OpenObserve

Воспроизводимые представления из [docs/dashboards.md](../../docs/dashboards.md): панели лежат рядом в виде SQL, а `build.py` собирает из них тела дашбордов.

## Что где

| Файл | Что это |
|---|---|
| `panel-sql/*.sql` | по файлу на панель, чистый SQL |
| `build.py` | собирает панели и раскладывает `product.json` и `load-and-llm.json` |
| `product.json` | дашборд «Реки: продукт», 9 панелей |
| `load-and-llm.json` | дашборд «Реки: нагрузка и LLM», 12 панелей |

## Как развернуть

1. `python3 -I observability/dashboards/build.py` — пересобрать JSON из SQL.
2. Отдать содержимое `product.json` целиком в инструмент `CreateDashboard` MCP-сервера OpenObserve. В файле уже готовые аргументы: `org_id` и `request_body`, дописывать ничего не нужно.

Панели выполняют SQL как есть (`customQuery: true`). `fields.x` задаёт ось времени или категории, `fields.y` — числовые значения, `fields.breakdown` — отдельные серии по кодам ответа и severity. Эти поля влияют на отображение результата.

## На чём стоят запросы

- Продуктовые панели читают поток `product`, технические — логи и трейсы `backend`, метрики идут через PromQL.
- MongoDB и вызовы модели используют `stream_type: traces`: одноимённый поток логов не содержит полей спанов.
- PromQL использует шаг `60s`. Строка `auto` не является допустимой длительностью и вызывает ошибку загрузки. Если серии 5xx отсутствуют, пустой график допустим и не означает ошибку запроса.
- HTTP-панели по логам считают завершения из `Serilog.AspNetCore.RequestLoggingMiddleware`, чтобы не учитывать повторно записи других логгеров.
- День в продуктовых панелях это `floor(_timestamp / 86400000000)`. Так надёжнее, чем через календарные функции, а обратно в дату переводит `to_timestamp_micros`.
- D1/D7 считаются по когортам первого наблюдаемого события; незавершённые окна исключаются. Weekly churn — прокси недельной неактивности с базой и числом ушедших, а не 100% минус D1.
- Сводка, сегменты, когорты, churn и активация используют panel_time_enabled + относительный диапазон 90d. Поэтому глобальные 4w не обрезают 30-дневный MAU. Подробные определения и ограничения — в docs/dashboards.md.
- `activity_kind = real` отсекает служебные события, поэтому DAU считается по живым игрокам, а не по всему потоку.
- Уровни ошибок в логах бэкенда: `severity` со значениями `Error`, `Critical`, `Fatal`. Поле кода ответа называется `statuscode`, а в трейсах то же самое уже `status_code`.

## Правка

Меняется SQL в `panel-sql/`, при необходимости подпись панели в `build.py`, дальше запускается `build.py`. Существующий дашборд обновляется через MCP `GetDashboard` → `UpdateDashboard`: сохранить его ID, folder и актуальный hash, заменить определения панелей из JSON. `CreateDashboard` нужен только при первом развёртывании, иначе появятся дубли. Порядок и размеры панелей задаются сеткой 192 колонки в `box(x, y, w, h, i)`.

Перед обновлением выполнить каждый SQL через MCP `SearchSQL` с типом потока из `fields.stream_type`, а PromQL — через `PrometheusRangeQuery` с шагом из `config.step_value`. Проверить как диапазон с данными, так и последние часы. После обновления перечитать дашборд и убедиться, что сохранены запросы, типы потоков и серии.
