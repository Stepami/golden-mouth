# Отношения, доверие и память поступков

Версия: `review-2026-10-20.5`. Предлагаемое расширение #192/#195 в PR #196. Код, API и миграции не реализованы. Этот контракт применяется к [сюжетным карточкам](stories.md) и свободной игре. Он не меняет действующий `Star.Relation`, его дневной лимит, достижения, энергию или подписчиков.

## Правила

Игрок может дружить, спорить, отказывать, сближаться или прекращать отношения. Сюжет доброволен. Согласие на романтику не требуется для прохождения. Для разнополых героев доступны дружба и добровольная взаимная романтика; для однополых — дружеские и конфликтные линии без романтики. Поддержка, верность и ответственность проявляются в поступках, а не назначаются оценкой текста.

Сюжетные сцены сохраняют выбранную хронологию. Новое знакомство не подменяет старую биографию, свободному герою не назначается чужое родство. Состав NPC, ID и ники остаются прежними. Ранний эпизод не получает отношения и знания будущего сезона.

Отношение, доверие и романтический статус независимы. Можно симпатизировать ненадёжному герою или уважать противника. Доверие не равно любви; числовое +3 существующей механики не создаёт пару.

## Данные пары

| Поле | Содержание |
| --- | --- |
| pair_key | Экземпляр мира и два стабильных actor_id. P означает владельца канала; выбранная роль хранится отдельно и не создаёт второго NPC. |
| direction | A → B. Отношение и доверие хранятся отдельно для каждого направления. Взаимность не предполагается. |
| attitude | ACQUAINTED, WARM, FRIEND, DEVOTED, RIVAL, ENEMY, HATE. При отсутствии контакта запись не создаётся. |
| trust | UNTESTED, RELIABLE, DAMAGED, REBUILDING, BROKEN. Это категории, не новая шкала очков. |
| romance | NONE, INTEREST, MUTUAL, PARTNER, SEPARATED. Состояние пары; интерес и согласия каждого участника сохраняются отдельно. |
| policy_id / version | Детерминированная политика NPC из таблицы ниже; её версия закреплена для действующей договорённости. |
| pact | ID, два участника, явное согласие каждого, тип обязательства, якорный пост/ветка, отдельные результаты сторон и состояние. Одновременно одна незавершённая договорённость на пару. |
| memory | ID события, причина, источник STORY/FREE, actor/target, operation_id, seq, предыдущие и новые значения. Один факт применяется один раз. |
| context_version | Версия эпизода и допустимые знания героев; свободная игра имеет собственный сохранённый контекст мира. |

Для готовых героев пол в предлагаемом справочнике задан явно: isabella/georgina/diana — F; eduard/yakov/gosha/roman/jon/james/greedy_wolf/2kotleti_news/alexey_nl — M. Для своего героя это необязательная характеристика вымышленной роли M/F/UNSPECIFIED, выбранная игроком; реальные данные пользователя не запрашиваются. При UNSPECIFIED романтические предложения не создаются. Пол не угадывается по имени, аватару, Telegram или тексту. Изменение роли не переписывает существующую пару; несовместимые романтические предложения закрываются без штрафа.

В первом контакте без сохранённой пары создаются ACQUAINTED/UNTESTED/NONE в обоих направлениях. Каноническая знакомость из завязки хранится как контекст, но не выдаёт статус «друг» или «пара» без пройденных событий. Если пара уже существует, старт главы не обнуляет её. Для NPC ↔ NPC применяется тот же reducer, но факты создаёт только явно указанная сценарная сцена; генерация фонового поста сама по себе отношения не меняет.

## Что считается событием

Свободный текст не определяет намерение. Рядом с обычным ответом можно явно выбрать предложенный социальный поступок: поддержать, объявить соперничество, принять договорённость, разделить авторство, присвоить результат, предложить примирение или сближение. Нейтральное «Ответить без выбора» всегда доступно; без social_ref это обычный оплаченный ответ без изменения нового социального статуса. Успешная публикация/ответ сохраняет текст и типизированный выбор в одной операции. Выбор не является отдельным платным ходом; стандартная стоимость действия берётся из баланса.

Предлагаемая social_ref содержит offer_id, choice_id, pair_version и одноразовый серверный token. Не более одной social_ref на оплаченный ход; actor берётся из авторизованного владельца, для ответа target должен совпадать с основным NPC этого хода; для CORRECTION_PUBLICATION, RESTORE_RECORD и сюжетного PUB target берётся из указанного pact, ответ NPC не является условием; сервер закрепляет тип публикации и карточку, а не принимает произвольную цель. Для выбора без генерации действует тот же контроль доступа и версии. Сервер заранее выдаёт `social_offer_id` с допустимыми choice_id, участниками, якорями, версией пары и условиями. При отправке проверяются автор, мир, состав, ID пары, NPC, пост, непосредственный родитель, версия, разрешённый выбор и успешный коммит. Самовольный choice_id, скрытый объект или устаревший offer отклоняются до генерации и списания. Угаданный клиентом результат не принимается. Без social_ref обычный пост/ответ не изменяет новый автомат отношений; существующие эффекты игры сохраняются.

Факт содержит `(event_id, operation_id, pair_key, actor, target, source, context_version, choice_id, offer_id, pact_id, post_id, parent_id, seq)`. При коммите порядок фиксирован: операция и явные выборы → результат договора → отношение/доверие → романтическое следствие разрыва → память. Проверки сюжетного перехода читают снимок этой же подтверждённой операции. Управляющие запросы и обычные ходы сериализуются по версии пары. Результат NPC является отдельным сохранённым enum, вычисленным политикой по версии пары до генерации текста. Ответ LLM не может поменять его. Ошибка, отказ или откат операции не создают социального факта. Посты NPC, реакции и текст «люблю» без соответствующего выбора также не создают его.

## Договорённость

Предмет свободного договора типа SHARED_CREDIT — совместное обсуждение с общим авторством, а не обещание физического спасения или реальной проверки AI. Предложение задаёт два независимых вклада: существующий NPC сохраняет отдельный подготовленный пост-дополнение q_contribution; игрок отвечает на него с явным выбором SHARE_CREDIT либо TAKE_CREDIT. Публикация NPC бесплатна и не даёт игроку XP или подписчиков. Оплаченный ответ имеет обычные эффекты треда; отдельной награды за отношения нет.

| Состояние договора | Событие / точное условие | Новое состояние |
| --- | --- | --- |
| OFFERED | ACCEPT_PACT: игрок выбрал принятие под указанным постом; NPC заранее сохранил ACCEPT по своей политике | ACTIVE |
| OFFERED | DECLINE_PACT: явный отказ любой стороны | CLOSED_NEUTRAL |
| ACTIVE | NPC_CONTRIBUTION: сохранён новый GamePost q_contribution с AuthorId = NPC, pact_id и уникальным alias | NPC_READY |
| NPC_READY | SHARE_CREDIT: новый корневой ответ P под q_contribution (parent = null) и основной ответ NPC в той же операции; actor/target/pact/choice совпадают | FULFILLED |
| NPC_READY | TAKE_CREDIT: тот же предикат адресного ответа, но явный выбор присвоить общий результат | BROKEN_BY_P |
| ACTIVE или NPC_READY | MUTUAL_CANCEL: явная отмена игрока и сохранённое согласие NPC | CLOSED_NEUTRAL |
| Любое незавершённое | Пауза, выход из сюжета, другой мир, отсутствие энергии, пропуск дня | То же состояние |
| Любое | Повтор операции, не тот автор/пост/родитель, обычный текст | То же состояние |
| FULFILLED, BROKEN_BY_P, CLOSED_NEUTRAL | Любое новое событие | То же конечное состояние |

В этой первой схеме NPC не предаёт произвольно: он либо принимает договор и вносит вклад, либо отказывается по политике. Обоюдное предательство NPC потребует отдельного заполненного события и последствий, не случайной реплики. Стороны могут совместно отменить договор без потери доверия; политики ниже принимают такой запрос всегда. Нет календарного дедлайна. Недоступный NPC/объект приостанавливает договор, не создаёт нарушения. Необратимо удалённый якорь закрывает договор как CLOSED_NEUTRAL с причиной CONTEXT_LOST, без отката обычной экономики.

## Переходы отношения и доверия

Таблица задаёт изменение направления NPC → P, поскольку поступок совершил игрок. Обратное направление меняется только отдельным явным выбором игрока; один NPC не назначает игроку чувства. Взаимный договор позволяет отдельно предложить обоим дружбу. Выборы не из таблицы и непройденные guards оставляют состояние прежним. Guard применяется к снимку до события; несколько строк с одинаковым событием имеют непересекающиеся условия.

| Событие | Предусловие | Отношение NPC → P | Доверие NPC → P | Последствие |
| --- | --- | --- | --- | --- |
| SUPPORT | Новый offer поддержки; attitude = ACQUAINTED | WARM | Без изменения | NPC допускает предложение совместного обсуждения |
| SUPPORT | Любое другое attitude | Без изменения | Без изменения | Поддержка остаётся в памяти; одного жеста недостаточно для примирения |
| COMPETE | Явный offer соперничества; attitude не ENEMY/HATE | RIVAL | Без изменения | Публичный спор без обвинения в предательстве |
| COMPETE | attitude = ENEMY/HATE | Без изменения | Без изменения | Степень конфликта не понижается сама |
| PACT_FULFILLED | trust = UNTESTED/RELIABLE и attitude = ACQUAINTED/WARM/RIVAL | FRIEND | RELIABLE | Открывается предложение нового совместного дела |
| PACT_FULFILLED | trust = UNTESTED/RELIABLE и attitude = FRIEND/DEVOTED | DEVOTED | RELIABLE | Открывается сцена союзнической поддержки |
| PACT_FULFILLED | trust = REBUILDING | ACQUAINTED | RELIABLE | Рабочее доверие восстановлено; прежняя дружба не возвращается автоматически |
| PACT_BROKEN | До события нет ни одного PACT_BROKEN этой пары | ENEMY | DAMAGED | Новое совместное дело закрыто до примирения |
| PACT_BROKEN | До события есть хотя бы один PACT_BROKEN другого pact_id этой пары | HATE | BROKEN | Сцена открытой вражды; романтическое сближение закрыто |
| REPAIR_ACCEPTED | trust = DAMAGED/BROKEN; политика NPC вернула ACCEPT | RIVAL | REBUILDING | Разрешён один восстановительный договор |
| REPAIR_DECLINED | trust = DAMAGED/BROKEN; политика вернула DECLINE | Без изменения | Без изменения | Требуется предложенный политикой конкретный исправляющий поступок |
| DECLINE_PACT, MUTUAL_CANCEL | Валидный явный выбор | Без изменения | Без изменения | Без штрафа и без обвинения в предательстве |

NPC_CONTRIBUTION и NPC_INTEREST создаются только серверным исполнителем по сохранённым правилам; клиент не может прислать их от лица NPC. PACT_FULFILLED применяется только к терминальному факту данного pact; PACT_BROKEN — только к BROKEN_BY_P. В DAMAGED/BROKEN обычные договоры не выдаются, поэтому иных сочетаний PACT_FULFILLED нет. При повторном разрыве учитывается история отличных pact_id, даже если доверие между ними успело восстановиться. Две строки PACT_BROKEN разделены отсутствием/наличием предыдущего нарушения и не пересекаются. Исправляющее действие не обязано доказывать искренность текста.

Если игрок явно выбирает «Считать другом», его направление P → NPC меняется на FRIEND/RELIABLE только при FULFILLED и trust = RELIABLE в NPC → P; «Сохранить дистанцию» оставляет прежнее. «Стать союзником» даёт DEVOTED/RELIABLE только после следующего отличного pact со статусом FULFILLED: при выборе FRIEND сохраняются friend_pact_id и friend_seq; новый pact завершается после friend_seq. Старый второй договор задним числом не подходит. «Считать соперником/врагом» задаёт RIVAL/ENEMY в направлении P → NPC, не изменяя автоматически NPC. HATE в направлении P → NPC задаётся только отдельным SET_HATE с явным подтверждением, когда сохранённое предыдущее отношение P → NPC уже ENEMY; по тексту конфликт не определяется. SET_RIVAL и SET_ENEMY требуют существующую пару и версию; это явные личные статусы игрока, не обвинение NPC в совершённом поступке.

Договоры принимаются и завершаются по одному. Один и тот же сохранённый пост или ответ не закрывает два договора; уже использованный receipt не используется повторно. Повтор поддержки под одним offer не повышает статус. Новый полноценный договор требует нового NPC-поста и двух отдельных оплаченных ответов игрока; бесконечные клики без игровых действий не развивают отношения. Это не ограничение по дням и не новый энергетический лимит.

## Характеры NPC и принципы доверия

Вдохновение: [The Evolution of Trust](https://ncase.me/trust/). Используются повторные встречи, память сотрудничества и цена нарушения договорённости. Турниры, монеты, случайные ошибки и эволюция популяций в игру не переносятся.

| Политика | Новый договор | Примирение |
| --- | --- | --- |
| RECIPROCAL | ACCEPT при trust = UNTESTED/RELIABLE/REBUILDING; иначе DECLINE | ACCEPT при DAMAGED. При BROKEN сначала требуется RESTORE_RECORD по нарушенному договору; затем ACCEPT |
| CAUTIOUS | При UNTESTED сначала WAIT_SUPPORT до явного SUPPORT в текущем offer; затем ACCEPT. При RELIABLE/REBUILDING сразу ACCEPT; иначе DECLINE | В DAMAGED/BROKEN сначала RESTORE_RECORD, затем ACCEPT |
| GRUDGE | Как CAUTIOUS | Сначала RESTORE_RECORD и отдельная CORRECTION_PUBLICATION, затем ACCEPT; только после нового выполненного договора восстанавливается рабочее доверие |

RESTORE_RECORD — исправляющее оплачиваемое действие для последнего BROKEN_BY_P этой пары по seq. Для SHARED_CREDIT это ROOT под q_contribution с основным ответом того же NPC и явной карточкой возврата общего авторства. Для EDITORIAL_PACT это новая PUB с social_ref на нарушенный pact, исходным HONOR-утверждением и ссылкой на ошибочную карточку; она показывает исправление публично, не удаляя старый поступок. Сервер проверяет тип договора, пару, последнюю нарушенную запись, карточку и новый receipt после нарушения. Смысл текста не проверяется. Результат сохраняется в pact.repair_receipt_id и публичной карточке; AuthorId и история постов не переписываются. Нет возврата энергии/подписчиков. При утраченном якоре создаётся явно связанный заменяющий пост с replaces_anchor_id; не ищем текст по смыслу. Старое исправление другого pact не открывает примирение после нового нарушения. Это действие само по себе не возвращает дружбу и не исполняет старый терминальный договор задним числом.

CORRECTION_PUBLICATION — новый пост P с явным social_ref на нарушенный pact и choice_id = CONFIRM_CORRECTION, созданный после RESTORE_RECORD. Связь с исходным договором, исправленная запись и авторы отображаются сервером в карточке публикации; смысл текста не проверяется. Он стоит обычную цену публикации, не даёт отдельной награды и используется только для одного pact. Это дополнительный путь GRUDGE, а не обязательная публикация для всех.

Политика NPC задаёт реакцию на поступки игрока, а не обязует игрока отвечать взаимностью. Последствие TAKE_CREDIT — присвоенное авторство; BREAK — выбранное публичное утверждение вопреки условию. Оба открывают конфликтный эпилог, без новых монет, подписчиков или XP. Долгая выгода сотрудничества — доступные совместные сцены и поддержка. Эти последствия не объявляются денежной выгодой и не меняют действующий баланс.

## Романтическая линия

Совместимость проверяется по явному справочнику, а не усмотрению LLM. Для готовых героев в текущих эпизодах ROMANCE_OPTIONAL разрешён только для пары isabella ↔ eduard мира evening. Остальные пары готовых героев — FRIEND_ONLY: в первом фильме Яков не получает будущую линию; школьные эпизоды ограничены первым годом; diana ↔ jon не получает романтику из-за родства, diana ↔ james — без неё по выбранным сценам; все IT-пары однополые. Для собственного героя по умолчанию допустим OWN_OPTIONAL с существующим NPC, если явно заданы разные M/F, нет заданного родства, совместим контекст и отсутствует другой PARTNER. UNSPECIFIED трактуется как FRIEND_ONLY. Более узкий FRIEND_ONLY в паспорте данного сюжетного offer имеет приоритет; свободный offer использует контекст мира и этот справочник. Новые разрешения требуют версии данных, не догадки генератора.


Романтические offers разрешены только при явно известных разных M/F, совместимом эпизоде и FRIEND/DEVOTED + RELIABLE в обоих направлениях. Текущая дружба не заменяет согласия. У каждого героя одновременно один PARTNER в экземпляре мира; начатая пара не меняется скрыто. Подтверждение проверяет занятость обоих actor_id среди всех пар атомарно: два одновременных подтверждения разных пар с одним героем не могут оба пройти. Это требует контроля версий участников или эквивалентного ограничения хранения при реализации. В первом фильме Яков не получает будущую романтическую линию и знания сиквелов. Ранние школьные эпизоды не выдают пару за один урок: для них указан путь FRIEND_ONLY. Будущая романтика требует отдельной подходящей карточки, а не возраста, угаданного генератором.

| Из | Событие и guard | В | Последствие |
| --- | --- | --- | --- |
| NONE | EXPRESS_INTEREST от P; романтический offer разрешён | INTEREST | Сохраняется интерес P; интерес NPC не подразумевается |
| INTEREST | NPC_INTEREST = ACCEPT по политике, обе стороны FRIEND/DEVOTED + RELIABLE | MUTUAL | Зафиксирована взаимная симпатия, ещё не пара |
| INTEREST | NPC_INTEREST = DECLINE либо P выбирает отозвать интерес | NONE | Дружба и доверие сохраняются |
| MUTUAL | CONFIRM_PAIR от P и NPC, нет другого PARTNER, guard совместимости сохранён | PARTNER | Открывается линия пары: поддержка, верность, общие решения |
| MUTUAL | Любая сторона отказывается от пары | NONE | Без штрафа за отказ |
| PARTNER | Явный BREAK_UP любой стороны либо PACT_BROKEN | SEPARATED | Пара прекращена; простое расставание не является предательством, отношение/доверие меняются только по отдельной причине |
| SEPARATED | Новый EXPRESS_INTEREST при заново выполненных условиях | INTEREST | Возврат требует новой взаимности |
| Любое | Неподходящий offer, другой actor, повтор или отсутствующий guard | То же | Ничего не назначается по тексту |

Решение NPC_INTEREST детерминировано: ACCEPT только если offer разрешает эту пару и взаимные guards выполнены; иначе DECLINE. Безусловной любви по запросу нет. CONFIRM_PAIR требует нового явного согласия обеих сторон после MUTUAL. При FRIEND_ONLY такие offers не выдаются. Это логика вымышленных отношений; NPC не говорит от лица реального IT-прототипа.

## Сюжетная договорённость

EDITORIAL_PACT — отдельный тип для 16 эпизодов. Это условие публичного общения: сохранить оговорку, не присвоить согласие или вклад. Конкретный предмет, главный NPC, разрешённые карточки и якоря заполнены в [stories.md](stories.md#карточки). История не требует после финала ещё раз пройти общий разбор с авторством ради доверия: выполнение договора и поддержка уже входят в основной исход.

| Состояние договора | Факт и guard | Новое состояние |
| --- | --- | --- |
| OFFERED | ACCEPT_WITH_SUPPORT с story_ref/social_ref, совпадающими run, парой, версией, условием и нужным ROOT/CHILD; политика заранее ACCEPT | ACTIVE |
| ACTIVE | Подтверждён q_contribution от того же NPC, pact_id, context_version и alias | NPC_READY |
| NPC_READY | HONOR: разрешённая серверная карточка соблюдённого условия в точном ROOT либо PUB, указанном паспортом; одна подтверждённая операция | FULFILLED; PACT_FULFILLED |
| NPC_READY | BREAK: такой же адресный guard, но карточка нарушения; одна подтверждённая операция | BROKEN_BY_P; PACT_BROKEN |
| OFFERED/ACTIVE/NPC_READY | Явный WITHDRAW с согласованным MUTUAL_CANCEL; политики принимают нейтральный выход | CLOSED_NEUTRAL |
| Любое незавершённое | Пауза, нет энергии, свободный пост, день без игры | То же |
| Любое | Повтор, другой pact, неверный якорь, свободный текст без выбора | То же |
| FULFILLED/BROKEN_BY_P/CLOSED_NEUTRAL | Любое событие договора | То же конечное состояние |

HONOR/BREAK не синонимы «хорошего/плохого текста». Для каждого эпизода заранее заполнены две разные серверные карточки с конкретным утверждением и последствием. Договор хранит condition_id, honor_card_id, breach_card_id, resolution_kind (ROOT/PUB), точный anchor, snapshot и receipt. Нельзя заменить тип разрешения, NPC или карточку клиентским запросом. PUB создаётся игроком; исполнитель не пишет его за пользователя. При принятии показываются обе возможные развязки, включая отказ без нарушения.

Публикация q_result с SUPPORT/REJECT нужна для сюжетной развязки, но не является вторым применением PACT_FULFILLED/BROKEN. Поступок меняет пару один раз в операции HONOR/BREAK. После HONOR доверие RELIABLE; при прежнем REBUILDING отношение ACQUAINTED, при новом контакте FRIEND. В обоих случаях NPC может поддержать конкретную совместную запись. Это не означает полного прощения или взаимной дружбы. P → NPC остаётся явным выбором P. COMPETE со вторым NPC в многоголосом эпизоде не изменяет главную пару.

## Режимы и продолжение отношений

Обычные свободные публикации и ответы не двигают сюжет. Социальные offers могут работать вне сюжета с source = FREE; для прежнего совместного разбора используется SHARED_CREDIT. В сюжетном ходе source = STORY, валидны обе привязки, максимум одна social_ref на ход. Источник меняет только связь с запуском; память и состояние пары общие. Подтверждённый свободный договор не засчитывается задним числом в сюжет.

Пары сохраняются после F_SUPPORT/F_CONFLICT/F_DISTANCE и между будущими главами. Старт и повтор эпизода не сбрасывают доверие. Повторное нарушение после прежнего примирения остаётся повторным. Нет награды за перезапуск или за очередное объявление дружбы. Отказ политики из-за DAMAGED/BROKEN показан бесплатно; можно закончить эпизод без союза, а примирение провести отдельно.

Запрос примирения, отказ/взаимная отмена, романтические согласия и явные статусы игрока — бесплатные типизированные запросы с версиями, без AI-хода и экономических наград. SUPPORT/COMPETE и принятые действия договора прикреплены к обычной оплаченной операции. Для CAUTIOUS/GRUDGE ACCEPT_WITH_SUPPORT применяет SUPPORT и ACCEPT атомарно; один ответ не списывается дважды. Доступность проверяется до генерации и ещё раз перед коммитом; один активный договор пары блокирует принятие другого до выполнения/взаимной отмены; неверная версия любой привязки откатывает весь совмещённый ход.

## Отношения между NPC

В текущих 16 социальных эпизодах автоматических событий NPC ↔ NPC нет. Спасение от тролля и уход с поляны — уже случившийся фон, который не назначает новые игровые статусы после комментария игрока. Пара NPC может меняться только по отдельному явно заполненному событию с участниками, якорем, версией и последствиями; таких событий в текущем наборе нет. Нельзя выводить их из генерации поста или из канонической дружбы. Это не мешает передавать каноническую знакомость в контекст без подмены сохранённых отношений.

## Приёмка

- Одинаковые версии пары, политика и событие дают одинаковое новое состояние; текст LLM на результат не влияет.
- Два направления, два разных мира и две пары не смешиваются; один receipt не закрывает два договора.
- Любой обычный ответ без social_ref оставляет новые статусы прежними; действующий числовой Relation продолжает жить по прежнему правилу.
- Два одновременных CONFIRM_PAIR с одним actor_id дают максимум одну пару.
- Поддержка не означает согласие на романтику. Отказ от договора, сближения, сюжета и пауза не являются предательством.
- SHARE_CREDIT/TAKE_CREDIT и HONOR/BREAK под чужим постом, с неверным parent, actor, pact_id или старой версией не засчитываются.
- Первый разрыв даёт ENEMY/DAMAGED, повторный после примирения — HATE/BROKEN. RESTORE_RECORD и новый завершённый договор позволяют восстановить рабочее доверие, не стирая память.
- При разных M/F и полном взаимном согласии возможен PARTNER; при одинаковых M/F или FRIEND_ONLY — нет. NONE/INTEREST никогда не равны согласию на пару.
- У каждого из 16 эпизодов есть собеседник, допустимый в его хронологии. Физические встречи не запускаются комментарием; автоматических изменений NPC ↔ NPC нет. Выбранный герой не возвращается в NPC.
- Решающий ответ NPC (согласие, отказ, условия примирения) показывается серверной заготовкой из сохранённого enum. LLM получает этот результат и текущую хронологию для дополнительных реплик, но не пишет решение заново. Никакой смысловой классификатор не определяет переход. Действующая модерация и ошибки AI-хода обрабатываются штатно, без автоматической перегенерации.

Это спецификация нового социального слоя, не подтверждение готового runtime. Перед реализацией нужны проверки транзакционности, конфликтов версий, доступа и воспроизведения событий на изолированных данных. Долгий сюжет и удовольствие от него проверяются на игроках, а не выводятся из числа состояний.
